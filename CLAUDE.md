# Проект: анализ финансового состояния российского юрлица по РСБУ

Локальный контур. Данные не покидают машину. Внешние LLM-API запрещены.

## Что строим

Пользователь вводит ИНН → система забирает годовую бухгалтерскую отчётность,
нормализует её по кодам строк, считает коэффициенты, присваивает класс
финансового состояния и формирует аналитическое заключение в Word.

## Инварианты — нарушать нельзя ни при каких обстоятельствах

1. **Языковая модель не вычисляет.** Все числа считает Python/SQL. Модель
   получает готовые значения и пишет только текст. Любой код, где модель
   просят «посчитать», «оценить долю», «определить класс» — ошибка архитектуры.
2. **Класс финансового состояния определяется детерминированно.** Скоринг —
   арифметика по фиксированным весам, зафиксированным в `methodology/`.
   Модель не имеет права его пересматривать.
3. **Каждое число в заключении привязано к коду строки или коду показателя.**
   Число без источника в выходной документ не попадает.
4. **«Не раскрыто» ≠ 0, но у этого две трактовки по контексту.** В отчётности
   прочерк, «X» и пустая ячейка означают отсутствие раскрытия. В БД это `NULL`.
   Для **расчёта коэффициентов** отсутствие остаётся `NULL`, показатель
   получает `not_calculable`, подстановка нуля запрещена. Для **проверки
   арифметики итога** нераскрытая строка считается нулём — иначе контроль
   сходимости разваливается на любой упрощённой форме, где организация
   раскрывает три строки из семи (проверено: у ПК «Стройсервис» итог 2400
   сходится при отсутствующей строке 2330). Одно значение, две трактовки;
   смешивать их нельзя. Причина нераскрытия хранится в `fact_report.value_status`:
   `ok` — значение раскрыто, `not_disclosed` — прочерк, «X» или пустая ячейка,
   `not_applicable` — строка неприменима к форме отчётности организации.
   Значение и статус связаны ограничением БД: `value IS NOT NULL` тогда и
   только тогда, когда статус `ok`. Разбор ячейки делает
   `utils.parse_value`, который различает пустую ячейку (`missing`), явный
   прочерк (`not_disclosed`) и нечисловое содержимое (`invalid`);
   `to_decimal` остаётся коротким вариантом, когда причина не важна.
5. **Денежные величины — только `Decimal`.** `float` для сумм и коэффициентов
   не используется нигде, кроме визуализации. Округление — явное, через
   `quantize`.
6. **Данные, не прошедшие контроли качества, в расчёт не идут.** Отчётность
   уходит в карантин, причина пишется в `dq_log`. Карантин ставится
   на **комплект** (`src_file.status`), а блокирующие контроли применяются
   только к **отчётному периоду** комплекта: за сравнительные колонки отвечают
   те комплекты, для которых эти периоды отчётные. Расчёт обязан отбрасывать
   факты из комплектов в карантине — `quality.runner.quarantined_src_files`.
7. **Секреты только в `.env`**, который в `.gitignore`. Реальные данные
   отчётности в репозиторий не коммитятся. Единственное исключение —
   `data/raw/probe/`: несколько публичных ответов ГИР БО, сохранённых как
   фикстуры, чтобы тесты не обращались к ФНС на каждом прогоне. Отчётность
   организаций, которые анализируются по запросу, не коммитится никогда.
8. **Ответ модели проходит постпроверку на посторонние числа.** Не прошёл —
   не показывается пользователю, пишется в `llm_log` с пометкой.

## Стек

- Python 3.12, менеджер окружения `uv` (запуск: `uv run ...`, не `pip`)
- **PostgreSQL 17 через Homebrew**, база `findb`, локальное подключение от
  пользователя системы без пароля. **Docker в проекте не используется,
  команды `docker exec` не применять.** SQL выполняется через
  `psql findb -f файл.sql`
- Ollama локально, `http://localhost:11434/v1`
- `psycopg2-binary` + сырой SQL. ORM не используем
- `httpx` для HTTP. LangChain, LlamaIndex и подобные надстройки — не ставить
- `pytest` для тестов, `ruff` для линтинга
- `python-docx` для выгрузки заключения

## Правила кода

- Типизация обязательна, возвращаемые типы указываем всегда.
- Docstring на русском, одной строкой, по существу.
- Никаких «магических чисел»: нормативы, веса, пороги — только из
  `methodology/*.yaml`, не в коде.
- Деление: всегда явная обработка нуля и `None`. Функция-хелпер
  `safe_div(a, b) -> Decimal | None`, которая возвращает `None`, а не ноль
  и не бесконечность.
- Все обращения к внешним источникам кэшируются на диск в `data/raw/`
  в исходном виде. Повторный запуск не должен дёргать сеть.
- Идемпотентность загрузки: повторная обработка той же отчётности не создаёт
  дублей (`ON CONFLICT ... DO UPDATE`). Если при этом значение строки
  изменилось, факт перезаписи пишется в `dq_log` с `check_code =
  'fact_overwrite'`, статусом `info` и прежним значением в `previous_value` —
  молча затирать ранее загруженное число нельзя. Совпавшее значение не
  переписывается вовсе: `updated_at` не трогается, журнал не засоряется.
- Загрузка комплекта — **одна транзакция**: снятие `is_actual` с прежних
  версий, запись `src_file` и запись фактов происходят вместе. Иначе при сбое
  посередине в базе остаётся либо ноль актуальных версий, либо две.
- Логирование через `logging`, не `print`, кроме CLI-вывода.

## Правила работы для Claude Code

- Перед изменениями больше чем в одном файле — сначала план, потом код.
- **Правки файлов вносятся только инструментом редактирования.** Генерация
  python/bash-скриптов для изменения файлов проекта запрещена, включая
  однострочные правки и конфиги в `methodology/` и `prompts/`. Скрипт прячет
  дифф и подменяет саму правку обёрткой вокруг неё, а на конфигурационные
  файлы тестов нет — дифф там единственный контроль.
- Одна задача = один коммит с осмысленным сообщением на русском.
- После каждой задачи: `uv run pytest` и `uv run ruff check .` должны быть
  зелёными. Не зелёные — задача не выполнена.
- **Не выдумывать формат внешних источников.** Если структура ответа ГИР БО
  неизвестна — сначала сделать пробный запрос, сохранить сырой ответ,
  показать его мне, и только потом писать парсер.
- **Не подставлять моки вместо реальных данных молча.** Если что-то не
  работает, сказать об этом, а не сгенерировать правдоподобную заглушку.
- Не добавлять зависимости без явного согласования.
- Не трогать `.env` и содержимое `data/`.
- Если моя формулировка задачи противоречит инвариантам выше — остановиться
  и сказать об этом, а не выполнять.

## Формулы

Полный расчётный аппарат — в `methodology/metrics.yaml`. Формулы заданы
в кодах строк РСБУ (баланс 1100–1700, ОФР 2100–2400, ОДДС 4100–4500).
Средние балансовые величины — полусумма на начало и конец периода.

Справочник строк — `methodology/lines.yaml`, загрузчик `normalize/lines.py`.

**Два набора строк.** `reporting_type: full | simplified` — полные формы и
упрощённые (приложение 5 к приказу 66н). Ключ справочника — пара
`(reporting_type, code)`: один код может существовать в обоих наборах и
означать разное. Пример: 2120 в полном наборе — «Себестоимость продаж»,
в упрощённом — «Расходы по обычной деятельности» вместе с коммерческими и
управленческими. Совпадение или различие смысла объявляется полем
`same_meaning_as_full`, иначе справочник не загрузится.

Тип отчётности хранится в `src_file.reporting_type` — это свойство сданного
комплекта, а не организации: право на упрощённую отчётность утрачивается при
росте выручки или обязательном аудите. Контроли качества выбирают набор
проверок по нему.

**Код упрощённой строки — подсказка, а не ключ.** В упрощённых формах код
укрупнённой строки указывается по показателю с наибольшим удельным весом и
между периодами меняется. Поэтому строка опознаётся по наименованию
(`match_by_name`), в `fact_report.line_code` пишется канонический код из
справочника, а фактический код отчётности — в `fact_report.source_line_code`.
В полных формах наоборот: наименования повторяются («Заёмные средства» — и
1410, и 1510), ключом служит код, и `match_by_name` для них не определён.

`source_line_code` заполняется **всегда**, `NULL` в нём не используется: для
полной отчётности он равен `line_code`, для упрощённой может отличаться.
Правило одно на весь проект, чтобы join и сравнения периодов не требовали
`COALESCE`.

**Строка, не опознанная по наименованию, не теряется.** Она не попадает
в `fact_report`, поэтому загрузчик обязан записать её в `dq_log` с
`check_code = 'line_not_recognized'`, `severity = 'warning'` и исходным
наименованием в `details`. Уровень не блокирующий: отчётность остановит
не сам факт неопознания, а несхождение итога раздела, в который строка
не попала. Коды контролей и уровни — в `quality/codes.py`, свободных строк
в коде быть не должно.

**Приоритет периода.** Один комплект даёт три периода, и один и тот же период
приходит дважды: как отчётный (`current`) в своём комплекте и как
сравнительный (`previous`, `before_previous`) в более поздних. Значения могут
расходиться из-за переклассификации. Поэтому `fact_report.period_role` хранит,
каким периодом значение пришло, а `ON CONFLICT` пропускает запись, если
приоритет входящего хуже: сравнительное значение не затирает отчётное.
Без этого результат зависел бы от порядка загрузки комплектов. Расхождение
пишется в `dq_log` с `check_code = 'period_value_mismatch'` — это
содержательный сигнал о переклассификации, а не техническая деталь.

**В `fact_report` истории версий нет.** Ключ строки — `(inn, report_date,
form_code, line_code)`, номера корректировки в нём нет. Поэтому при загрузке
версии 1 значения версии 0 затираются, а строка `src_file` версии 0 остаётся
без собственных фактов. Это осознанно: одна строка = один код за период.
Следствие: **сравнить «было / стало» можно только по `dq_log`** — там лежат
`previous_value` и `new_value`. В `fact_report` прошлой версии значения
не найти, и запросы вида «показать отчётность до корректировки» к нему
неприменимы.

## Стандарт отчётности

`Standard` — сквозное измерение модели: `rsbu` (отчётность отдельного
юридического лица) и `ifrs` (консолидированная по МСФО). **Ветка МСФО
не реализована**, значение заведено заранее, чтобы при её появлении
не мигрировать данные.

Стандарт входит в ключи уникальности `src_file`, `fact_report` и
`metric_value`, а `period_quality` группируется с его учётом. Причина не
формальная: **ряды по РСБУ и по МСФО несопоставимы**, и без этого измерения
расчёт по одному стандарту молча затирал бы значения другого через
`ON CONFLICT`, а `load_series` возвращал бы ряд, в котором точки разных
стандартов выглядят одинаково. Умолчание везде — `rsbu`.

**Известные точки связывания с РСБУ.** При появлении ветки МСФО править
придётся именно их, искать заново не нужно:

| Место | Что зашито |
|---|---|
| `normalize/lines.py` | код строки `^\d{4}$`, форма `^\d{7}$` |
| `metrics/formula.py` | код строки в формуле `^\d{4}$` (строчные идентификаторы в грамматике свободны) |
| `quality/checks.py` | константы `BALANCE = "0710001"`, `PROFIT = "0710002"` |
| `sources/girbo.py` | `FORM_PERIOD_DEPTH` по кодам форм |

Сейчас они намеренно не тронуты: правка без второй ветки была бы умозрительной.

Получение отчётности по МСФО — отдельная задача после задачи 10. Первым шагом
там ручная загрузка файлов в `data/raw/ifrs/{ИНН}/` и разбор XBRL, где он есть;
PDF — только через выгрузку в таблицу руками. Автоматическое получение
с `e-disclosure.ru` не планируется: источник отвечает HTTP 403 на вежливый
`User-Agent`, обходить защиту мы не будем.

## Доверие к периоду

Блокирующие контроли применяются только к отчётному периоду комплекта, поэтому
период, существующий **только сравнительной колонкой**, ими не проверялся.
Представление `period_quality` и `quality/periods.py` дают явный признак:

- `verified` — период проверен в своём комплекте;
- `comparative_only` — собственного комплекта нет, показатели считаются,
  но с пониженным доверием;
- `quarantined` — собственный комплект в карантине, период в расчёт не идёт.

Признак пишется в `metric_value.confidence`. Текст оговорки отдаёт
`quality.periods.limitations(inn)`, и он **обязан** попасть в раздел
«Ограничения анализа» заключения: иначе динамика за три года выглядит
одинаково достоверной, хотя два периода блокирующими контролями не проверялись.

## Контроли качества

Допуски и уровни — `methodology/thresholds.yaml`, в коде их нет. Прогон —
`quality.runner.run_checks(src_file_id, conn)`, всё одной транзакцией.

**Подстановка нуля живёт в одном месте — `quality/values.py::as_addend`.**
Это единственная функция, имеющая право превратить нераскрытое значение в ноль,
и пользуются ею только контроли сходимости. Модуль `metrics/` её не импортирует,
что проверяется тестом, а не соглашением: при расчёте коэффициентов нераскрытое
значение остаётся `NULL`, показатель получает `not_calculable`.

**Четыре исхода контроля, и их нельзя путать.**

| Исход | Когда | Статус / уровень |
|---|---|---|
| пройден | сошлось в пределах допуска | `pass` |
| провален | не сошлось | `fail`, уровень из методики |
| не выполнялся | итог не раскрыт или не раскрыто ни одно слагаемое | `info` / `info` |
| не проверяемо | слагаемое не загружено, потому что **мы** отказались угадывать | `info` / `warning` |

Последний случай отдельный и важный: у малого предприятия код 1190 подходит
двум укрупнённым строкам, мы его не разносим, и итог раздела I проверить
нечем. Это наш пробел, а не дефект отчётности, поэтому карантина он не вызывает
и в сообщение выносится код-виновник. Иначе каждое малое предприятие уезжало бы
в карантин ни за что.

**Строка 2410 приходит по-разному в двух наборах.** В полной форме — со знаком
(минус при расходе, плюс при налоговом доходе), и в составе 2400 складывается.
В упрощённой — положительной величиной и вычитается. Проверено на данных:
у Газпрома за 2020–2025 годы `2400 = 2300 + 2410 + 2460` сходится во всех
восьми периодах, у Стройсервиса `2400 = 2110 − 2120 − 2330 + 2340 − 2350 − 2410`
сходится копейка в копейку. Это различие форм, а не ошибка.

**Четыре судьбы кода источника, и их нельзя смешивать.**

| Исход | Что значит | Журнал |
|---|---|---|
| `mapped` | код привязан к строке справочника | — |
| `ignored` | методика не использует код осознанно, список в `lines.yaml` | не пишется |
| `not_applicable` | код есть в полном наборе, но не в упрощённом; упрощённая форма приходит в той же схеме, что полная | не пишется |
| `unknown` | кода нет ни в одном наборе — **сигнал проверить справочник** | `unknown_line_code` |

Игнорируемый код — принятое решение, неизвестный — недоработка. Если код
начал появляться в отчётности и не опознаётся, его нужно либо завести
в справочник, либо явно внести в `ignored_codes` с обоснованием.

**Неоднозначность кода и спор кодов — разные вещи, разные контроли.**
`ambiguous_line_code` — код допускают несколько строк (1190 подходит и
«Материальным внеоборотным активам», и «Нематериальным, финансовым и другим»);
разрешается по занятости, то есть исключением претендентов, чей канонический
код уже раскрыт в этой же отчётности, а при неразрешимости строка не грузится.
Причина здесь — неполнота справочника. `multiple_source_codes` — значение одной
укрупнённой строки раскрыто сразу несколькими кодами (1220 и 1230 при том, что
оба это «Финансовые и другие оборотные активы»); причина здесь — аномалия самой
отчётности, и это может быть содержательным сигналом. Различать по `details`
нельзя: коды нужны раздельно в сводке качества, в фильтрах и в заключении.

**Оговорки справочника попадают в заключение.** Если в расчёте участвовала
строка, у которой в `lines.yaml` заполнено поле `note` (например,
«Материальные внеоборотные активы» — ограничение по незавершённым
капитальным вложениям, которые в полной форме могут стоять по строке 1190),
текст `note` обязан попасть в раздел «Ограничения анализа» заключения
(задача 9). Оговорка, оставшаяся только в справочнике, считается потерянной.

**Соглашение о знаке.** Расходные и контр-статьи (себестоимость, проценты
к уплате, собственные акции, платежи по ОДДС) хранятся в `fact_report` как
величина расхода, а вычитание задано оператором в составе итоговой строки:
`2100 = +2110 −2120`, `1300 = +1310 −1320 +1340 +1350 +1360 +1370`. Такие
строки помечены `in_brackets: true`. Поле `sign` говорит о другом — может ли
показатель быть отрицательным (`any`) или нет (`positive`); это вход для
контролей качества, а не для арифметики.

## Источник ГИР БО

Протокол выверен на реальных пробах, они лежат в `data/raw/probe/`. Домен —
`bo.nalog.gov.ru`, старый `bo.nalog.ru` отдаёт 302; базовый URL и контакт для
`User-Agent` берутся из `.env`, в коде их нет.

- Два запроса на организацию: поиск по ИНН и `/nbo/organizations/{id}/bfo/`,
  который отдаёт **все годы и все формы разом**. Ответ — JSON, не XML.
- Формы приходят отдельными блоками (`balance`, `financialResult`,
  `fundsMovement`), значения — в атрибутах `current1600`, `previous1600`,
  `beforePrevious1600`. Наименований строк в ответе нет: для этого источника
  строка опознаётся по коду, `match_by_name` нужен только файловым источникам.
- **Тип отчётности — по `knd`:** `0710099` полная, `0710096` упрощённая.
  Код формы (`okud`) при этом одинаковый, различать по нему нельзя.
- **Глубина истории по формам разная:** третий период (`beforePrevious`) есть
  только в балансе, у ОФР и ОДДС его нет. Метрики задачи 6 обязаны опираться
  на `report_dates` конкретной формы, а не считать глубину одинаковой.
- **Единица измерения в ответе не указана вообще.** Значения приходят
  в тысячах рублей, это принимается как предположение: `unit_code = '384'`,
  `unit_source = 'assumed'`.
- **Числа читаются только через `json_loads_decimal`** (`parse_float=Decimal`).
  Дробные значения в ответе есть, обычный `json.load` нарушит инвариант 5.
- **Отчёт об изменениях капитала (0710004) не разбирается.** В ответе он есть,
  но устроен матрицей (`authorized3100`, `additional3100`, `reserve…`), в
  справочник строк не заложен и в методике не используется. Нераспределённая
  прибыль берётся из баланса — **строка 1370**, искать её в форме 0710004
  не нужно. То же касается отчёта о целевом использовании средств.
- **Корректировки:** `correction_version` входит в ключ уникальности
  `src_file`, актуальность определяется сравнением с `actualCorrectionNumber`.
  При этом **источник отдаёт только актуальную версию** — прежней в ответе
  нет (проверено на ИНН 2522002003: за 2024 год `actualCorrectionNumber = 1`
  и ровно один элемент `typeCorrections` с `correctionVersion = 1`, версии 0
  в ответе нет). Поэтому обе версии оказываются в БД только за счёт наших
  собственных запусков: если версия 0 была загружена раньше, она остаётся
  лежать, а пришедшая версия 1 добавляется отдельной строкой. Загрузчик
  обязан снять признак `is_actual` со всех прежних версий того же года.
- **Кредитные организации вне периметра.** Банки сдают отчётность в Банк
  России по формам 0409, в ГИР БО их нет (ИНН Сбербанка 7707083893 даёт пустой
  результат поиска). Признак `isCb` отбраковывается на входе с записью
  в `dq_log` (`check_code = 'credit_organization'`, уровень `blocking`).

Показатель, для которого нет входных данных, не рассчитывается и помечается
как `not_calculable` с указанием причины. Подстановка приближений запрещена:
например, при отсутствии амортизации показатель «Чистый долг / EBITDA»
не считается, а не заменяется на «Чистый долг / прибыль от продаж».

## Класс финансового состояния

Арифметика зафиксирована в `methodology/scoring.yaml`. Модель класс
не определяет и пересматривать не вправе (инвариант 2).

**Балл показателя** = `0,6 · уровень + 0,4 · динамика`. Уровень отвечает
на вопрос «где показатель находится», динамика — «куда движется». Одной
динамики недостаточно: устойчиво хорошая, но не растущая организация
получала бы средний балл, а слабая, но улучшающаяся — высокий.

**Все шкалы кусочно-линейные.** Ступень давала бы скачок класса при изменении
коэффициента на сотую долю, а объяснить это пользователю нельзя. Между
опорными точками — линейная интерполяция, за крайними точками значение
не меняется. Единственная неустранимая ступень — границы классов, поэтому
рядом с классом всегда приводится балл.

**Опорные точки — не нормативы.** `calibration_points` в `scoring.yaml`
объявлены экспертной калибровкой с полем `origin`; `scale_type: absolute`
меняется на `percentile` одним изменением, когда наберётся база отчётностей.
Формулировки «ниже норматива» и подобные запрещены — правило в
`prompts/rules.md`. В «Ограничениях анализа» обязателен постоянный пункт
из `calibration_points.limitation_note`.

**Сумма весов групп равна 100**, проверяется при загрузке методики и тестом.

**Стоп-факторы, две градации.** Условие — в `metrics.yaml`, последствие —
в `scoring.yaml` с полем `rationale`: отрицательный собственный капитал
и автономия опускают класс до низшего, отрицательный оборотный капитал
и покрытие процентов ниже единицы ограничивают класс средним.

**`in_scoring: false`** — показатель считается и попадает в заключение,
но в балл не идёт. Причина обязательна. Так исключены собственный капитал
(это стоп-фактор, а не измерение) и финансовый рычаг (монотонная функция
автономии, то же самое измерение дважды).

**Класс присваивается не всегда.** Балл считается при любых данных, но класс
требует достаточно широкого основания (`sufficiency` в `scoring.yaml`).
Главный признак — **не число показателей, а доля веса, которую забирает одна
группа**: четыре показателя в четырёх группах информативнее шести в одной.
Класс не присваивается, если одна группа весит больше половины, если групп
меньше двух или показателей меньше четырёх. Причина пишется
в `assessment.no_class_reason`, и ограничение БД не даёт сохранить оценку
без класса и без причины. Узость основания, не блокирующая класс, понижает
уверенность ступенчато.

**Исключение методикой ≠ неполнота отчётности.** Показатель с
`in_scoring: false` выпадает из балла по нашему решению, а не из-за нехватки
данных, и уверенность за это не понижается. В разложении он виден с причиной.

**Разложение обязательно.** Класс без разложения защитить нельзя, поэтому
`assessment` хранится вместе с `assessment_group`, `assessment_metric`
и `assessment_flag`: балл каждой группы, номинальный и фактический вес,
уровень и динамика каждого показателя по отдельности, причина исключения,
сработавший стоп-фактор и класс до его применения.

## Языковая модель

Инструкция — `prompts/conclusion.md`, общие правила — `prompts/rules.md`,
подставляются в шаблон при сборке, а не дублируются в нём.

**Постпроверка сверяет не только числа.** Три независимые проверки, каждая
отклоняет ответ целиком: числа (`llm/verify.py`), формулировки
(`llm/wording.py`) и утверждения о состоянии показателя (`llm/claims.py`).

- **Отсылка к нормативу запрещена словарём.** Методика абсолютных нормативов
  не содержит принципиально, но модель возвращает их текстом: «коэффициент
  текущей ликвидности 0,82, что ниже норматива». Словарь обходится
  перефразировкой — и это не повод его не иметь: обходится он намеренно,
  а нарушения происходят случайно.
- **Порог нельзя ввести и числом.** «Что ниже 1,0» — тот же норматив без
  слова «норматив», а 1 разрешена без привязки как тривиальная. Поэтому 0, 1
  и 100 теряют разрешение, когда стоят объектом сравнения. Исключение —
  **порог стоп-фактора при своём показателе**: «покрытие процентов ниже 1»
  правомерно, «текущая ликвидность ниже 1» нет, хотя число то же.
- **Нельзя называть нерассчитанным показатель, значение которого дано.**
  Сверка идёт с блоком, а не со словами. Ограничения проверки — в `BACKLOG.md`.
- **Класс и балл не пересматриваются** (`llm/verdict.py`). Названный класс
  должен совпадать с присвоенным; когда класс не присвоен, назвать любой —
  выдумать оценку; итоговый балл в текст не выносится, если он не раскрыт
  в блоке ОЦЕНКА. Балл группы под запрет не подпадает — он в блоках есть.

**Числа готовых формулировок цитируются без кода.** В блоках ФЛАГИ и
ОГРАНИЧЕНИЯ величины подставлены в прозу («финансовые вложения составляют
21,2 % активов»), кода при них нет, а привести текст модель обязана дословно.
Такие числа объявлены цитируемыми — то есть проверка для них выключена, и это
записано в `BACKLOG.md` как долг, а не как решение.

**Тексты, которые модель цитирует дословно, обязаны проходить постпроверку.**
Правило распространяется на всё содержимое `methodology/` и `prompts/`,
попадающее в промпт: оговорки (`note`), тексты флагов, формулировки
стоп-факторов, ограничения, примеры в инструкциях. Такой текст модель обязана
привести без сокращений — и если он сам нарушает правила постпроверки, ответ
отклоняется за наше нарушение, а не за её.

Проверено на живом случае: оговорка о долях говорила «сумма приведённых долей
меньше 100 %», постпроверка увидела сравнение с числом без кода показателя
и отклонила верный ответ. Формулировка переписана.

При написании формулировки проверяй по тем же правилам, что и ответ модели:

- число в тексте либо стоит при своём коде, либо его там быть не должно;
- сравнения с числом («меньше 100 %», «ниже 1,0») не писать вовсе —
  формулируй словами: «всей структуры баланса не исчерпывают»;
- слова «норматив», «при норме», «не менее», «должен составлять» запрещены
  и нам, а не только модели;
- глагол при величине изменения должен соответствовать её знаку.

Это же относится к **шаблонам документа** (задача 9): текст, попадающий
в заключение рядом с числами, живёт по тем же правилам.

**Условные формулировки методики в контекст не идут.** Оговорка «в упрощённой
отчётности не рассчитывается» — свойство методики, а не факт об организации;
поданная рядом с посчитанным значением, она читается как утверждение. Модель
написала так про Газпром, который сдаёт полную отчётность, и постпроверка
чисел этого не поймала — чисел в утверждении нет. Поэтому в `metrics.yaml`
два разных поля: `note` — безусловная оговорка о содержании показателя, идёт
в блок ОГРАНИЧЕНИЯ; `methodology_note` — описание методики, **в промпт
не передаётся никогда**, что проверяется тестом.

Та же пара полей в `lines.yaml`: оговорка о содержании строки идёт
в ОГРАНИЧЕНИЯ, сопоставление с другим набором отчётности («Со строкой 1240
полного набора не сопоставима») — нет. И в `scoring.yaml` у стоп-фактора:
`statement` — что он означает для этой организации, идёт в блок ОЦЕНКА;
`rationale` — почему методика устроена так («отрицательный оборотный капитал
бывает штатным режимом при быстром обороте»), в промпт не идёт, иначе рядом
с оценкой читается как оправдание положения именно этой организации.

**Блок ПОКАЗАТЕЛИ содержит только фактическое состояние** показателя у этой
организации: значение либо `not_calculable` с конкретной причиной. Оговорок
в нём нет вовсе — рядом со значением модель читает любую из них как
утверждение об организации.

**Модель получает только посчитанное.** `llm/context.py` собирает шесть блоков
из `fact_report`, `metric_value` и `assessment`; исходный файл отчётности
ей не передаётся, и каждое число идёт с кодом строки или кодом показателя.
Числа подаются уже округлёнными — у модели не должно быть повода считать самой.

**Постпроверка сверяет пару «число — код», а не число само по себе.**
Проверки одного числа недостаточно: модель может назвать верную величину
при чужом коде — подставить значение текущей ликвидности к коэффициенту
автономии. Число совпадёт со входным, а утверждение будет ложным.
Поэтому `llm/verify.py` для каждого числа ищет ближайший код или наименование
показателя (`llm/pairs.py`, окно 160 символов) и сверяет число со значениями
именно этого показателя. Три вида нарушения: `not_in_blocks` — числа нет
во входных данных, `no_anchor` — число приведено без кода, `wrong_anchor` —
число принадлежит другому показателю.

Порядок выбора якоря такой. Первым берётся код, **приписанный к самому числу
справа** в скобках и один — «снизилась на 1,6 % (1600_chg_pct)». Иначе
ближайший код **слева**: по формату `prompts/rules.md` код ставится перед
значениями, и без этого правила второе число перечисления привязалось бы
к следующему показателю. Код справа, отделённый словами, берётся последним.

Две тонкости, обе найдены на живых ответах. Тег, приписанный к числу, этому
числу и принадлежит: во фразе «на 1,6 % (1600_chg_pct) до 25 736 328 136» сумма
привязывается к 1600, а не к коду процентного изменения. И код, за которым
внутри тех же скобок стоит своё число — «(nwc_chg_abs -1 248 224 574)», —
тегом не является: он относится к числу внутри скобок.

**Изменение сверяется по модулю, но направление проверяется отдельно.**
У изменения направление задаёт глагол, а не знак: «сократилась на 59,6 %» —
правильный русский, «сократилась на −59,6 %» — нет. Поэтому якоря `_chg_abs`
и `_chg_pct` принимают величину с любым знаком, а `llm/direction.py` сверяет
глагол при числе со знаком входного значения: `wrong_direction`. Так ловится
«коэффициент вырос с 1,23 до 0,82», где оба числа верны, а утверждение ложно.

Проверка направления намеренно осторожна и при сомнении молчит: отклонённый
ответ пользователю не показывается вовсе, поэтому ложное отклонение дороже
пропуска. Она не применяется, **если сама величина отрицательна**: у убытка
«рост убытка» означает падение показателя, и судить по глаголу нельзя. Слово
берётся только из того же предложения и только ближайшее к числу.

Разрешены без привязки только 0, 1, 100, номера годов, даты, коды форм
по ОКУД, номера нормативных документов после «№» и номера пунктов списка
(включая заголовки Markdown вида `### 4.`). Цитирование с меньшей точностью
допускается — это не вычисление; перевод единиц не проходит. Рассуждение
модели (`<think>`) вырезается до проверки и в заключение не попадает.

**Тире перед числом минусом не считается.** В русском тексте тире стоит
и при положительных величинах, отличить его от знака по написанию нельзя.
Отрицательная величина обязана приводиться со знаком: величина по модулю
с вынесенным в слова знаком («перешёл в отрицательную зону — 521 415 920»)
проверку не проходит и не должна.

**Отклонённый ответ наверх не возвращается.** Делается одна повторная попытка,
затем `ConclusionRejectedError`. **Журнал `llm_log` пишется на собственном
соединении**, а не в транзакции вызывающего: иначе запись об отклонении
откатилась бы вместе с исключением, а нужна она именно тогда, когда что-то
пошло не так.

## Командная строка и цикл обработки

`finlib/pipeline.py` — полный цикл одной организации: получение, загрузка,
контроли, расчёт, оценка, текстовая часть, документ. Этапы вынесены из CLI
в именованный `Stage`: цикл нужен и вне терминала (регрессионный прогон
задачи 17), а CLI обязан называть этап, на котором остановился.

**Молчаливого продолжения после неудачи нет.** Каждый этап либо проходит,
либо поднимает `PipelineError` с этапом и причиной: заключение по неполным
данным хуже отсутствия заключения. Все комплекты в карантине — остановка
на контролях, ни одного рассчитанного показателя — остановка на расчёте.

`finlib/cli.py` на typer, точка входа `fin-analysis`: `analyze`, `show`,
`quality`, `reprocess`. `--no-llm` собирает документ без разделов модели;
такой документ **прямо оговаривает**, что заключением не является и служит
расчётной справкой, а в приложении стоит «модель не привлекалась».
`reprocess` не обращается к источнику вовсе.

## Единая точка округления

Разрядность отображения задана в `metrics.yaml`, блок `display`, по единицам
измерения, с полем `origin`; показатель вправе объявить свою через
`display_scale`. Округляет одна функция — `metrics/display.py::round_to`,
и **дельты с темпами считаются от округлённых величин**, а не от полных.

Прежде дельты считались по полной точности, а уровни отображались
округлёнными, и документ становился арифметически несогласованным:
«рентабельность активов снизилась с 0,41 до 0,31 (изменение 0,11)» —
разность отображаемых уровней 0,10, а темп −25,6 % из 0,41 и 0,31
не выводится, получается −24,4 %. Формально ошибки нет, но читатель видит
противоречие и правильно ему не доверяет.

Отсюда следствия: в `metric_value` значения хранятся **полными** — округление
относится к представлению, а не к точности расчёта; в контекст модели, в текст
документа, в приложение и в вывод CLI идут **одни и те же** округлённые
величины; контроль `delta_does_not_match_levels` в `report/consistency.py`
сторожит равенство и блокирует документ при расхождении.

Это отменяет прежнее решение подавать модели точные значения: оно принималось
ради того же — чтобы текст и приложение не расходились, — и единая точка
округления решает задачу надёжнее.

## Заключение в Word

Сборка — `report/`, выход `data/output/{ИНН}_{дата}.docx`. Раздел 1 и приложение
собираются детерминированно из базы (`report/summary.py`, `report/appendix.py`),
разделы 2–6 пишет модель. Ответ модели разбирается по заголовкам
(`report/sections.py`), и **отсутствие обязательного раздела — ошибка**,
а не повод отдать неполный документ. Порядок разделов задаём мы, а не модель.

**Документ не появится, пока ответ не прошёл постпроверку.** Незаверенный текст
не показывается пользователю (инвариант 8), а файл на диске — тем более.

**Единица измерения определяется формой, а не ответом источника.** ГИР БО её
не сообщает вовсе, и прежде она принималась как предположение. Это дефект
данных, а не представления: ошибка в тысячу раз не ловится ни одним контролем —
баланс сойдётся, сходимость разделов сойдётся, коэффициенты будут верны,
а все абсолютные величины окажутся неверны. Правило «форма → код ОКЕИ» лежит
в `lines.yaml`, блок `units`, с полем `origin`; комплект из форм вне перечня
уходит в карантин блокирующим контролем `unit_not_determined`. Значения
`assumed` нет ни в базе, ни в документе.

**Определение единицы по форме — правило, а не факт из данных**, и оно
сломается на источнике, отдающем рубли. Поэтому рядом стоят два контроля
правдоподобия (`methodology/thresholds.yaml`, блок `magnitude`, оба с `origin`):
`balance_magnitude` — грубые границы валюты баланса, предупреждение
с требованием ручного подтверждения; `period_magnitude_shift` — отношение
величин смежных периодов, близкое к тысяче, блокирующий. Проверяется именно
кратность тысяче, а не всякий большой скачок: рост в триста раз бывает
хозяйственным событием и ловится `jump_detection`. Ноль из проверки границ
исключён: умножение на тысячу его не меняет, подменой единицы он быть не может.

**Стоп-фактор старше правила достаточности.** Отрицательный собственный
капитал — состояние, установленное одним показателем, и узость основания его
не отменяет. При сработавшем стоп-факторе класс присваивается, а недостаток
групп отражается отдельным полем `assessment.breadth_reason` и отдельной
фразой «балльная оценка не формируется». Прежде в разделе соседствовали два
взаимоисключающих утверждения: класс не присвоен и класс присвоен низший.

Из этого следует третье правило раскрытия балла: **при заполненном
`breadth_reason` балла нет нигде**, хотя класс присвоен, — балльной оценки
просто не существует, и число рядом с классом читалось бы как её итог.

**Веса групп хранятся долями, оба поля.** `nominal_weight` и
`effective_weight` — величины одного рода, и раньше первое хранилось
процентом, а второе долей. Приложение печатало 3000,0 % вместо 30,0 %.

**Причина исключения из балла имеет машинный вид и фиксированную иерархию**
(`ExclusionKind`): стоп-фактор → нет шкалы уровня → дублирует другой
показатель → нет данных. Текст причины обязан быть безусловным: он печатается
у любой организации, и разъяснение про отрицательный капитал у организации
с положительным — ложное утверждение.

**Класс присваивается не всегда, и это штатный исход.** У двух проб из трёх
класса нет. Тогда вместо класса печатается причина отказа и перечень
показателей, которых не хватило. Нехватка данных и исключение решением
методики разведены: первое — пробел в отчётности, второе — наше решение.

**Балл раскрывается по двум разным правилам, и их нельзя путать:**

| Где | Условие |
|---|---|
| раздел 1 «Ключевой вывод» | класс присвоен **и** стоп-фактор не сработал |
| приложение | класс присвоен; при стоп-факторе — с пометкой «до применения стоп-фактора» |

**Без класса балла нет нигде** — ни в разделе 1, ни в приложении, ни в промпте
модели, ни баллов групп. Причина: балл 67 при отрицательном собственном
капитале арифметически верен, но рядом с отказом присвоить класс читается как
противоречие. Балл единственной уцелевшей группы («Рентабельность» — 94 из 100)
опаснее вдвойне: класс не присвоен именно потому, что основание узкое.

**Документ проверяется на согласованность с собой** (`report/consistency.py`).
Каждый кусок по отдельности верен, а вместе они противоречили: «Ограничения»
сообщали, что отчётность за 2025 год в расчёт не включена, а «Происхождение
документа» перечисляло её среди принятых — выборка комплектов не отсекала
карантин. Противоречие в документе хуже отсутствия сведений, поэтому контроль
блокирующий: документ не формируется.

**Номер таблицы приложения ставит сборщик**, а не заголовок таблицы: таблица
может не строиться, и зашитые номера оставляли дыру — таблицы 3 не было,
а таблица 4 номер сохраняла.

**Графа считает то, как называется.** «Показателей в балле» — именно в балле;
ноль в ней не означает, что показатели группы не рассчитаны. Смешение
«рассчитано» и «участвует в балле» — повторяющийся источник ошибок.

**`make probes` пересчитывает и оценку.** Без этого набор данных расходился
сам с собой: показатели свежие, класс и разложение — от прежней версии
методики.

**Повторная попытка несёт перечень замечаний.** Температура нулевая, и повтор
с тем же промптом давал тот же ответ — вторая попытка была бессмысленна.
`service.with_corrections` дописывает к инструкции, что именно нашла проверка.
Замечания формулируются как факты о прошлом ответе, а не как подсказка, что
написать: содержание — работа расчёта, не модели.

## Расчёт показателей

Определения — `methodology/metrics.yaml`, интерпретатор — `metrics/formula.py`,
без `eval`. Язык формул беден намеренно: четырёхзначное число — код строки,
`avg(код)` — полусумма на начало и конец периода, прописное имя — константа
из `thresholds.yaml`. **Числовых литералов в формулах нет**: любое число было бы
магическим, и разбор такую формулу отвергает. Число дней в периоде — константа
`DAYS`, потому что для отчётности за неполный год оно другое.

**Нормативов в методике нет.** Ни отраслевых, ни единых абсолютных: основа
интерпретации — динамика во времени, а не сравнение с числом неизвестного
происхождения. Исключение — четыре стоп-фактора, у которых порог содержателен
вне отрасли: отрицательный собственный капитал, отрицательный коэффициент
автономии, отрицательный чистый оборотный капитал, покрытие процентов меньше
единицы. Они помечены в `metrics.yaml` полем `stop_factor`.

**Один недостающий компонент отменяет показатель целиком.** Частичных
вычислений нет. В `reason` перечисляются все отсутствующие коды, в `reason_code`
— машинная причина: `missing_lines`, `no_previous_period`, `zero_denominator`.
Раскрытый ноль и нераскрытая строка ведут себя по-разному: при нулевых запасах
оборачиваемость не определена, но данные полны, и текст причины другой.

**Средние величины без предыдущего периода не считаются.** Полусумма требует
двух точек; подставлять значение на конец периода вместо средней запрещено —
это тихо исказило бы оборачиваемость и рентабельность. Следствие: за самый
ранний период в базе показатели по средним величинам не рассчитываются никогда.

**Производные величины считаются в Python и подаются модели готовыми.**
Темпы изменения нужны в заключении постоянно, но во входных блоках их не было,
и модель делила числа сама — прямое нарушение инварианта 1. Поэтому
`metrics/derived.py` считает изменение за период (`1230_chg_abs`),
то же изменение в процентах (`1230_chg_pct`) и долю строки в валюте баланса
(`1230_share`); те же окончания у показателей (`cur_liq_chg_pct`). Состав —
в `metrics.yaml`, блок `derived`: перечни строк там, а не в коде.

Производные хранятся в `metric_value` рядом с показателями и **в балльную
оценку не входят**: скоринг перебирает показатели справочника, а динамика уже
учтена в балле показателя отдельным слагаемым. Справочник не примет показатель,
чей код оканчивается как производная, — иначе они делили бы один код.

**Процент не считается от неположительной базы и при смене знака.** «Рост
на 55 %» при движении капитала с −442 до −200 и «снижение на 150 %» при
переходе прибыли в убыток арифметически верны, но читаются как ложь. Причины —
`zero_denominator`, `negative_denominator`, `sign_change`; величины и
абсолютное изменение при этом остаются, и динамика описывается словами.

**Нет данных — производной нет вовсе**, а не `not_calculable`: иначе за самый
ранний период в контекст ушли бы десятки строк «нет предыдущего периода»
и содержательный отказ утонул бы среди них.

**Динамика требует минимум двух рассчитанных точек**, и её достоверность
ограничена доверием к периодам. `metrics.store.MetricSeries` отдаёт ряд вместе
с `confidence` каждой точки и готовым текстом оговорки: ряд, опирающийся на
`comparative_only` периоды, обязан сопровождаться этой оговоркой в заключении.
