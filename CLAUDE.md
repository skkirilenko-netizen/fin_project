# Проект: анализ финансового состояния российского юрлица по РСБУ

Локальный контур. Данные не покидают машину. Внешние LLM-API запрещены.

## Что строим

Пользователь вводит ИНН → система забирает годовую бухгалтерскую отчётность,
нормализует её по кодам строк, считает коэффициенты, присваивает класс
финансового состояния и формирует аналитическое заключение в Word.

## Инварианты — нарушать нельзя ни при каких обстоятельствах

1. **Языковая модель не вычисляет.** Все числа считает Python/SQL. Модель
   получает готовые значения и пишет только текст. Любой код, где модель
   просят «посчитать», «оценить долю», «определить класс» — ошибка архитектуры.
2. **Класс финансового состояния определяется детерминированно.** Скоринг —
   арифметика по фиксированным весам, зафиксированным в `methodology/`.
   Модель не имеет права его пересматривать.
3. **Каждое число в заключении привязано к коду строки или коду показателя.**
   Число без источника в выходной документ не попадает.
4. **«Не раскрыто» ≠ 0, но у этого две трактовки по контексту.** В отчётности
   прочерк, «X» и пустая ячейка означают отсутствие раскрытия. В БД это `NULL`.
   Для **расчёта коэффициентов** отсутствие остаётся `NULL`, показатель
   получает `not_calculable`, подстановка нуля запрещена. Для **проверки
   арифметики итога** нераскрытая строка считается нулём — иначе контроль
   сходимости разваливается на любой упрощённой форме, где организация
   раскрывает три строки из семи (проверено: у ПК «Стройсервис» итог 2400
   сходится при отсутствующей строке 2330). Одно значение, две трактовки;
   смешивать их нельзя. Причина нераскрытия хранится в `fact_report.value_status`:
   `ok` — значение раскрыто, `not_disclosed` — прочерк, «X» или пустая ячейка,
   `not_applicable` — строка неприменима к форме отчётности организации.
   Значение и статус связаны ограничением БД: `value IS NOT NULL` тогда и
   только тогда, когда статус `ok`. Разбор ячейки делает
   `utils.parse_value`, который различает пустую ячейку (`missing`), явный
   прочерк (`not_disclosed`) и нечисловое содержимое (`invalid`);
   `to_decimal` остаётся коротким вариантом, когда причина не важна.
5. **Денежные величины — только `Decimal`.** `float` для сумм и коэффициентов
   не используется нигде, кроме визуализации. Округление — явное, через
   `quantize`.
6. **Данные, не прошедшие контроли качества, в расчёт не идут.** Отчётность
   уходит в карантин, причина пишется в `dq_log`. Карантин ставится
   на **комплект** (`src_file.status`), а блокирующие контроли применяются
   только к **отчётному периоду** комплекта: за сравнительные колонки отвечают
   те комплекты, для которых эти периоды отчётные. Расчёт обязан отбрасывать
   факты из комплектов в карантине — `quality.runner.quarantined_src_files`.
7. **Секреты только в `.env`**, который в `.gitignore`. Реальные данные
   отчётности в репозиторий не коммитятся. Единственное исключение —
   `data/raw/probe/`: несколько публичных ответов ГИР БО, сохранённых как
   фикстуры, чтобы тесты не обращались к ФНС на каждом прогоне. Отчётность
   организаций, которые анализируются по запросу, не коммитится никогда.
8. **Ответ модели проходит постпроверку на посторонние числа.** Не прошёл —
   не показывается пользователю, пишется в `llm_log` с пометкой.

## Стек

- Python 3.12, менеджер окружения `uv` (запуск: `uv run ...`, не `pip`)
- **PostgreSQL 17 через Homebrew**, база `findb`, локальное подключение от
  пользователя системы без пароля. **Docker в проекте не используется,
  команды `docker exec` не применять.** SQL выполняется через
  `psql findb -f файл.sql`
- Ollama локально, `http://localhost:11434/v1`
- `psycopg2-binary` + сырой SQL. ORM не используем
- `httpx` для HTTP. LangChain, LlamaIndex и подобные надстройки — не ставить
- `pytest` для тестов, `ruff` для линтинга
- `python-docx` для выгрузки заключения

## Правила кода

- Типизация обязательна, возвращаемые типы указываем всегда.
- Docstring на русском, одной строкой, по существу.
- Никаких «магических чисел»: нормативы, веса, пороги — только из
  `methodology/*.yaml`, не в коде.
- Деление: всегда явная обработка нуля и `None`. Функция-хелпер
  `safe_div(a, b) -> Decimal | None`, которая возвращает `None`, а не ноль
  и не бесконечность.
- Все обращения к внешним источникам кэшируются на диск в `data/raw/`
  в исходном виде. Повторный запуск не должен дёргать сеть.
- Идемпотентность загрузки: повторная обработка той же отчётности не создаёт
  дублей (`ON CONFLICT ... DO UPDATE`). Если при этом значение строки
  изменилось, факт перезаписи пишется в `dq_log` с `check_code =
  'fact_overwrite'`, статусом `info` и прежним значением в `previous_value` —
  молча затирать ранее загруженное число нельзя. Совпавшее значение не
  переписывается вовсе: `updated_at` не трогается, журнал не засоряется.
- Загрузка комплекта — **одна транзакция**: снятие `is_actual` с прежних
  версий, запись `src_file` и запись фактов происходят вместе. Иначе при сбое
  посередине в базе остаётся либо ноль актуальных версий, либо две.
- Логирование через `logging`, не `print`, кроме CLI-вывода.

## Правила работы для Claude Code

- Перед изменениями больше чем в одном файле — сначала план, потом код.
- **Правки файлов вносятся только инструментом редактирования.** Генерация
  python/bash-скриптов для изменения файлов проекта запрещена, включая
  однострочные правки и конфиги в `methodology/` и `prompts/`. Скрипт прячет
  дифф и подменяет саму правку обёрткой вокруг неё, а на конфигурационные
  файлы тестов нет — дифф там единственный контроль.
- Одна задача = один коммит с осмысленным сообщением на русском.
- После каждой задачи: `uv run pytest` и `uv run ruff check .` должны быть
  зелёными. Не зелёные — задача не выполнена.
- **Не выдумывать формат внешних источников.** Если структура ответа ГИР БО
  неизвестна — сначала сделать пробный запрос, сохранить сырой ответ,
  показать его мне, и только потом писать парсер.
- **Не подставлять моки вместо реальных данных молча.** Если что-то не
  работает, сказать об этом, а не сгенерировать правдоподобную заглушку.
- Не добавлять зависимости без явного согласования.
- Не трогать `.env` и содержимое `data/`.
- Если моя формулировка задачи противоречит инвариантам выше — остановиться
  и сказать об этом, а не выполнять.

**Методическое решение и технический параметр разбора — разные вещи, и правила
у них разные.** Всё, что лежит в `methodology/`, правится диффом, но согласия
требует не всё: согласия требует то, что участвует в суждении об эмитенте.

| Род | Что это | Кто правит |
|---|---|---|
| методическое решение | пороги оценки, веса групп, шкалы и опорные точки, формулировки документа и сигналов, состав ядра справочника, отсечки существенности и свежести | только с моим согласием, диффом |
| технический параметр разбора | окна просмотра, признаки структуры документа, допуски распознавания, длины заголовков, число строк до таблицы | правится наравне с кодом |

Различение не в файле, а в предмете: `contents_list_window: 6` лежит
в `methodology/ifrs_parsing.yaml` и означает «сколько строк смотреть под
заголовком» — к оценке эмитента это отношения не имеет, и ошибка здесь
видна на первом же документе. `share_of_total_assets: 0.05` лежит рядом
и означает, какую статью считать существенной, — это суждение.

Отсюда правило ночной работы: технические параметры разбора править можно,
методические решения — нет, и встреченная развилка идёт в `NIGHT_QUESTIONS.md`
с числами и вариантами, а не решается самостоятельно.

## Формулы

Полный расчётный аппарат — в `methodology/metrics.yaml`. Формулы заданы
в кодах строк РСБУ (баланс 1100–1700, ОФР 2100–2400, ОДДС 4100–4500).
Средние балансовые величины — полусумма на начало и конец периода.

Справочник строк — `methodology/lines.yaml`, загрузчик `normalize/lines.py`.

**Два набора строк.** `reporting_type: full | simplified` — полные формы и
упрощённые (приложение 5 к приказу 66н). Ключ справочника — пара
`(reporting_type, code)`: один код может существовать в обоих наборах и
означать разное. Пример: 2120 в полном наборе — «Себестоимость продаж»,
в упрощённом — «Расходы по обычной деятельности» вместе с коммерческими и
управленческими. Совпадение или различие смысла объявляется полем
`same_meaning_as_full`, иначе справочник не загрузится.

Тип отчётности хранится в `src_file.reporting_type` — это свойство сданного
комплекта, а не организации: право на упрощённую отчётность утрачивается при
росте выручки или обязательном аудите. Контроли качества выбирают набор
проверок по нему.

**Код упрощённой строки — подсказка, а не ключ.** В упрощённых формах код
укрупнённой строки указывается по показателю с наибольшим удельным весом и
между периодами меняется. Поэтому строка опознаётся по наименованию
(`match_by_name`), в `fact_report.line_code` пишется канонический код из
справочника, а фактический код отчётности — в `fact_report.source_line_code`.
В полных формах наоборот: наименования повторяются («Заёмные средства» — и
1410, и 1510), ключом служит код, и `match_by_name` для них не определён.

`source_line_code` заполняется **всегда**, `NULL` в нём не используется: для
полной отчётности он равен `line_code`, для упрощённой может отличаться.
Правило одно на весь проект, чтобы join и сравнения периодов не требовали
`COALESCE`.

**Строка, не опознанная по наименованию, не теряется.** Она не попадает
в `fact_report`, поэтому загрузчик обязан записать её в `dq_log` с
`check_code = 'line_not_recognized'` и исходным наименованием в `details`.

**Уровень записи зависит от того, что строка несла, и путать эти два случая
нельзя.** Строка без раскрытого значения — пробел справочника: её стоит
завести, но отчётность из-за неё не останавливается, уровень `warning`.
Строка с раскрытым ненулевым значением — тихая потеря данных: величина
в отчётности есть, в расчёт она не попадёт, и если строка не входит ни в один
проверяемый итог, пропажу не заметит ни один контроль сходимости. Уровень
`blocking`, статус `fail`, комплект уходит в карантин. Раскрытый ноль потерей
не считается. Поэтому **карантин ставится по блокирующим записям журнала,
откуда бы они ни пришли** — и от прогона контролей, и от загрузчика.

Записи загрузчика о сопоставлении строк (`MAPPING_CODES` в `quality/codes.py`)
при повторной загрузке комплекта переписываются, а не накапливаются: они
описывают состояние комплекта, а не событие. Иначе исправленный справочник
не снимал бы карантин — тот стоял бы по записи, оставшейся от прежнего прогона.
Перезапись значения и расхождение периодов в это семейство не входят: они
события, и они история.

**Строка без кода — не то же самое, что строка, не опознанная по наименованию.**
В выгрузке их два рода, и разметка их не различает: расшифровка «в том числе»
внутри строки с кодом и дополнительная строка, которую организация ввела сама
(в выгрузках встречаются обе, причём у одних организаций расшифровка сдвинута
правее наименования, у других стоит в той же колонке). Расшифровка уже входит
в свою строку с кодом, и загрузить её значило бы посчитать величину дважды;
дополнительная строка входит в итог раздела, и её отсутствие итог разваливает.
Различает их только арифметика итога, поэтому такие строки не грузятся,
их перечень пишется в `src_file.meta.uncoded_rows`, а ловит пропажу
блокирующий `section_sum`. Проверено: у ПАО «ЭсЭфАй» расхождения итогов
разделов I и II равны копейка в копейку двум строкам без кода —
«Дебиторская задолженность» и «Средства в банках».

Коды контролей и уровни — в `quality/codes.py`, свободных строк в коде
быть не должно.

**Приоритет периода.** Один комплект даёт три периода, и один и тот же период
приходит дважды: как отчётный (`current`) в своём комплекте и как
сравнительный (`previous`, `before_previous`) в более поздних. Значения могут
расходиться из-за переклассификации. Поэтому `fact_report.period_role` хранит,
каким периодом значение пришло, а `ON CONFLICT` пропускает запись, если
приоритет входящего хуже: сравнительное значение не затирает отчётное.
Без этого результат зависел бы от порядка загрузки комплектов. Расхождение
пишется в `dq_log` с `check_code = 'period_value_mismatch'` — это
содержательный сигнал о переклассификации, а не техническая деталь.

**Пересмотр эмитентом и расхождение соглашения о знаке — разные вещи,
и код у них разный.** Пересмотр меняет величину; расхождение, в котором
величина совпадает до копейки, а знак обратный, — это способ печати расходной
статьи, и приписывать его эмитенту нельзя. Проверено на данных: у ПАО «Газпром»
строка 2411 за 2023 год приходит и как 14 235 635, и как −14 235 635 — одна
и та же организация печатает налог на прибыль в одном году в скобках,
в другом без них; в упрощённой форме та же строка положительна по устройству
набора. Признак один на оба стандарта и определён в одном месте
(`quality/values.py::sign_only_difference`), код записи —
`sign_convention_mismatch`. В `period_value_mismatch` таким записям не место:
по нему считается интенсивность пересмотра, и сигнал мерил бы нас, а не
эмитента. Из 13 знаковых расхождений набора РСБУ все 13 — эта строка.

**В `fact_report` истории версий нет.** Ключ строки — `(inn, report_date,
form_code, line_code)`, номера корректировки в нём нет. Поэтому при загрузке
версии 1 значения версии 0 затираются, а строка `src_file` версии 0 остаётся
без собственных фактов. Это осознанно: одна строка = один код за период.
Следствие: **сравнить «было / стало» можно только по `dq_log`** — там лежат
`previous_value` и `new_value`. В `fact_report` прошлой версии значения
не найти, и запросы вида «показать отчётность до корректировки» к нему
неприменимы.

## Стандарт отчётности

`Standard` — сквозное измерение модели: `rsbu` (отчётность отдельного
юридического лица) и `ifrs` (консолидированная по МСФО). **Ветка МСФО
в работе** (задачи 20–30, `TASKS-3.md`); задача 20 готовит к ней модель
данных и самой отчётности по МСФО ещё не касается.

**Измерение называется `standard`, а не `source`.** `src_file.source` занят
и означает другое — способ получения комплекта (`gir_bo` или `file`). Одна
и та же отчётность приходит обоими способами, оставаясь отчётностью одного
стандарта, и смешивать эти два понятия в одном имени нельзя.

Стандарт входит в ключи уникальности `src_file`, `fact_report`,
`metric_value` и `assessment`, а `period_quality` группируется с его учётом.
Причина не формальная: **ряды по РСБУ и по МСФО несопоставимы**, и без этого
измерения расчёт по одному стандарту молча затирал бы значения другого через
`ON CONFLICT`, а `load_series` возвращал бы ряд, в котором точки разных
стандартов выглядят одинаково. Умолчание везде — `rsbu`.

**В разложении оценки стандарт не дублируется.** `assessment_metric`,
`assessment_group`, `assessment_flag` и `assessment_signal` получают его
от `assessment` внешним ключом, и ключ уникальности родителя его уже
содержит. Второе поле той же величины умеет разойтись с первым — это уже
случалось с весами групп, хранившимися в разных единицах.

**Запрет смешения стандартов действует везде, а не только в показателях.**
Правило было написано для расчёта и туда же дотянулось; сигналы, контроли
и выборки журнала остались без него, и `revision_intensity` брал числитель
по организации целиком, а знаменатель по стандарту оценки — у Сегежи
9 пересмотров по МСФО ложились на 5 комплектов РСБУ. Это класс, а не случай:
**всякая выборка по ИНН обязана называть стандарт**, потому что ряды
по РСБУ и по МСФО несопоставимы, а запись о комплекте другого стандарта
неотличима на вид от своей. Проверено по всем запросам: то же было
в отборе карантинных комплектов (`quality/runner.py`) и в выборке
расхождений для документа (`quality/context.py`); во флагах и в скоринге
нет — они получают готовые величины, а не ходят в базу. Перечень контролей
в терминале стандарт теперь печатает: скрыть его значило бы выдать
смешанный перечень за ряд одного стандарта.

**Показатель не считается из величин двух стандартов.** Чистый долг группы
к выручке управляющей компании — не долговая нагрузка, а артефакт, и число
при этом получается настоящее на вид. Стандарт каждой величины хранится
рядом с ней (`PeriodValues.standards`), контроль живёт в `compute_metric`,
исход — `not_calculable` с `reason_code = 'mixed_standards'`. Параметр
`standards` у `compute_metric` обязателен намеренно: контроль, который можно
молча не передать, неотличим от невыполненного. Число проверенных
показателей идёт в журнал рядом с числом отвергнутых.

**Правила обращения со стандартом — `methodology/standards.yaml`.** Там
порядок предпочтения для базы оценки (у группы с консолидированной
отчётностью база — МСФО, у организации без неё — РСБУ), оговорки для
документа и текст причины при смешении. Там же заготовка сигнала
о расхождении показателя между стандартами: объявлена неактивной, причина
названа — порога нет, потому что организаций с показателями обоих стандартов
в базе пока ноль. Объявить сигнал действующим, не дав порога, справочник
не позволит.

**Известные точки связывания с РСБУ.** При появлении ветки МСФО править
придётся именно их, искать заново не нужно:

| Место | Что зашито |
|---|---|
| `normalize/lines.py` | код строки `^\d{4}$`, форма `^\d{7}$` |
| `metrics/formula.py` | ~~код строки в формуле `^\d{4}$`~~ — **грамматика приняла код позиции МСФО** `ifrs.<имя>` (задача 29); голое строчное имя по-прежнему константа методики |
| `quality/checks.py` | константы `BALANCE = "0710001"`, `PROFIT = "0710002"` |
| `sources/girbo.py` | `FORM_PERIOD_DEPTH` по кодам форм |
| `sources/model.py` | `KND_TO_REPORTING_TYPE` по кодам налогового документа |
| `sources/inbox.py` | код строки `^\d{4}$`, подписи шапки форм РСБУ |
| `methodology/report.yaml` | ~~вступление «Фактической базы» обещает коды строк~~ — **разведено по стандарту (задача 20)** |

Остальные намеренно не тронуты: правка без второй ветки была бы
умозрительной. Седьмая точка правки потребовала: вступление раздела
обещало читателю коды строк, а кодов, утверждённых нормативным актом,
консолидированная отчётность не содержит — статьи опознаются позициями
унифицированной модели. Формулировка обязана быть объявлена для каждого
стандарта, иначе справочник не загрузится.

## Справочник статей МСФО

`methodology/ifrs_lines.yaml`, загрузчик `normalize/ifrs_lines.py` —
**параллельный справочник, а не продолжение справочника РСБУ**. Причины
в природе данных: кодов строк, утверждённых нормативным актом, в МСФО нет,
и позиция опознаётся наименованием через синонимы, тогда как в РСБУ первичен
код, а наименования повторяются («Заёмные средства» — и 1410, и 1510). Состав
статей меняется от эмитента к эмитенту, тогда как справочник РСБУ фиксирован
формой. Общий каталог заставил бы натягивать один механизм на другой.

**Код позиции — `ifrs.<имя>`, префикс обязателен.** Четырёхзначное число
в грамматике формул уже означает код строки РСБУ, голое строчное имя —
константу методики из `thresholds.yaml`. Код с точкой не может быть ни тем,
ни другим и в `fact_report.line_code` с первого взгляда отличим от кода РСБУ.
Разделы отчётности (`ifrs.statement_of_financial_position` и прочие) кодов
ОКУД не имеют по той же причине и названы так же.

**Синоним объявляет, у какого эмитента встречен** (`seen_at`). Через полгода
при решении, поднимать ли позицию в ядро, нужно видеть, откуда взялось
написание. Одно наименование не может принадлежать двум позициям **одного
раздела** — иначе статья ляжет в ту, что встретилась раньше, то есть
произвольно; проверяется при загрузке, а не при разборе файла эмитента.

**Между разделами повтор правомерен, и различает их раздел.** «Кредиты
и займы» стоят в балансе дважды — в долгосрочных обязательствах
и в краткосрочных; в РСБУ их различает код строки (1410 и 1510), в МСФО
кода нет. Прежде справочник повтора не допускал, обе строки опознавались
одной позицией, и **краткосрочный долг затирал долгосрочный**: у ЛСР
в расчёт шло 35 876 вместо 328 256, и то же у Норникеля и Сегежи. Ошибка
самая дорогая из найденных — все показатели долговой нагрузки считались
по величине, заниженной в разы, при сходящемся балансе.

Двойников не один: тем же образом повторяются «Обязательства по аренде»
(ФосАгро, Норникель, Сегежа), «Оценочные обязательства» и «Резервы»
(Норникель, ЛСР), «Кредиты и облигации» (ФосАгро). Там затирания
не было — обе строки не опознавались вовсе, и величины терялись тихо.

Раздел строки определяется по ближайшему итогу **ниже** неё, тем же
правилом, по которому строится иерархия итогов. Раздел и опровергает
опознание: статья оборотных активов, стоящая в разделе внеоборотных,
не опознаётся вовсе — у ЛСР «Торговая и прочая дебиторская задолженность»
давала 1 410 вместо 215 664.

**Распределение позиции — тождество, а не второй способ её набрать.**
Прибыль за период набирается из прибыли до налогообложения и налога,
а делится между акционерами материнской компании и неконтролирующими долями
(МСФО (IAS) 1.81B). Это два разных утверждения об одной величине, и оба
обязаны сойтись, поэтому распределение объявлено отдельным полем
(`split_into`), а не запасным составом: сошедшееся распределение закрыло бы
собой несошедшуюся цепочку прибыли, то есть скрыло бы дефект вместо того,
чтобы его показать. Сверяет его экран сверки той же арифметикой
(`quality/totals.py`), и в счётчик сверенных итогов оно входит.

**Один код в двух формах правомерен, а величина принадлежит форме.**
Неденежные корректировки отчёта о движении денежных средств по определению
повторяют статьи баланса и отчёта о прибыли — амортизация, проценты, права
пользования, — и плодить для них двойники справочника хуже, чем позволить
один код двум формам. Но **одна и та же позиция в балансе и в потоке — два
разных факта**: величины разных форм не складываются и не подменяют друг
друга, поэтому притязание строки чужой формы в величину позиции не входит
вовсе, а уходит отдельным исходом (`Fold.OTHER_FORM`). Раздел у него
не сверяется: разделы двух форм несопоставимы.

Прежде такое притязание отклонялось, строка возвращалась в очередь
и размечалась присест за присестом — у ФосАгро «права пользования» так собрали
три кода. Ключ уникальности `fact_report` форму содержит, поэтому два факта
в базе различаются сами; подтверждённое человеком в факты пока не пишется
вовсе, и это записано в `NIGHT_QUESTIONS.md`.

**Читающий факты обязан назвать форму, и правило выбора одно на проект**
(`normalize/ifrs_forms.py::pick_by_form`). Есть величина в форме, объявленной
у позиции, — берётся она; нет — берётся единственная оставшаяся, и это
называется: величина пришла из чужой формы. Отбросить её было бы хуже —
у эмитента, раскрывшего амортизацию в отчёте о прибыли, а не корректировкой
потока, EBITDA не посчиталась бы вовсе, а присвоение, сделанное человеком,
перестало бы работать молча. Прежде ключ был по коду без формы в трёх местах
разом — расчёт показателей, значения периодов, величины документа, — и оставалось
то из двух, что пришло позже, то есть выбор зависел от порядка строк в ответе
базы. Проверено: у Сегежи налог на прибыль равен −4 784 в отчёте о прибыли
и +4 784 в потоке, и так же расходятся знаком обесценение, курсовые разницы
и прочий финансовый результат — четыре величины из 24 столкновений на наборе.

**Позиция объявляет, складывается ли она из нескольких строк** (`summable`).
Обычно да: «Прочие доходы» и «Прочие расходы» у ЛСР — две строки одного
сальдо. Но распределение печатается один раз на блок, и та же формулировка
стоит второй раз под общим совокупным доходом: у Акрона «Собственникам
Компании» складывалось в 75 439 — величину, которой нет ни в отчётности,
ни в природе. Раздел таких строк не различает, потому что они стоят ниже
всех опознанных итогов, поэтому несуммируемая позиция при двух притязаниях
даёт **спор**: величина не берётся, строки уходят на разметку.

**Игнорируемое наименование — решение, неопознанное — недоработка.** Блок
`ignored` в `ifrs_lines.yaml` — то же, что `ignored_codes` у РСБУ, только
по наименованиям: у каждого предмета объявлена причина, строка не идёт ни
в очередь разметки, ни в основания экрана сверки и считается отдельно
(«осознанно игнорируется N» рядом с «не опознано M»). Объявлены четыре
предмета, и общее у них одно: **это величины на акцию и свойства
инструмента, а не финансового состояния** — прибыль на акцию, число акций,
номинал, дивиденд на акцию. Ни один показатель, флаг или стоп-фактор на них
не опирается, а единица у них своя (рубли на акцию), и в фактах комплекта
такое число было бы величиной в чужой единице.

Сравнение дословное, как у синонимов: игнорирование по вхождению слова
однажды проглотило бы настоящую статью, а потеря величины здесь так же
тиха, как везде в ветке. Наименование, объявленное и позицией,
и игнорируемым, справочник не загрузит — иначе строка опознавалась бы
и отбрасывалась одновременно. Перечень написаний бывает пуст: предмет
объявлен, строка не встречена, и выдумывать написание незачем.

**База существенности объявляется формой, а у потока её нет вовсе.**
Отсечка одна (5 %), а мерится ею величина к базе **своей формы**:
статья баланса — к валюте баланса, строка отчёта о прибыли — к выручке,
у отчёта о движении денежных средств базы нет, потому что поток за период
не доля ни от запаса, ни от оборота. Правило лежит в `materiality.bases`
(`ifrs_lines.yaml`), считает его одна функция
(`ifrs_extract.materiality_share`), и форма, о базе умолчавшая, справочник
не загрузит: молчание читалось бы как решение методики.

Прежде порог применялся к строкам любой формы: у О'КЕЙ «Поступление денежных
средств от покупателей» 249 352 219 против валюты баланса 74 006 934 давало
336,9 %, у Самолёта «Финансовые расходы» — 795 %. Из 106 статей сверх порога
65 были строками потока, и по ним же комплекты требовали подтверждения.
**Основание при этом исчезает, а не получает нулевой порог** — нулевой
срабатывал бы на любой строке потока. Рядом со сработавшими печатается число
измеренных строк: ноль статей сверх порога при неизвестном числе измеренных
не означает ничего.

**Мера называется вместе со своей базой.** Прежде разметка звала её «долей
активов», и у строки отчёта о прибыли графа содержала долю выручки — графа
считала не то, как называлась; в журнале подтверждений она теперь
`materiality_share`, а `NULL` в ней означает «мерить нечем», а не
«несущественна».

**Подтверждённые специфические статьи — в базе, не в методике.** Статья сверх
порога существенности не сворачивается в «прочее»,
а выносится отдельной позицией с кодом, присвоенным человеком на экране
сверки. Такие коды живут в `ifrs_line_confirmation`: методика правится руками
и диффом, а позиция, присвоенная во время работы, методикой не является.
Вместе с кодом хранится **наименование дословно**, как стояло в отчётности:
по коду не увидеть, одну ли вещь подтверждали у разных эмитентов под разными
названиями, — код присваивали мы. Представление `ifrs_core_candidate`
показывает, у скольких эмитентов статья подтверждена независимо; порог
кандидата в ядро задан методикой, а поднятие остаётся решением человека
и правкой YAML руками.

**Разметка переносится внутри эмитента и почти не переносится между
эмитентами.** Замер — `eval/ifrs_markup_scale.py` (`make ifrs-scale`),
на 15 комплектах: другой комплект того же эмитента закрывает 44–52 %
очереди, чужие эмитенты — 19,0 % (от 11 до 27 % по комплектам). Каждый новый
эмитент приносит около четырёх пятых новых наименований, и объём разметки
растёт вместе с набором почти линейно: около 45 решений на комплект при
измеренном темпе 25 секунд на решение.

Это не отменяет ядра: 33 кода из 91 встречаются у десяти и более эмитентов,
и опознаются ими 51,3 % строк. Но **по сумме общие коды покрывают 29 %**,
а у Черкизово 2,9 % — хвост, который приходится размечать руками, держит
деньги. Поэтому доля автоматического прохождения растёт не от добора
документов, а от роста справочника: все комплекты набора спотыкаются об одни
и те же три условия экрана сверки, и первое из них — неопознанная позиция.

**Порядок обхода на кривую насыщения влияет, поэтому мерится не он.**
У каждого комплекта считается доля очереди, встречающаяся у остальных, —
отдельно у своего второго комплекта и отдельно у чужих. Последовательная
кривая показывала бы 62–68 % там, где рядом стоят два комплекта одного
эмитента, и 3 % там, где эмитенты идут подряд, — то есть свойство порядка,
а не свойство данных.

## Запись комплекта МСФО

`normalize/ifrs_loader.py`, точка входа цикла — `pipeline.
accept_ifrs_document` с названным ИНН. Загрузка одной транзакцией, ключи
те же, что у РСБУ, и стандарт входит в них: `fact_report` различает величину
по МСФО и по РСБУ за одну и ту же дату.

**Прочитанное в документе помимо таблиц — один довод и одно чтение**
(`sources/ifrs_document.py::DocumentReading`: заключение, величины примечаний,
тип эмитента, наименование эмитента). Довод обязательный и позиционный,
поля без умолчаний, и набрать его руками боевой код не вправе — это
проверяется строением. Причина дорогая: шесть кодов аудиторского заключения
числились подключёнными с 18.09.2026 и не появились ни у одного комплекта,
потому что заключение читал цикл, а базу наполняет прогон приёма — он их
не читал вовсе. **Достижимость вызова не означает, что довод дошёл**, и реестр
контролей такого не ловит.

**Сведения заключения хранятся с комплектом** (`src_file.meta.audit`) сырыми:
вид мнения, разделы-признаки, дословный текст цитируемых разделов, аудитор
и дата. Документ собирается из базы, файла при сборке нет, и слова аудитора
взять больше неоткуда; формулировки при этом берутся из методики в момент
сборки — она правится, и результат обязан меняться вместе с ней. Из мнения
с оговоркой следует трое: сигнал в разделе 4, дословная цитата основания
в «Ограничениях анализа» и — **когда оговорка о величинах** — понижение
уверенности ступенью (`ifrs_audit.yaml`, блоки `caveat_kinds`, `signals`,
`quoted_sections`; основания понижения — `ifrs_metrics.yaml`, блок
`confidence`).
Три прочих состояния — обзорная проверка, нечитаемое заключение, отсутствие
заключения — уверенности не понижают: приравнять их молча значило бы решить
методический вопрос умолчанием.

**Сомнение в достоверности и сомнение в продолжении деятельности — разные
обстоятельства, и второе тяжелее.** Оговорка о достоверности говорит, что
часть отчётности аудитор подтвердил не полностью; раздел о существенной
неопределённости говорит, что организация может не продолжить деятельность
вовсе, — и объявляется он независимо от вида мнения: у Сегежи мнение
немодифицированное, а раздел есть. Поэтому неопределённость непрерывности —
**стоп-фактор** с ограничением класса D, надзорный сигнал и основание
понижения уверенности, а не запись в журнале. Прежде соразмерность выходила
перевёрнутой: у Сегежи при классе E уверенность стояла высшей и эскалации
не возникало, а у ФосАгро с нераскрытыми сегментами — средней и с эскалацией.

**Условие стоп-фактора задаётся величиной либо разделом заключения, и у
второго показателя нет вовсе** (`ifrs_issuer_type.yaml`, `condition:
audit_section`). Отсюда два следствия: нормы неприменимости к нему
не относятся — они говорят о показателях, — и «величина не рассчитана»
о нём не пишется: пробела данных здесь нет. Сверяется же с заключением
только стоп-фактор, выведенный **нами** из величин: вопрос сверки — видит
ли аудитор то же, что видим мы, и заданный о разделе заключения, он отвечал
«внешнего подтверждения нет» ровно у того обстоятельства, которое аудитор
и объявил.

**Оговорка о величинах и оговорка о раскрытии — разные обстоятельства,
и следствия у них разные** (`ifrs_audit.yaml`, блок `caveat_kinds`). Оговорка
о величинах ставит под вопрос сами числа, из которых считаются показатели:
у Автодора занижен резерв. Оговорка о полноте раскрытий говорит о составе
раскрытий при подтверждённых величинах: у ФосАгро не раскрыта информация
о сегментах, требуемая МСФО (IFRS) 8, — и понижать за это уверенность
в показателях не за что. Прежде вид не различался вовсе, и нераскрытые сегменты
понижали уверенность наравне с заниженным резервом, получая сверх того
надзорный уровень и эскалацию.

**Вид оговорки предлагает машина, а устанавливает человек** (`ifrs-confirm
--caveat about_values|about_disclosure`). Приметы в тексте основания — приметы,
а не доказательство: аудитор пишет прозой, и одно слово решает, о величине речь
или о раскрытии; приметы двух видов сразу предложения не дают вовсе. До решения
человека действует вид `not_determined`: уровень сигнала «требует внимания»,
уверенность не понижается, эскалации не возникает, а предложение машины
печатается рядом — тому, кто вид и подтверждает. **Решение переживает повторный
разбор**: сведения заключения читаются из документа заново, а вид оговорки
не оттуда, и не названный в новой загрузке он берётся из прежней записи
комплекта — иначе подтверждение исчезало бы при всякой правке разбора.
У каждого вида свой сигнал со своим уровнем и своя оговорка в «Ограничениях
анализа»: вид без сигнала молчал бы, а одна общая формулировка говорила бы
о нераскрытых сегментах то же, что о заниженном резерве.

**Уверенность в оценке МСФО понижается четырьмя основаниями, и два из них
не о заключении** (`ifrs_metrics.yaml`, блок `confidence`): оговорка
о величинах отчётности, объявленная неопределённость непрерывности, принятое
человеком основание карантина и группы, в каждой из которых рассчитано
по одному показателю. Последние два — о нашем знании, а не об эмитенте: комплект,
принятый решением человека, машиной не подтверждён, а балл группы
из одного показателя опирается на единственное наблюдение. Высокая
уверенность означает «понижать не по чему», и при таком основании она ложна.

**Цитата раздела кончается заголовком подраздела, и границу держит начало
строки.** Подразделы, предписанные МСА, разделами-признаками не являются,
и в «Основание для выражения мнения» у ФосАгро попали «Независимость»
и колонтитул страницы. Но и по вхождению слов резать нельзя: заключение
ссылается на «Ответственность аудитора…» внутри предложения, и цитата
обрывалась на середине фразы.

**Наименование эмитента читается строением документа**: титульный лист,
подтверждённый колонтитулом через формы. Оно же отводит чужой ответ — подпись
аудитора в титуле и заключении встречается чаще эмитента, и без правила
колонтитула наименованиями трёх комплектов из семнадцати становились аудиторы.
Из 17 документов наименование определилось у 12, у 5 отказ, неверных нет:
отказ здесь дороже догадки, потому что документ тогда выходит с ИНН в шапке —
это верно, а чужое наименование было бы ложью.

**Сравнительная графа примечания — та же величина за прошлый период.**
Прежде из примечания писалась только отчётная графа, и показатель,
считающийся по примечанию, за сравнительный период не считался вовсе:
у ФосАгро покрытие процентов за 2024 год отказывало «нет входных величин»,
тогда как проценты стоят в примечании 10 рядом с отчётными. Отказ был верен
по форме и неверен по существу.

**Пройденные условия экрана сверки идут в журнал записями `pass` с числом
проверенных объектов.** Иначе сводка контролей комплекта, прошедшего
автоматически, не содержит ни одной проверки — и по документу нельзя сказать,
что именно проверено.

**Отчётные даты определяются по каждой форме отдельно.** В годовом комплекте
они у всех форм одни, в промежуточном — нет, и это норма МСФО (IAS) 34,
а не исключение: отчёт о прибыли сравнивается с тем же периодом прошлого
года, отчёт о финансовом положении — с концом прошлого года. Даты берутся
из шапки таблицы самой формы (`ifrs_inbox.form_dates`), а кончается шапка
там, где начинается первая статья, — опора на строение, а не на число строк.
Форма, о своих датах умолчавшая, берёт даты документа, и перечень таких форм
объявляется (`DocumentProfile.inherited_dates`): молча унаследованная дата
неотличима от прочитанной.

Прежде одна пара дат применялась ко всем формам, и величина баланса
на 31 декабря записывалась ещё и под датой 30 июня — число настоящее,
баланс сходится, разделы сходятся, а такого периода у баланса нет вовсе.
Достройка голыми годами добавляла к двум настоящим датам выдуманную третью;
теперь она работает только там, где явных дат меньше двух.

**Роль периода назначается по порядку колонок своей формы**: первая отчётная
дата — `current`, остальные сравнительные. Правило приоритета то же, что
в РСБУ: сравнительное значение не затирает отчётное, а расхождение между ними
идёт в журнал кодом `period_value_mismatch`. Другого источника истины для
прошлой отчётности эмитента у нас нет, поэтому сравнивается с тем, что уже
лежит в базе.

**Столкновение периодов считается со знаменателем** (`period_priority`):
сколько входящих величин встретили уже загруженную, сколько совпало, сколько
отклонено приоритетом. Правило приоритета два года выглядело работающим,
не сработав ни разу — потому что дефект дат разводил сталкивающиеся величины
по разным периодам, а ноль отклонений при неизвестном числе сверок ничего
не означает. На парах комплектов ФосАгро, ЛСР и Сегежи столкновений
89, из них отклонено приоритетом 2.

**Записи состояния комплекта переписываются, записи событий — нет**
(`ifrs_loader.STATE_CODES`). Сводка сопоставления, сводка столкновений,
основания экрана сверки и сведения аудиторского заключения описывают
комплект и кладутся заново при каждой загрузке. Расхождение периодов,
расхождение соглашения о знаке и перезапись значения — события, и они
история.

**Комплект, не прошедший экран сверки и не подтверждённый человеком, уходит
в карантин.** Извлечение, о котором машина не знает, что перед ней, в расчёт
не идёт; подтверждение снимает карантин и сохраняет присвоенные коды
в `ifrs_line_confirmation`.

**Контроли РСБУ к комплекту МСФО не применяются, и об этом есть запись.**
Они построены на формах и кодах строк РСБУ — равенство 1600 = 1700, состав
разделов, цепочка прибыли; прогнать их по МСФО значило бы получить полтора
десятка ложных провалов и карантин на ровном месте. Пропуск объявляется
записью в журнал, а не молчанием: комплект без записей выглядит проверенным
и чистым.

**Прогон приёма — `eval/ifrs_intake_run.py`.** Отвечает на ключевой вопрос
ветки: какая доля документов проходит извлечение без участия человека.
Без `--write` в базу не пишет. Пустой каталог не даёт нулевой доли —
он говорит, что измерения не было: печатать ноль здесь значило бы выдать
отсутствие данных за результат.

## Извлечение форм МСФО и экран сверки

`sources/ifrs_extract.py` — разбор форм, `sources/ifrs_review.py` — решение
об автоматическом прохождении. Точка входа цикла — `pipeline.
accept_ifrs_document`: приём, извлечение, сверка.

**Ячейка таблицы читается по конвенции документа.** Разделитель разрядов
и разделитель колонок — оба пробелы, отличаются только шириной промежутка:
«700 000        650 000» — это две величины, а не одна. Внутри числа пробел
ровно один, между колонками два и более, и без этого различия колонки
слипаются в число, которого нет.

**Где границу колонки видно по координатам — она берётся оттуда.** Плоский
текст извлекателя сводит промежуток к одному пробелу, и «Амортизация
737 562» у Автодора читалось одной величиной: амортизация в шестьдесят
процентов активов. В координатах между «737» и «562» семьдесят три пункта,
а внутри «737» девять. Ячейки кладутся в колонки по **правому** краю —
величины выровнены по нему, левый у них разный, — и колонка примечаний
отпадает сама: она левее всех колонок величин у всех строк сразу.

Это свидетельство, а не правило строения числа, и оно старше правил.
Но **величин от него не убывает**: если ячейка не легла ни в одну колонку,
чтение по координатам отбрасывается целиком — свидетельство о границе
не повод потерять величину. Там, где координат нет, работают правила:
у готовой текстовой выгрузки координат не бывает.

Режим раскладки pypdf для той же цели не годится, и это проверено: он рвёт
слова («консолид ированного») и теряет повёрнутый текст, опознание у ЛСР
и Сегежи падает вдвое.

**Граница между формами и примечаниями держится с двух сторон, и обе нужны.**
Строка примечания, попавшая в очередь разметки основных форм, — это будущее
задвоение итога: её разметят кодом формы, и величина войдёт в состав дважды.
Поэтому заголовок формы не может стоять **внутри** примечаний, а блок формы
кончается там, где примечания начинаются, даже если таблица не кончилась.

У О'КЕЙ страница с отчётом о прибыли или убытке не имеет текстового слоя,
и заголовком формы стала проза примечания — «Сравнительные показатели отчёта
о прибыли или убытке… были пересчитаны», за которой идёт таблица прекращённой
деятельности. Блоком формы становилось примечание целиком: выручкой комплекта
оказывалась выручка прекращённой деятельности, 52 756 406 вместо настоящей.
Это тот же класс, что графы чужой длительности у ФосАгро — **величина
настоящая, но не та**, — и ловится он так же: не допуском, а строением.

**Отсчёт примечаний ведётся от первой найденной формы.** До форм нумерованным
абзацем идёт аудиторское заключение, и у Европлана «1. Мы не имели возможности
получить достаточные надлежащие аудиторские доказательства…» становилось
первым примечанием: тогда внутри примечаний оказывались все формы сразу,
и документ, в котором формы есть, объявлялся не отчётностью. Порядок проверок
здесь и есть правило: сперва формы находятся как прежде, затем по первой
из них считается начало примечаний, и лишь потом заголовки отбираются заново.

**Заголовок примечания величин не несёт.** Строка формы, у которой номер
примечания напечатан слева, выглядит заголовком точно так же: у СИБУРа
«4 Активы, предназначенные для продажи 12 605 -» — строка баланса, и указатель
начинал примечания на шестьдесят тысяч знаков раньше настоящего первого.
Определение строки таблицы одно на весь проект (`ifrs_inbox.is_table_row`).

**Заголовком формы становится то вхождение, за которым идёт сама форма,
а не первое упоминание её наименования.** Упоминаний в документе несколько,
и у трёх комплектов из пятнадцати первым шло не форма: у Самолёта — строка
«Содержания», у которой номер страницы ушёл в перенос (таблицу под ней
изображали телефоны с бланка аудитора, и «Fax: +» шло в очередь разметки
величиной 755 970, то есть 74 % валюты баланса); у Брусники — ссылка в прозе
другой формы, «(по данным консолидированного отчета о движении | денежных
средств) 14, 15 1 538 1 141», за которой стоят десять строк сверки EBITDA.
В обоих случаях настоящая форма не разбиралась вовсе: у Брусники фактов
потока не было ни одного.

Различают их два признака, и оба структурные. **Оглавление объявляет себя
перечнем**: рядом со строкой оглавления стоят другие такие же, с номером
страницы в конце и без иных чисел, — по отдельности такая строка от заголовка
неотличима, а две подряд встречаются только в оглавлении. И **заголовок формы
сам строкой таблицы не бывает**: то же `is_table_row`, что и у границы
примечаний. Третий случай — СИБУР — этими признаками не снимается: у него
страница отчёта о прибылях без текстового слоя, и наименование нашлось
у отчёта о совокупном доходе; потеря страницы **первой** формы в признак
`pages_without_text` не попадает, потому что окно считается между первой
и последней найденной формой. Это записано в `NIGHT_QUESTIONS.md`.

**Неподписанный итог опознаётся структурой, а не наименованием.**
У Норникеля итог внеоборотных активов — просто число, у ФосАгро слово
«Внеоборотные активы» служит и заголовком раздела, и подписью итога. Опора
одна: строка, равная сумме предшествующих строк блока. Равенство здесь —
способ опознания, а не контроль качества: оно отвечает на вопрос «что это
за строка». **Совпадение требуется по всем периодам сразу**: по одному оно
бывает случайным, и такая строка остаётся неопознанной — то есть уходит
на экран сверки, а не в расчёт.

**Текст под формой извлекается наравне с таблицей.** У ЛСР сноской под
балансом сказано, что в состав денежных средств не включены средства
на счетах эскроу — 217 501 млн руб. Парсер таблиц её не увидит, а без неё
ликвидность читается неверно.

**Автоматическое прохождение — условие осуществимости, а не послабление.**
При обязательном ручном подтверждении скрининг ста эмитентов невозможен,
а маршрутизация — цель ветки. Извлечение принимается само, только если
сошлись все контроли, опознаны все позиции, нет статей сверх порога
существенности и вид отчётности полный. Ни одно условие не смягчается:
каждое из четырёх — случай, когда машина не знает, что перед ней.
Автопрохождение при нуле выполненных проверок запрещено отдельно — это
было бы то же «ноль срабатываний», только в решении о приёме.

**Основание подтверждения уходит в журнал кодом контроля** (`REASON_CODES`):
основание без кода в `dq_log` не попадёт, и причина отбраковки останется
в памяти того, кто смотрел экран.

**Для нового эмитента автопрохождение недостижимо, и это свойство ветки,
а не её дефект.** Условие «опознаны все позиции» требует, чтобы справочник
знал каждую строку документа, а замер разметки показал: каждый новый эмитент
приносит около четырёх пятых наименований, которых не было ни у кого
(`eval/ifrs_markup_scale.py`). Значит, первый документ эмитента проходит через
человека всегда, а автоматическим может стать только **повторный** — следующий
год уже размеченного.

**Первое автопрохождение случилось 21.09.2026** — годовой комплект ФосАгро,
1 из 14. Стоило оно того, что перечислено ниже: 290 подтверждений человека,
63 синонима, 15 позиций ядра, правило игнорируемых наименований и восемь
починенных дефектов разбора — графы чужой длительности, разорванное слово,
граница примечаний, потеря разметки при исправлении, заголовок формы
из оглавления и из прозы, мера существенности не по своей форме, притязание
чужой формы, подтверждённое опознание без фактов. Ни одно условие экрана при
этом не смягчалось — смягчилась только наша неспособность их выполнить.

**Цена измерена и растёт не там, где кажется.** Из восьми дефектов шесть
нашлись не журналом и не тестом, а замером, поставленным ради другого:
телефоны с бланка аудитора — по доле существенности выше 100 %, склейка номера
примечания с величиной — тем же замером, отсутствующая форма — сверкой
обещанного с найденным. Правило отсюда одно: **счётчик, поставленный рядом
с проверкой, находит дефекты, которых проверка не искала.**

Последней держала одна строка, и держала её **наша** ошибка: «права
пользования» получили балансовый код в отчёте о движении денежных средств,
притязание отклонялось правилом формы, строка возвращалась в очередь, а
человек размечал её заново — три присеста подряд, потому что исправление
ложилось рядом с ошибкой, а не заменяло её.

**Опознание бывает двух сил, и слабейшей хватает для повторного комплекта
того же эмитента.** Справочник утверждает: строка с таким наименованием
означает это у любого эмитента. Ранее подтверждённое утверждает меньше:
у **этого** эмитента эта строка означает это. Условие «опознаны все позиции» —
требование методики, а не логическая необходимость, и подтверждение его
выполняет: человек уже смотрел ту же строку в той же форме той же
организации, и машина ничего не угадывает. Это не смягчение, а второй
источник того же знания.

Границы объявлены и не раздвигаются (`sources/ifrs_confirmed.py`): **только
тот же эмитент** — у чужого то же слово может означать другое, потому
подтверждённый код и не становится ядром; **только то же наименование** —
сравнение приведёнными наименованиями, тем же `normalize_name`, которым
опознаётся любой синоним; **только та же форма и раздел** — притязание
строки чужой формы отклоняется, как у автомата. Индекс строки в ключ
не входит: у следующего года он означает другую строку. Величины
подтверждённых строк участвуют в итогах наравне с опознанными справочником,
и **в документе печатаются оба числа** порознь («Опознание позиций:
справочником N, по ранее подтверждённому M») — доверие к ним разное.

**Подтверждённое идёт в факты, и сила опознания хранится рядом с величиной**
(`fact_report.recognition`: `catalog` или `confirmation`). Прежде факты
писались только из строк, опознанных справочником, и статьи, о которых человек
уже сказал, чем они являются, в расчёт не попадали вовсе: у Норникеля
выпадали все 64 подтверждённые статьи, у Автодора 39 из 40 — включая две,
в которых лежат 85 % активов. Показателей по МСФО при этом не считалось
ни одного (все комплекты в карантине), поэтому ни одно число дефект
не исказил, — но снятый карантин означал бы расчёт по неполным данным.

Фактами становятся точное присвоение и специфическая статья. Детализация
и агрегат — нет: величина детализации уже входит в свою позицию, а агрегат
покрывает несколько позиций, и разложить его нечем. Форма факта берётся
у строки, а не у позиции: балансовый код в отчёте о потоках — другой факт.

**Дословная запись и ключ поиска — разные графы.** `source_name` хранится как
прочитано, с мусором разбора того дня («Поступление от выпуска акций 19
51 012 -»), и не правится никогда: это доказательная база. Искать же
подтверждение надо ключом нынешнего разбора, поэтому рядом лежит `match_key` —
величина производная, и она пересчитывается перед каждым присестом разметки.

**Ключ вычисляет тот же разбор, что делит строку формы**
(`ifrs_extract.row_name`): наименование отделяется от номера примечания
и величин одной функцией, и двух определений наименования в проекте быть
не должно. Сравнение по ключу идёт во всех трёх местах — проверка занятости
кода, перенос разметки между комплектами и вопрос справочнику «не опознаёшь
ли ты теперь эту строку сам». Прежде сравнивалось дословно, и у Сегежи
«Обязательства, относящиеся к опционным соглашениям» под старым склеенным
написанием **занимали код у самих себя**: разметка отказывала — «код уже
присвоен статье», называя ту же статью, — и человеку предлагалось завести
второй код для одной вещи. Таких записей нашлось 8 у трёх эмитентов.

**Остальные основания это не затрагивает.** Неполный вид отчётности
и страница без текстового слоя остаются блокирующими: там не опознание,
а состав раскрытий и потеря содержимого, и подтверждением строки они
не снимаются. Отсюда и цена: у ЛСР годовой после этой правки не осталось
ни одной неопознанной строки, ни одной статьи сверх порога и все 14 итогов
сошлись — а автопрохождения нет, потому что отчётность раскрываемая и внутри
форм потеряна страница 6. Из 15 разобранных комплектов 7 не полные, а страницу
теряют 5 комплектов у 4 эмитентов; ближе всех к автопрохождению годовой
ФосАгро — одно расхождение итога и четыре строки.

**Арифметика «лучшего состава» одна на два экрана.** Экран разметки знал
о запасных составах, а экран сверки нет, и один комплект получал два разных
ответа: у ЛСР разметка показывала 14 сошедшихся итогов из 14, а сверка —
провал контроля. Запасные составы объявлены методикой потому, что у Сегежи
нет валовой прибыли, а у ФосАгро и Норникеля — строки «Итого обязательства»;
экран, не знающий об этом, мерил не отчётность, а собственную неполноту.

Смягчать условие нельзя: оно означает «машина знает, что перед ней», и любое
послабление возвращает разбор к угадыванию. Из свойства следует не правка
критерия, а **разделение источников**, на котором ветка и построена: масса
эмитентов отбирается по Cbonds, где документ не нужен вовсе, а PDF идёт
в разбор там, где нужны примечания, эскроу, заключение аудитора и
специфические статьи. Скрининг ста новых эмитентов делается нормализованными
данными; автоматический разбор документа — это ежегодный пересчёт по тем,
кого уже разметили.

## Приём файла МСФО: порядок определения параметров

`sources/ifrs_inbox.py::identify`, правила — `methodology/ifrs_parsing.yaml`.
Параметры определяются по очереди, и **очередь — часть правила, а не деталь
устройства**: текстовый слой, тип документа, периметр методики, валюта,
единица, разделитель разрядов, отчётные даты, вид отчётности.

**Тип документа проверяется до всего остального.** Годовой отчёт эмитента
на триста страниц финансовой отчётностью не является, но числа в нём есть,
они осмысленны, и любой параметр в нём определится: найдётся и валюта,
и единица, и конвенция записи чисел. Документ пройдёт приём и станет
комплектом, которого не существует. Проверено дорого — однажды вместо
отчётности загрузились пять годовых отчётов. Признак отчётности —
заголовки основных форм, и берутся они из справочника статей вместе
с синонимами: перечень один на всю ветку.

**Отказы называют код контроля и причину словами**: нет текстового слоя
(скан, распознавание не реализовано), не отчётность, финансовая организация,
валюта не определена, валюта не рублёвая, единица не определена, конвенция
не определена, отчётные даты не найдены. Файл, не ставший комплектом, фактов
не порождает.

**Валюта и единица не принимаются по умолчанию.** В долларах отчитываются
и российские эмитенты, а ошибка в единице не ловится ни одним контролем
сходимости — то же основание, что у разделителя разрядов. Умолчание
объявлено только у вида отчётности, и там оно неопасно: полная годовая
отчётность маркеров не несёт, а промежуточная, раскрываемая и специального
назначения объявляют себя сами. Ошибка в сторону полноты видна сразу —
примечания, которых требует методика, не найдутся.

**Число периодов переменное и берётся из документа**: Норникель даёт три,
остальные разобранные эмитенты два. Заранее заданное число отбросило бы
колонку.

**Графы различаются не только датой, но и длительностью периода, и берутся
графы объявленной длительности.** Промежуточный отчёт ФосАгро о прибыли или
убытке печатает четыре графы: полугодие 2026, полугодие 2025, квартал 2026,
квартал 2025 — МСФО (IAS) 34 этого не запрещает. Прежде бралось столько
последних граф, сколько у формы отчётных дат, то есть квартальные, и комплект
за полугодие собирался из величин квартала: прибыль 18 432 вместо 18 653,
налог −6 466 вместо −6 766, себестоимость −100 381 вместо −194 587. Ошибка
того же рода, что разделитель разрядов: графа согласована сама с собой, все
итоги по ней сходятся, и неверны только сами величины — поэтому отношение
то же, правило вместо предположения и отказ при расхождении.

Длительность читается из шапки таблицы словами
(`methodology/ifrs_parsing.yaml`, блок `column_spans`), длительность
комплекта — из отчётной даты правилом методики показателей
(`annualisation.months_from`), одним на весь проект. Разметка граф живёт
в `ColumnLayout` и доходит до разбора через `DocumentProfile.columns_by_form`.
**Правило действует и в чтении по координатам**: координаты говорят, где
кончается графа, но не говорят, за какой период она приведена, и самые правые
графы у ФосАгро квартальные — одна форма выходила собранной из двух периодов,
выручка за полугодие и финансовые доходы за квартал.

**Объявление сильнее умолчания.** Вид отчётности определяется маркерами
с объявленным умолчанием «полная», и документ, чьи формы назвали длительность
граф сами, о своём периоде заявил прямо: отказать ему за наше умолчание
значило бы предпочесть догадку заявлению. Поэтому при расхождении делается
одна проверка по правилу отчётной даты, и сошлось — комплект промежуточный,
а маркера вида мы не знаем (это пишется в журнал).

**Граф больше, чем дат, а длительность не объявлена — блокирующее нарушение,
а не норма** (`extra_columns_dropped`). Отброшенная вслепую графа может быть
как раз той, величины которой нужны, поэтому строка называется вместе
с числами, а рядом стоит знаменатель — сколько строк с величинами всего.
Номер примечания отброшенной величиной не считается: он ссылка. Шапка таблицы
и колонтитул в счёт не идут — они отсеяны отдельно и объявлены
в `auto_dismissed`.

## Разделитель разрядов документа МСФО

`methodology/ifrs_parsing.yaml`, определитель — `sources/ifrs_numbers.py`.
**Конвенция определяется по документу целиком, а не по отдельному числу.**
Отдельное число её не выдаёт: «663,888» — это 663 888 при запятой в роли
разделителя разрядов и 663,888 при запятой в роли десятичного знака. Оба
прочтения осмысленны, различаются в тысячу раз, и выбрать между ними можно
только по выборке чисел.

**Это тот же класс дефекта, что единица измерения в РСБУ.** Применённая ко
всем числам одинаково, неверная конвенция оставляет баланс сошедшимся,
разделы сошедшимися и коэффициенты верными — неверными окажутся все
абсолютные величины. Поэтому отношение то же: правило, а не предположение,
и отказ при неопределённости.

Свидетельством считается только однозначная разметка: пробел между группами
по три цифры и дробная часть не из трёх цифр — за русскую конвенцию; две
и более запятых в одном числе, дробная часть после точки — за английскую.
Число вида «663,888» свидетельством не является ни для одной: именно оно
и создаёт неоднозначность. Иначе — `digit_grouping_not_determined`, причины
различаются (`ambiguous`, `conflicting`, `insufficient`, `outweighed`).

**Порог улик один на обе стороны.** Требовалось три улики у победителя
и ни одной против — то есть полное единогласие. Единогласия не даёт ни одна
вёрстка: проверено на Акроне, где 162 улики за русскую конвенцию и ноль
против, а одно подставленное число английской разметки отказывает документ
целиком. Одна-две улики противоположной стороны — та же опечатка
составителя, что и одна улика в пользу победителя, и мерить их разными
мерками нельзя. Они отбрасываются и **называются в журнале**: числа,
прочитанные вопреки собственной разметке, человек обязан увидеть. Три
и более с каждой стороны — конвенции в документе действительно две,
и это отказ.

**Отказ по конвенции проверяется глазами, поэтому печатает сами числа.**
Счётчик отвечает «сколько улик», а разбираться приходится с «какие»:
«1.5» — улика за английскую конвенцию ровно до тех пор, пока не видно,
что это ставка процента. `GroupingDetection.evidence()` отдаёт числа
с обеих сторон, `pdf-check` печатает их вместе со строками, в которых
они стоят.

**Правдоподобие проверяется после определения** — `check_plausibility`:
сумма разделов против итога, актив против пассива, валюта баланса против
порядка величин выручки. Проверяется именно кратность тысяче: расхождение
в полтора раза бывает дефектом отчётности и ловится контролем сходимости,
а отношение ровно в тысячу раз означает разное прочтение чисел. Счётчик
сверенных величин идёт рядом с числом расхождений.

**Конвенция хранится в `src_file.digit_grouping` и печатается в приложении**
наравне с единицей измерения: ошибка в разделителе даёт верные коэффициенты
при неверных величинах, и по самому документу её иначе не увидеть. Для
источников, отдающих числа машиночитаемо, графа объясняет, почему конвенции
нет, вместо того чтобы пустовать.

**Арифметика сходимости вынесена в `quality/totals.py`** и работает с любым
справочником: она проверяет равенство суммы, а не природу кодов. Там же
живёт единственная законная подстановка нуля — `as_addend`, и `metrics/`
этот модуль не импортирует, что проверяется тестом.

Получение отчётности по МСФО — отдельная задача после задачи 10. Первым шагом
там ручная загрузка файлов в `data/raw/ifrs/{ИНН}/` и разбор XBRL, где он есть;
PDF — только через выгрузку в таблицу руками. Автоматическое получение
с `e-disclosure.ru` не планируется: источник отвечает HTTP 403 на вежливый
`User-Agent`, обходить защиту мы не будем.

## Cbonds: нормализованная отчётность как вторая опора

`data/raw/cbonds/` — сохранённые ответы, `sources/cbonds.py` — клиент
и чтение их с диска. **Клиент появился 18.09.2026**, прежде его не было
намеренно. Решение принято не потому, что источник стал основным: основными
формами остаются PDF эмитента и ГИР БО. Он нужен, чтобы отбирать эмитентов
по признакам **до** выгрузки документа, — руками этого не сделать.

**Имя метода выводится из данных, а не подбирается.** В номенклатуре поле
`report` равно `report_msfo_real`, и метод называется `get_report_msfo_real`;
`get_msfo_real` источник не знает вовсе. Ошибка называет причину словами
и различает два случая: `invalid operation name` — метода нет,
`invalid resource name` — метод есть, доступа к нему нет.

**Неподдерживаемое поле отбора Cbonds пропускает молча** и отдаёт весь
справочник: запрос эмитентов по наименованию возвращает 323 925 записей,
начиная с Ленинградской области, и первая же сошла бы за найденного
эмитента. Поэтому клиент сверяет записи с условием отбора
(`_verify_applied`) и при расхождении отказывается. Отбор возможен только
по `emitent_inn`; по наименованию источник не отбирает, и перечень
приходится забирать целиком — он невелик, 6 194 записи по 481 эмитенту.

Что отбирается по API: валюта (472 RUB, 7 USD, 1 EUR, 1 KZT), масштаб,
убыток (142 из 481), отрицательный капитал (40 из 481). Чего нет:
аудированность (`ln101` равно нулю у всех, включая заведомо аудированных),
вид мнения, обзорная проверка, конвенция разрядов и число отчётных колонок —
последние два суть свойства вёрстки документа, которых у нормализованных
данных нет по устройству. **Отбирать убыточных по EBITDA нельзя**: у Автодора
и Сегежи она равна нулю при настоящем убытке; для этого служит чистая прибыль.

Отдаёт по ИНН нормализованные формы: пять строк ОПУ, три сальдо потоков,
полтора десятка строк баланса, реквизиты (валюта, масштаб, стандарт,
аудированность). Сверка на пяти эмитентах: **из 97 величин отчётного
периода разошлись пять**, и все пять различаются определением показателя,
а не ошибкой разбора. Заполненность высокая — 29–31 первичная статья
из 32 у каждого.

**Приоритет источников объявлен, и он не тот, что у ролей периода.**
Сравнительная колонка свежего отчёта эмитента **главнее** данных Cbonds
за тот же период: она из первоисточника и отражает последнюю редакцию
самого эмитента, тогда как запись агрегатора — его прочтение отчёта того
года. Внутри первоисточника прежнее правило в силе: отчётный период
не затирается сравнительным. Cbonds остаётся независимой проверкой,
и расхождение содержательно.

Проверено: расхождение редакций **не системно**. Из 127 сверенных величин
за отчётный и сравнительные периоды пяти эмитентов разошлись семь, и пять
из них у одного Автодора, где пересмотр настоящий (операционная прибыль
2024 года 448 против 2 272). У ФосАгро, ЛСР и Сегежи совпадение полное.

**Чего Cbonds не различает — то и размечается.** Всё, что не легло
в именованные коды, сворачивается в «прочие», и доля свёрнутого
отличается на два порядка: 0,3 % валюты баланса у ЛСР против 86 %
у Автодора. Отсюда признак очереди разметки `Priority.IN_CBONDS_OTHER`:
раздел, «прочее» которого существенно по валюте баланса, и строка,
существенная **внутри этого прочего**. Второй порог берётся от прочего,
а не от валюты: у Сегежи прочие внеоборотные активы — тридцать процентов
баланса, и строка в полтора процента валюты составляет двадцатую часть
того, чего не видно вовсе.

Разметка от этого не отменяется, а сужается до статей, которых нет нигде,
кроме PDF. **Работа с PDF остаётся и по другой причине**: примечания,
аудиторское заключение, сноски и специфические статьи есть только там.
Средства на счетах эскроу ЛСР — 217 501 млн — стоят сноской под балансом,
и у Cbonds их нет ни в каком виде.

**Ноль у Cbonds не означает нуля.** Источник пишет ноль и там, где
величина не раскрыта: у Автодора за 2024-03-31 активы и капитал нулевые
при выручке 715, OIBDA нулевая у всех пятерых во всех периодах. Различать
предстоит нам, и правило — три признака, а не перечень полей: ноль,
ломающий тождество отчётности; ноль у итога при ненулевом составе; ноль,
постоянный у эмитента и непостоянный у других. Третий признак включается
при наборе эмитентов и до тех пор объявлен недействующим — иначе он мерил
бы размер набора.

## Потеря внутри читаемого документа

**Страница без текстового слоя внутри распознаваемого файла — отдельный
класс дефекта, и он опаснее скана целиком.** Скан отбраковывается
на входе; потеря одной страницы не отбраковывается ничем: половина формы
извлеклась, контроли по ней прошли, и заметить нечем. У Автодора баланс
занимает страницы 8 и 9, слой есть только у восьмой — **вся сторона
пассива не существовала**, а актив при этом сходился сам с собой.

Не редкость: из восьми файлов МСФО страницы без слоя есть у четырёх, и у трёх
из них потеря приходится на страницы внутри форм (Автодор — 9, ЛСР — 6,
Самолёт — 9 и 12). Признак — `PdfDocument.pages_without_text`, в профиле
остаются только страницы между первой и последней формой: аудиторское
заключение сканом разбору не мешает. Такой комплект автоматически
не проходит.

**Проверка эта до 18.09.2026 в цикле не работала.** `identify` получает
страницы отдельным доводом, а цикл его не передавал — и признак всегда был
пуст. Контроль отвечал одно и то же, то есть был неотличим от невыполненного;
поймал его не журнал, а случай Самолёта: текстовый слой у документа есть,
формы находятся, а двух страниц внутри них нет.

**Потеря страницы **первой** формы окном не ловится, и ловит её обещание
документа.** Окно считается между первой и последней **найденной** формой,
поэтому у СИБУРа страница отчёта о прибылях — 7-я из 60 — оказалась до окна:
первой найденной формой стал отчёт о совокупном доходе, а потерянная форма
выглядела как форма, которой в документе нет. Поэтому перечень форм берётся
из обещания самого документа (`ifrs_inbox.expected_forms`): сперва
из аудиторского заключения — оно перечисляет проверенную отчётность, — при
нечитаемом заключении из оглавления, а если нет и его — обязательным составом
МСФО (IAS) 1. Форма из перечня, не найденная при найденных остальных, даёт
`lost_page` с указанием, чем она была обещана.

Перечень сужен до форм, которые методика разбирает: отчёт об изменениях
капитала IAS 1 требует, а мы его не разбираем, и требовать его значило бы
объявлять потерю там, где её нет. Обещание при этом переносится по строкам
в обеих своих формах — «о прибыли или | убытке» в заключении,
«…о прибыли или убытке | и прочем совокупном доходе 12» в оглавлении, — и без
склейки теряется вместе с потерей формы. На наборе обещание читается у всех
15 комплектов: 14 из заключения, Автодор из оглавления — его заключение скан.

**Случай СИБУРа этим не закрыт, и это объявлено.** Заключение обещает четыре
отчёта, справочник знает три кода, «о совокупном доходе» — синоним кода ОПУ,
и форма считается найденной, хотя найдена другая. Развести их можно только
отдельным кодом формы для совокупного дохода; пока этого нет, потеря видна
лишь по нулю опознанных строк в форме.

**Проверять документ до выгрузки в проект — `fin-analysis pdf-check ПУТЬ`**
(`make pdf-check FILE=…`), файлы или каталоги, в базу не пишется ничего.
Команда печатает и то и другое порознь: страницы без слоя вообще и те из них,
что попали внутрь форм, — и рядом что из документа извлеклось: формы, даты
каждой из них, опознанные строки, сведённые итоги. **«Текстовый слой есть»
и «формы извлекаются» — разные вещи**, и различает их только второй набор
цифр.

**У выгрузок РСБУ тот же класс выглядит иначе.** Страниц там нет, но есть
точный аналог: лист формы в файле есть, а раскрытых величин из него ноль.
На 71 выгрузке таких три — проверено, в источнике они действительно пусты,
разбор не виноват. Молчания при этом быть не должно по тому же правилу,
по которому ноль срабатываний неотличим от невыполненного контроля.

## Доверие к периоду

Блокирующие контроли применяются только к отчётному периоду комплекта, поэтому
период, существующий **только сравнительной колонкой**, ими не проверялся.
Представление `period_quality` и `quality/periods.py` дают явный признак:

- `verified` — период проверен в своём комплекте;
- `comparative_only` — собственного комплекта нет, показатели считаются,
  но с пониженным доверием;
- `quarantined` — собственный комплект в карантине, период в расчёт не идёт.

Признак пишется в `metric_value.confidence`. Текст оговорки отдаёт
`quality.periods.limitations(inn)`, и он **обязан** попасть в раздел
«Ограничения анализа» заключения: иначе динамика за три года выглядит
одинаково достоверной, хотя два периода блокирующими контролями не проверялись.

## Контроли качества

Допуски и уровни — `methodology/thresholds.yaml`, в коде их нет. Прогон —
`quality.runner.run_checks(src_file_id, conn)`, всё одной транзакцией.

**Подстановка нуля живёт в одном месте — `quality/values.py::as_addend`.**
Это единственная функция, имеющая право превратить нераскрытое значение в ноль,
и пользуются ею только контроли сходимости. Модуль `metrics/` её не импортирует,
что проверяется тестом, а не соглашением: при расчёте коэффициентов нераскрытое
значение остаётся `NULL`, показатель получает `not_calculable`.

**Четыре исхода контроля, и их нельзя путать.**

| Исход | Когда | Статус / уровень |
|---|---|---|
| пройден | сошлось в пределах допуска | `pass` |
| провален | не сошлось | `fail`, уровень из методики |
| не выполнялся | итог не раскрыт или не раскрыто ни одно слагаемое | `info` / `info` |
| не проверяемо | слагаемое не загружено, потому что **мы** отказались угадывать | `info` / `warning` |

Последний случай отдельный и важный: у малого предприятия код 1190 подходит
двум укрупнённым строкам, мы его не разносим, и итог раздела I проверить
нечем. Это наш пробел, а не дефект отчётности, поэтому карантина он не вызывает
и в сообщение выносится код-виновник. Иначе каждое малое предприятие уезжало бы
в карантин ни за что.

**Строка 2410 приходит по-разному в двух наборах.** В полной форме — со знаком
(минус при расходе, плюс при налоговом доходе), и в составе 2400 складывается.
В упрощённой — положительной величиной и вычитается. Проверено на данных:
у Газпрома за 2020–2025 годы `2400 = 2300 + 2410 + 2460` сходится во всех
восьми периодах, у Стройсервиса `2400 = 2110 − 2120 − 2330 + 2340 − 2350 − 2410`
сходится копейка в копейку. Это различие форм, а не ошибка.

**Четыре судьбы кода источника, и их нельзя смешивать.**

| Исход | Что значит | Журнал |
|---|---|---|
| `mapped` | код привязан к строке справочника | — |
| `ignored` | методика не использует код осознанно, список в `lines.yaml` | не пишется |
| `not_applicable` | код есть в полном наборе, но не в упрощённом; упрощённая форма приходит в той же схеме, что полная | не пишется |
| `unknown` | кода нет ни в одном наборе — **сигнал проверить справочник** | `unknown_line_code` |

Игнорируемый код — принятое решение, неизвестный — недоработка. Если код
начал появляться в отчётности и не опознаётся, его нужно либо завести
в справочник, либо явно внести в `ignored_codes` с обоснованием.

**Неоднозначность кода и спор кодов — разные вещи, разные контроли.**
`ambiguous_line_code` — код допускают несколько строк (1190 подходит и
«Материальным внеоборотным активам», и «Нематериальным, финансовым и другим»);
разрешается по занятости, то есть исключением претендентов, чей канонический
код уже раскрыт в этой же отчётности, а при неразрешимости строка не грузится.
Причина здесь — неполнота справочника. `multiple_source_codes` — значение одной
укрупнённой строки раскрыто сразу несколькими кодами (1220 и 1230 при том, что
оба это «Финансовые и другие оборотные активы»); причина здесь — аномалия самой
отчётности, и это может быть содержательным сигналом. Различать по `details`
нельзя: коды нужны раздельно в сводке качества, в фильтрах и в заключении.

**Оговорки справочника попадают в заключение.** Если в расчёте участвовала
строка, у которой в `lines.yaml` заполнено поле `note` (например,
«Материальные внеоборотные активы» — ограничение по незавершённым
капитальным вложениям, которые в полной форме могут стоять по строке 1190),
текст `note` обязан попасть в раздел «Ограничения анализа» заключения
(задача 9). Оговорка, оставшаяся только в справочнике, считается потерянной.

**Соглашение о знаке.** Расходные и контр-статьи (себестоимость, проценты
к уплате, собственные акции, платежи по ОДДС) хранятся в `fact_report` как
величина расхода, а вычитание задано оператором в составе итоговой строки:
`2100 = +2110 −2120`, `1300 = +1310 −1320 +1340 +1350 +1360 +1370`. Такие
строки помечены `in_brackets: true`. Поле `sign` говорит о другом — может ли
показатель быть отрицательным (`any`) или нет (`positive`); это вход для
контролей качества, а не для арифметики.

## Источник ГИР БО

Протокол выверен на реальных пробах, они лежат в `data/raw/probe/`. Домен —
`bo.nalog.gov.ru`, старый `bo.nalog.ru` отдаёт 302; базовый URL и контакт для
`User-Agent` берутся из `.env`, в коде их нет.

- Два запроса на организацию: поиск по ИНН и `/nbo/organizations/{id}/bfo/`,
  который отдаёт **все годы и все формы разом**. Ответ — JSON, не XML.
- Формы приходят отдельными блоками (`balance`, `financialResult`,
  `fundsMovement`), значения — в атрибутах `current1600`, `previous1600`,
  `beforePrevious1600`. Наименований строк в ответе нет: для этого источника
  строка опознаётся по коду, `match_by_name` нужен только файловым источникам.
- **Тип отчётности — по `knd`:** `0710099` полная, `0710096` упрощённая.
  Код формы (`okud`) при этом одинаковый, различать по нему нельзя.
- **Глубина истории по формам разная:** третий период (`beforePrevious`) есть
  только в балансе, у ОФР и ОДДС его нет. Метрики задачи 6 обязаны опираться
  на `report_dates` конкретной формы, а не считать глубину одинаковой.
- **Единица измерения в ответе не указана вообще.** Значения приходят
  в тысячах рублей, это принимается как предположение: `unit_code = '384'`,
  `unit_source = 'assumed'`.
- **Числа читаются только через `json_loads_decimal`** (`parse_float=Decimal`).
  Дробные значения в ответе есть, обычный `json.load` нарушит инвариант 5.
- **Отчёт об изменениях капитала (0710004) не разбирается.** В ответе он есть,
  но устроен матрицей (`authorized3100`, `additional3100`, `reserve…`), в
  справочник строк не заложен и в методике не используется. Нераспределённая
  прибыль берётся из баланса — **строка 1370**, искать её в форме 0710004
  не нужно. То же касается отчёта о целевом использовании средств.
- **Корректировки:** `correction_version` входит в ключ уникальности
  `src_file`, актуальность определяется сравнением с `actualCorrectionNumber`.
  При этом **источник отдаёт только актуальную версию** — прежней в ответе
  нет (проверено на ИНН 2522002003: за 2024 год `actualCorrectionNumber = 1`
  и ровно один элемент `typeCorrections` с `correctionVersion = 1`, версии 0
  в ответе нет). Поэтому обе версии оказываются в БД только за счёт наших
  собственных запусков: если версия 0 была загружена раньше, она остаётся
  лежать, а пришедшая версия 1 добавляется отдельной строкой. Загрузчик
  обязан снять признак `is_actual` со всех прежних версий того же года.
- **Кредитные организации вне периметра.** Банки сдают отчётность в Банк
  России по формам 0409, в ГИР БО их нет (ИНН Сбербанка 7707083893 даёт пустой
  результат поиска). Признак `isCb` отбраковывается на входе с записью
  в `dq_log` (`check_code = 'credit_organization'`, уровень `blocking`).

Показатель, для которого нет входных данных, не рассчитывается и помечается
как `not_calculable` с указанием причины. Подстановка приближений запрещена:
например, при отсутствии амортизации показатель «Чистый долг / EBITDA»
не считается, а не заменяется на «Чистый долг / прибыль от продаж».

## Ручная подача

Когда источник недоступен, отчётность выгружается из ГИР БО руками и кладётся
в `data/inbox/` файлами XLSX. Разбор — `sources/inbox.py`, загрузка та же:
файл даёт тот же `ReportSet`, что и ответ ресурса, и проходит те же этапы.
Комплект, организация и форма живут в `sources/model.py`, а не в `girbo.py`:
это модель отчётности, а не деталь конкретного источника.

**Организация, период, тип отчётности и единица измерения берутся
из содержимого файла.** Имя файла не значит ничего — его назначает тот, кто
выгружал. ИНН стоит в реквизитах, в шапке каждой формы и в номере выгрузки
(`0710099_7736050003_2025_000_20260916`); расхождение между этими местами —
отказ, а не выбор. Номер выгрузки — единственное место, где есть номер
корректировки. Единицу выгрузка объявляет сама, поэтому `unit_source =
explicit`; правило «форма задаёт единицу» остаётся для источников, которые
единицу не сообщают.

**Файл, из которого нельзя определить эти величины, комплектом не становится
вовсе.** Фактов не пишется, причина называется кодом контроля
(`file_inn_not_determined`, `file_period_not_determined`,
`file_reporting_type_unknown`, `file_not_parsed`, `unit_not_determined`)
и уходит в `dq_log`, когда ИНН известен. Файл, у которого не определился
и ИНН, в журнал попасть не может — привязать его не к чему, — и называется
только в выводе команды загрузки.

**Особенности формата, выверенные на 71 выгрузке.**

- Ни строка шапки таблицы, ни колонка кода не постоянны: шапка в строке 4
  или 5, колонка «Код строки» — с 7-й по 18-ю. Таблица ищется по подписям.
- Значение может стоять правее своей колонки заголовка: границы объединённых
  ячеек у шапки и у строк расходятся. Значение ищется от колонки периода
  до колонки следующего периода.
- К наименованиям и числам приклеены номера сносок: «Выручка7», «(29 390)5».
- Круглые скобки — способ печати, а не знак: у строки с `in_brackets` это
  величина расхода, у прочих — отрицательное число. Что именно, говорит
  справочник строк. Проверено: одна и та же организация печатает налог
  на прибыль в одном году в скобках, в другом без них.
- На листе ОФР бывает вторая таблица — «Дополнительные строки», где код 2410
  означает другое. Разбирается только первая таблица листа.
- Отчёт об изменениях капитала и отчёт о целевом использовании средств
  методикой не разбираются, их листы пропускаются.

**Актуальная версия года одна, и источник в это не входит.** Одна и та же
отчётность, полученная ресурсом и поданная файлом, — две доставки одного
комплекта: ключ факта источника не содержит. Держать актуальными обе значило
бы иметь за год два комплекта с общими фактами, поэтому загрузка снимает
признак со всех прочих версий года. Номер актуальной корректировки сообщает
только сам ресурс; по файлам актуальной считается наибольшая поданная, но
подача старой версии не отменяет загруженную новую.

## Класс финансового состояния

Арифметика зафиксирована в `methodology/scoring.yaml`. Модель класс
не определяет и пересматривать не вправе (инвариант 2).

**Балл показателя** = `0,6 · уровень + 0,4 · динамика`. Уровень отвечает
на вопрос «где показатель находится», динамика — «куда движется». Одной
динамики недостаточно: устойчиво хорошая, но не растущая организация
получала бы средний балл, а слабая, но улучшающаяся — высокий.

**Все шкалы кусочно-линейные.** Ступень давала бы скачок класса при изменении
коэффициента на сотую долю, а объяснить это пользователю нельзя. Между
опорными точками — линейная интерполяция, за крайними точками значение
не меняется. Единственная неустранимая ступень — границы классов, поэтому
рядом с классом всегда приводится балл.

**Опорные точки — не нормативы.** `calibration_points` в `scoring.yaml`
объявлены экспертной калибровкой с полем `origin`; `scale_type: absolute`
меняется на `percentile` одним изменением, когда наберётся база отчётностей.
Формулировки «ниже норматива» и подобные запрещены — правило в
`prompts/rules.md`. В «Ограничениях анализа» обязателен постоянный пункт
из `calibration_points.limitation_note`.

**Сумма весов групп равна 100**, проверяется при загрузке методики и тестом.

**Стоп-факторы, две градации.** Условие — в `metrics.yaml`, последствие —
в `scoring.yaml` с полем `rationale`: отрицательный собственный капитал
и автономия опускают класс до низшего, отрицательный оборотный капитал
и покрытие процентов ниже единицы ограничивают класс средним.

**У ветки МСФО стоп-факторы те же четыре, и объявлены они целиком в методике**
(`ifrs_issuer_type.yaml`, блок `stop_factors`): показатель, условие, отсечка,
градация, формулировка для документа и основание градации. Применяет их одна
реализация на замер и на расчёт по фактам —
`scoring/ifrs.py::evaluate_stop_factors`, — и она же считает применимость
по типу эмитента и сверку с аудиторским заключением.

Прежде перечень стоял в методике, а величины, по которым стоп-факторы
проверяются, — в `eval/ifrs_scoring_run.py`: замер их применял, а расчёт
по фактам звал оценку с пустым перечнем исключённых и писал
`stop_factor_code = NULL`. В замере стоп-фактор менял исход, в документе его
не было вовсе, и ноль сработавших был неотличим от непроверенных. Поэтому
`stops` у `assess` — **обязательный довод**, число проверенных стоит рядом
с числом сработавших, а тест падает, если боевой вызов подставляет пустые
стоп-факторы.

**Величина стоп-фактора объявляется показателем, а не статьёй.** У эмитента,
не раскрывшего капитал отдельной строкой, статьи нет, а показатель считается —
поэтому в справочнике показателей МСФО заведены `equity` и `nwc`, справочные,
вне балла. Чистый оборотный капитал считается по итогам разделов баланса:
отговорка «состав оборотных активов различается от эмитента к эмитенту»
не держится — итоги раздела опознаются справочником, и состав внутри итога
на разность не влияет.

**Условие, ссылающееся на величину, которой не бывает, не срабатывает
никогда.** Норма неприменимости `negative_nwc` ссылалась на показатель
`interest_cover`, которого в ветке нет: замер подставлял величину отдельным
словарём, и в расчёте по фактам норма молчала бы всегда. Теперь тест сверяет
каждый код показателя из условий с справочником показателей ветки.

**`in_scoring: false`** — показатель считается и попадает в заключение,
но в балл не идёт. Причина обязательна. Так исключены собственный капитал
(это стоп-фактор, а не измерение) и финансовый рычаг (монотонная функция
автономии, то же самое измерение дважды).

**Класс присваивается не всегда.** Балл считается при любых данных, но класс
требует достаточно широкого основания (`sufficiency` в `scoring.yaml`).
Главный признак — **не число показателей, а доля веса, которую забирает одна
группа**: четыре показателя в четырёх группах информативнее шести в одной.
Класс не присваивается, если одна группа весит больше половины, если групп
меньше двух или показателей меньше четырёх. Причина пишется
в `assessment.no_class_reason`, и ограничение БД не даёт сохранить оценку
без класса и без причины. Узость основания, не блокирующая класс, понижает
уверенность ступенчато.

**Исключение методикой ≠ неполнота отчётности.** Показатель с
`in_scoring: false` выпадает из балла по нашему решению, а не из-за нехватки
данных, и уверенность за это не понижается. В разложении он виден с причиной.

**Разложение обязательно.** Класс без разложения защитить нельзя, поэтому
`assessment` хранится вместе с `assessment_group`, `assessment_metric`
и `assessment_flag`: балл каждой группы, номинальный и фактический вес,
уровень и динамика каждого показателя по отдельности, причина исключения,
сработавший стоп-фактор и класс до его применения.

## Надзорные сигналы

Справочник — `methodology/signals.yaml`, расчёт — `scoring/signals.py`,
результат — в `assessment_signal` и в разделе 4 документа. Сигнал — не
интерпретация, а арифметика: условие проверяется по формуле, формулировка
берётся из справочника дословно и подставляется величинами. Модель их
не изобретает и не переписывает (инвариант 1).

Основание — экспертная оценка: по ПК «Стройсервис» система не отразила
единственный существенный факт. При чистой прибыли 40 839 тыс. руб.
собственный капитал ушёл с 691 до −442 тыс. руб., то есть из организации
изъято около 42 000 тыс. руб., и в заключение это не попало вовсе.
**Выявление такого не может оставаться на усмотрение модели.**

**Три способа задать сигнал, и условие объявлено у всех трёх.** Обычный
сигнал задан выражением по строкам отчётности (`equity_withdrawal`,
`equity_contribution`, `transit_structure`, `extreme_margin`); структурный
сдвиг и интенсивность пересмотра считаются не формулой. Но `condition`
стоит и у них: иначе отсечка лежала бы в методике, а знак сравнения —
в коде, и, прочитав справочник, нельзя было бы сказать, когда печатается
формулировка. Сравнение модуля — такое же объявление (`compare_absolute`):
у структурного сдвига важен и уход доли, и её приход, и правило это лежало
в коде, пока признак был один.

**Перечень укрупнённых статей и их наименования — тоже методика.** Коды
и то, как статью зовёт **формулировка**, объявлены в `structure_shift.lines`;
прежде и коды, и наименования стояли в коде `scoring/engine.py`. Наименование
здесь своё не по небрежности: справочник строк зовёт статью «Итого
по разделу I», и в прозе сигнала это читателю ничего не говорит.

## Надзорные сигналы ветки МСФО

Справочник свой — `methodology/ifrs_signals.yaml`, загрузчик
`normalize/ifrs_signals.py`, входы собирает `scoring/ifrs_signals.py`, **а
арифметика общая** (`scoring/signals.py`): второе выражение того же правила
разошлось бы с первым, и увидеть это можно было бы только сравнив два
документа. Параллельность здесь та же, что у справочников статей
и показателей: величины опознаются кодами `ifrs.*`, отсечки привязаны
к валюте баланса, а не к выручке, состав признаков другой.

Чтобы выражение могло назвать величину МСФО, **грамматика формул приняла код
позиции**: `ifrs.<имя>` — такая же ссылка на величину, как четырёхзначный код
строки, и `prev()` работает с обоими. Голое строчное имя кодом позиции
не становится — точка обязательна, иначе «equity» читалось бы то константой
методики, то позицией.

**Отсечка капитальных признаков — 5 % валюты баланса**, порог существенности
ветки. Выручка базой не годится: у группы движение капитала соотносится
с размером баланса, а у холдинга без выручки отсечка от выручки не определена
вовсе.

Что перенесено и во что превратилось:

| Признак | В ветке МСФО |
|---|---|
| `equity_withdrawal` | выплаты акционерам **прямо** из отчёта о движении денежных средств, а не остатком «прирост капитала минус прибыль»: в консолидированной отчётности выплата стоит строкой, и косвенный признак ей не нужен |
| `equity_contribution` | прирост уставного капитала и эмиссионного дохода **по балансу**: у Сегежи поступление от выпуска акций 51 012, а прирост 87 333 — разница неденежная, и по потоку она теряется. Уровень «требует внимания»: поддержка акционера — обстоятельство в пользу организации, и внимания требует её направление |
| `structure_shift` | те же 20 п. п., итоги разделов консолидированного баланса |
| `revision_intensity` | объявлен **недействующим**: комплектов у эмитента один-два, а расхождений на паре 89, и отсечка по такому знаменателю мерила бы размер набора. Это единственное недействующее правило ветки |
| `transit_structure` | **не переносится**: выручка к валюте баланса выше двадцати у группы недостижима, а признак, не срабатывающий никогда, неотличим от невыполненного контроля |
| `extreme_margin` | **отложен**: чистая прибыль МСФО включает долю в ассоциированных, переоценку и курсовые, и у холдинга рентабельность выше половины выручки — норма. Признак осмыслен по операционной марже, отсечки для неё пока нет |

**Предмет признака выплат — изъятие сверх заработанного, а не выплата.**
Отсечка привязана к финансовому результату, а не к валюте баланса, и это
поправка по прочтению документа: у ФосАгро дивиденды 46 620 при прибыли
114 243 — обычная дивидендная политика, а признак давал надзорный уровень
и эскалацию. Величина — превышение выплат над результатом; при убытке
превышение равно выплатам плюс убыток, поэтому **любая выплата при убытке
признак даёт**: заработанного не было вовсе. Третий случай формулой
не выражается вовсе — выплата при сработавшем стоп-факторе есть
обстоятельство независимо от размера, и условие это об исходе оценки,
а не о величинах: признак объявляет `requires_stop_factor`, отсечка у него
нулевая намеренно, а ограничивает его сам стоп-фактор.

Плюс два признака ветки, которых в РСБУ нет. **Необъяснённое движение
капитала** — сверка тождества IAS 1.106: что не объяснилось совокупным
доходом, вложениями акционеров и выплатами им, то и признак; сравнивается
модуль, потому что необъяснённый прирост — такое же обстоятельство, как
необъяснённая убыль. **Смещение долга в краткосрочный мерит смещение,
а не уровень**: доля краткосрочного долга сама по себе — свойство долговой
политики (у ФосАгро 63,8 % при классе B), а признак о том, что срочность
изменилась за период. Отсечка та же, что у структурного сдвига, — 20 п. п.:
она уже откалибрована и мерит то же самое. У ФосАгро смещение 15 п. п.,
и признака оно не даёт.

**Величина, посчитанная формулой долей единицы, печатается процентными
пунктами по объявлению** (`as_percentage_points`): числовых литералов
в формулах нет, и умножить на сто выражение не может. Перевод относится
к представлению и применяется к величине и к отсечке сразу.

**Слоты формулировки объявлены справочником** (`slots`: имя → код величины).
Прежде код прибыли стоял в коде подстановки числом «2400» — то есть
формулировка ветки МСФО подставляла бы величину, которой в её данных нет.
Неизвестный слот справочник не загрузит: подстановка обрушилась бы
у первого же эмитента, у которого признак сработает. И **после слота
единицы точка не ставится**: наименование кончается точкой, и выходит
«выплачено 87 333 млн руб.. Стоп-фактор…».

**Недействующий признак объявляется вместе с причиной, и справочник этого
требует** (`active: false` без `inactive_reason` не загрузится, как
и действующий без отсечки). Подогнанная под два наблюдения отсечка выглядит
работающим правилом, а меряет размер набора; удалённый признак при этом
не отличить от забытого, поэтому он остаётся в справочнике и не срабатывает.
Непереносимые признаки перечислены отдельно (`not_transferred`) с причиной
у каждого: перечень ветки сравнивают с перечнем РСБУ, и отсутствующий
признак без причины неотличим от забытого.

**Единица комплекта подставляется в формулировку** (`{unit}`): «46 620»
без единицы читатель прочтёт в тех единицах, которые предположит сам,
а консолидированная отчётность составляется в миллионах. Формулировка,
единицу не называющая, слот не содержит.

На живых комплектах срабатывает один признак: у Сегежи `equity_contribution` —
прирост 87 333 млн против отсечки 7 087 млн при убытке 88 378 млн. У ФосАгро
не срабатывает ни один, и это верно: дивиденды умещаются в прибыль, смещение
долга не дотягивает до отсечки. Прежде раздел 4 документа по МСФО держался
на одном аудиторском заключении, и докапитализация Сегежи до читателя
не доходила вовсе.

**Порог задаётся долей, когда абсолют бессмыслен.** `threshold_of` привязывает
отсечку к строке отчётности: расхождение в миллион у крупной организации —
округление, у малой — вся деятельность.

**Уровень сигнала — это место в документе и в порядке вопросов.**
`attention` — обстоятельство, требующее объяснения; `supervisory` — признак,
по которому принимают надзорные меры: он старше стоп-фактора в очереди
вопросов и он же включает эскалацию в предложениях по действиям.

**Происхождение и зрелость порога — разные сведения, и полей поэтому два.**
`origin` отвечает, откуда взялась величина; `calibration_status` — на скольких
наблюдениях она проверена. Статус обязателен и начинается машинным признаком:
`preliminary` или `calibrated`. Сейчас предварительны все: наблюдений три,
и это не выборка, а три организации. К каждому сигналу в документе печатается
величина и отсечка — тезис без них проверить нечем.

**Доля укрупнённой статьи в балансе не ограничена диапазоном 0–100 %,
и структурный сдвиг правомерно выходит за ±100 п. п.** Для статей актива
(1100, 1200) доля лежит между нулём и сотней, для статей пассива — нет:
при отрицательном собственном капитале доля отрицательна. У ПК «Стройсервис»
1300/1600 даёт 691/916 = 75,4 % на конец 2023 года и −442/418 = −105,7 %
на конец 2024 года, сдвиг −181,2 п. п. Величина верна, единица — именно
процентные пункты. Сигнал сравнивает **модуль** сдвига: важен и уход доли,
и её приход.

**Величина сигнала набирается один раз и хранится готовой.** В разделе она
печатается дважды — в предписанной формулировке и в основании под ней, —
и набирать её второй раз нельзя: разрядность и знак разойдутся. Строку делает
`scoring.signals.shown` по `display_scale` и `as_absolute` справочника, обе
строки ложатся в `assessment_signal.details` (`value_shown`, `threshold_shown`),
а документ печатает их как есть. Оценка, посчитанная прежней версией, основания
не получает вовсе, и в журнал идёт требование пересчитать: молча набрать
величину заново — значит вернуть то самое расхождение. Прежде рядом стояли
«изменение — 181,2 п. п.» и «Расчётная величина: -181,18».

**Знак величины — математический минус, а не дефис**, и свёртка многострочной
формулировки в одну строку обязана щадить неразрывный пробел: `" ".join(
text.split())` съедает его вместе с разрядами числа.

**Интенсивность пересмотра считается по журналу качества.** Число
пересмотренных величин с кодом `period_value_mismatch` делится на число
актуальных комплектов организации. Пересмотр сравнительных данных правомерен,
но его интенсивность — сама по себе характеристика отчётности, которую прежде
никто не интерпретировал.

**Считается величина, а не строка журнала.** Записи журнала — история,
и повторная загрузка того же комплекта кладёт их заново: сигнал рос бы
от наших прогонов. Расхождение соглашения о знаке сюда не попадает вовсе —
у него свой код. Обе поправки вместе сняли сигнал у половины набора:
срабатывал у 22 организаций из 47, стал у 11.

**В промпт идут наименования сигналов, а не их величины.** Формулировки
печатает расчёт, и дублировать их модели незачем; числа предписанных
формулировок в блоках отсутствуют, поэтому процитировать сигнал модель
не может — постпроверка сочла бы эти числа посторонними. Следствие: сигнал
она видит как основание для вопроса, но истолковать его в разделе 3 не может.
Это записано в `BACKLOG.md` и снимается задачей 18, где сигналы пойдут
тезисами вместе с величинами и кодами.

## Языковая модель

Инструкция — `prompts/conclusion.md`, общие правила — `prompts/rules.md`,
подставляются в шаблон при сборке, а не дублируются в нём.

**Постпроверка сверяет не только числа.** Три независимые проверки, каждая
отклоняет ответ целиком: числа (`llm/verify.py`), формулировки
(`llm/wording.py`) и утверждения о состоянии показателя (`llm/claims.py`).

- **Отсылка к нормативу запрещена словарём.** Методика абсолютных нормативов
  не содержит принципиально, но модель возвращает их текстом: «коэффициент
  текущей ликвидности 0,82, что ниже норматива». Словарь обходится
  перефразировкой — и это не повод его не иметь: обходится он намеренно,
  а нарушения происходят случайно.
- **Порог нельзя ввести и числом.** «Что ниже 1,0» — тот же норматив без
  слова «норматив», а 1 разрешена без привязки как тривиальная. Поэтому 0, 1
  и 100 теряют разрешение, когда стоят объектом сравнения. Исключение —
  **порог стоп-фактора при своём показателе**: «покрытие процентов ниже 1»
  правомерно, «текущая ликвидность ниже 1» нет, хотя число то же.
- **Нельзя называть нерассчитанным показатель, значение которого дано.**
  Сверка идёт с блоком, а не со словами. Ограничения проверки — в `BACKLOG.md`.
- **Класс и балл не пересматриваются** (`llm/verdict.py`). Названный класс
  должен совпадать с присвоенным; когда класс не присвоен, назвать любой —
  выдумать оценку; итоговый балл в текст не выносится, если он не раскрыт
  в блоке ОЦЕНКА. Балл группы под запрет не подпадает — он в блоках есть.

**Числа готовых формулировок цитируются без кода.** В блоках ФЛАГИ и
ОГРАНИЧЕНИЯ величины подставлены в прозу («финансовые вложения составляют
21,2 % активов»), кода при них нет, а привести текст модель обязана дословно.
Такие числа объявлены цитируемыми — то есть проверка для них выключена, и это
записано в `BACKLOG.md` как долг, а не как решение.

**Тексты, которые модель цитирует дословно, обязаны проходить постпроверку.**
Правило распространяется на всё содержимое `methodology/` и `prompts/`,
попадающее в промпт: оговорки (`note`), тексты флагов, формулировки
стоп-факторов, ограничения, примеры в инструкциях. Такой текст модель обязана
привести без сокращений — и если он сам нарушает правила постпроверки, ответ
отклоняется за наше нарушение, а не за её.

Проверено на живом случае: оговорка о долях говорила «сумма приведённых долей
меньше 100 %», постпроверка увидела сравнение с числом без кода показателя
и отклонила верный ответ. Формулировка переписана.

При написании формулировки проверяй по тем же правилам, что и ответ модели:

- число в тексте либо стоит при своём коде, либо его там быть не должно;
- сравнения с числом («меньше 100 %», «ниже 1,0») не писать вовсе —
  формулируй словами: «всей структуры баланса не исчерпывают»;
- слова «норматив», «при норме», «не менее», «должен составлять» запрещены
  и нам, а не только модели;
- глагол при величине изменения должен соответствовать её знаку.

Это же относится к **шаблонам документа** (задача 9): текст, попадающий
в заключение рядом с числами, живёт по тем же правилам.

**Условные формулировки методики в контекст не идут.** Оговорка «в упрощённой
отчётности не рассчитывается» — свойство методики, а не факт об организации;
поданная рядом с посчитанным значением, она читается как утверждение. Модель
написала так про Газпром, который сдаёт полную отчётность, и постпроверка
чисел этого не поймала — чисел в утверждении нет. Поэтому в `metrics.yaml`
два разных поля: `note` — безусловная оговорка о содержании показателя, идёт
в блок ОГРАНИЧЕНИЯ; `methodology_note` — описание методики, **в промпт
не передаётся никогда**, что проверяется тестом.

Та же пара полей в `lines.yaml`: оговорка о содержании строки идёт
в ОГРАНИЧЕНИЯ, сопоставление с другим набором отчётности («Со строкой 1240
полного набора не сопоставима») — нет. И в `scoring.yaml` у стоп-фактора:
`statement` — что он означает для этой организации, идёт в блок ОЦЕНКА;
`rationale` — почему методика устроена так («отрицательный оборотный капитал
бывает штатным режимом при быстром обороте»), в промпт не идёт, иначе рядом
с оценкой читается как оправдание положения именно этой организации.

**Блок ПОКАЗАТЕЛИ содержит только фактическое состояние** показателя у этой
организации: значение либо `not_calculable` с конкретной причиной. Оговорок
в нём нет вовсе — рядом со значением модель читает любую из них как
утверждение об организации.

**Модель получает только посчитанное.** `llm/context.py` собирает шесть блоков
из `fact_report`, `metric_value` и `assessment`; исходный файл отчётности
ей не передаётся, и каждое число идёт с кодом строки или кодом показателя.
Числа подаются уже округлёнными — у модели не должно быть повода считать самой.

**Постпроверка сверяет пару «число — код», а не число само по себе.**
Проверки одного числа недостаточно: модель может назвать верную величину
при чужом коде — подставить значение текущей ликвидности к коэффициенту
автономии. Число совпадёт со входным, а утверждение будет ложным.
Поэтому `llm/verify.py` для каждого числа ищет ближайший код или наименование
показателя (`llm/pairs.py`, окно 160 символов) и сверяет число со значениями
именно этого показателя. Три вида нарушения: `not_in_blocks` — числа нет
во входных данных, `no_anchor` — число приведено без кода, `wrong_anchor` —
число принадлежит другому показателю.

Порядок выбора якоря такой. Первым берётся код, **приписанный к самому числу
справа** в скобках и один — «снизилась на 1,6 % (1600_chg_pct)». Иначе
ближайший код **слева**: по формату `prompts/rules.md` код ставится перед
значениями, и без этого правила второе число перечисления привязалось бы
к следующему показателю. Код справа, отделённый словами, берётся последним.

Две тонкости, обе найдены на живых ответах. Тег, приписанный к числу, этому
числу и принадлежит: во фразе «на 1,6 % (1600_chg_pct) до 25 736 328 136» сумма
привязывается к 1600, а не к коду процентного изменения. И код, за которым
внутри тех же скобок стоит своё число — «(nwc_chg_abs -1 248 224 574)», —
тегом не является: он относится к числу внутри скобок.

**Изменение сверяется по модулю, но направление проверяется отдельно.**
У изменения направление задаёт глагол, а не знак: «сократилась на 59,6 %» —
правильный русский, «сократилась на −59,6 %» — нет. Поэтому якоря `_chg_abs`
и `_chg_pct` принимают величину с любым знаком, а `llm/direction.py` сверяет
глагол при числе со знаком входного значения: `wrong_direction`. Так ловится
«коэффициент вырос с 1,23 до 0,82», где оба числа верны, а утверждение ложно.

Проверка направления намеренно осторожна и при сомнении молчит: отклонённый
ответ пользователю не показывается вовсе, поэтому ложное отклонение дороже
пропуска. Она не применяется, **если сама величина отрицательна**: у убытка
«рост убытка» означает падение показателя, и судить по глаголу нельзя. Слово
берётся только из того же предложения и только ближайшее к числу.

Разрешены без привязки только 0, 1, 100, номера годов, даты, коды форм
по ОКУД, номера нормативных документов после «№» и номера пунктов списка
(включая заголовки Markdown вида `### 4.`). Цитирование с меньшей точностью
допускается — это не вычисление; перевод единиц не проходит. Рассуждение
модели (`<think>`) вырезается до проверки и в заключение не попадает.

**Тире перед числом минусом не считается.** В русском тексте тире стоит
и при положительных величинах, отличить его от знака по написанию нельзя.
Отрицательная величина обязана приводиться со знаком: величина по модулю
с вынесенным в слова знаком («перешёл в отрицательную зону — 521 415 920»)
проверку не проходит и не должна.

**Отклонённый ответ наверх не возвращается.** Попыток три (`MAX_ATTEMPTS`),
затем `ConclusionRejectedError`. **Журнал `llm_log` пишется на собственном
соединении**, а не в транзакции вызывающего: иначе запись об отклонении
откатилась бы вместе с исключением, а нужна она именно тогда, когда что-то
пошло не так.

**Запись теста помечается `is_test`, и сторож следит за обеими сторонами.**
`llm_log` — доказательная база: по ней видно, что предъявлялось модели и что
она ответила, и статистика отказов считается по ней же. Прогон тестов однажды
её стёр, поэтому сессионная фикстура сравнивает состояние журнала до и после.
Сравниваются два числа, и они ловят разное: число боевых записей — удаление,
наибольший идентификатор — добавление. Незапомеченная запись теста от рабочего
прогона неотличима, и задним числом установить её происхождение нельзя. Признак
проходит и через `build_report`: тесту, которому нужен полный путь сборки,
иначе нечем пометить свою запись.

## Командная строка и цикл обработки

`finlib/pipeline.py` — полный цикл одной организации: получение, загрузка,
контроли, расчёт, оценка, текстовая часть, документ. Этапы вынесены из CLI
в именованный `Stage`: цикл нужен и вне терминала (регрессионный прогон
задачи 17), а CLI обязан называть этап, на котором остановился.

**Изменение существующей таблицы сопровождается догонкой — правило
с 17.09.2026.** `CREATE TABLE IF NOT EXISTS` не приносит в готовую таблицу
колонки и ограничения, добавленные позже: он видит таблицу и целиком
пропускает объявление. Поэтому правка объявления и `ALTER TABLE ... ADD
COLUMN IF NOT EXISTS` (либо `DO`-блок для ограничения) идут одним коммитом.

Дата важна, потому что граница применимости файла одна и явная. **Изменения
до 17.09.2026 догонок не имеют**: 23 колонки добавлены после создания своих
таблиц, и часть из них объявлена `NOT NULL` без значения по умолчанию —
дописать их в базу с данными нельзя, значение взять неоткуда. Файл,
обновляющий базу наполовину, хуже файла, который честно требует
пересоздания, поэтому для баз, отставших до этой даты, путь один —
`make db-reset`. Изменения после неё гарантированно применяются к живой базе.

**Схема базы сверяется с DDL до работы с данными.** `finlib/schema.py`,
этап `Stage.SCHEMA` — первый в цикле. Эталон строится из самого
`sql/001_schema.sql`: файл применяется во временную схему внутри точки
сохранения, метаданные снимаются, точка откатывается. Отдельный снимок
не поддерживается — он разошёлся бы с файлом третьим случаем.

Случаев уже два. Колонка `llm_log.code_version` и внешние ключи разложения
оценки были объявлены в файле и отсутствовали в рабочей базе: `CREATE TABLE
IF NOT EXISTS` не приносит того, чего не было при создании таблицы, а `ALTER`
для них никто не дописал. Узнавали случайно. **Нехватка объекта останавливает
работу**, лишнее в базе только пишется в журнал: колонка от прежней версии
работать не мешает. Сравниваются и определения целиком, а не имена: ключ
`fact_report_uniq`, потерявший `standard`, остаётся ключом и выглядит
исправным. Сверка идёт раз на процесс — прогон набора из 47 организаций
от неё не тяжелеет.

**Молчаливого продолжения после неудачи нет.** Каждый этап либо проходит,
либо поднимает `PipelineError` с этапом и причиной: заключение по неполным
данным хуже отсутствия заключения. Все комплекты в карантине — остановка
на контролях, ни одного рассчитанного показателя — остановка на расчёте.

`finlib/cli.py` на typer, точка входа `fin-analysis`: `analyze`, `ingest`,
`show`, `quality`, `reprocess`, `ifrs-markup`, `ifrs-confirm`, `ifrs-assess`,
`pdf-check`.

**Разметка и подтверждение — разные действия, и команды у них разные.**
Присест `ifrs-markup` пишет присвоенные коды в журнал подтверждений, но
комплект остаётся в карантине: решение «я посмотрел это извлечение и отвечаю
за него» принимается о комплекте целиком, а не о строке. Принимает его
`ifrs-confirm --inn --report-date --who`: комплект перезагружается с названным
автором, экран сверки видит подтверждённые строки наравне с опознанными
справочником, и карантин снимается, если неопознанных строк не осталось.
Основания, которые подтверждением не снимаются, команда называет. Ею же
устанавливается вид оговорки аудитора — `--caveat about_values |
about_disclosure`, — и команда печатает, что записалось и что предлагала машина:
предложение, принятое молча, было бы решением методики, сделанным приметой
в прозе.

`pdf-check`
проверяет документ МСФО до выгрузки в проект и базу не трогает вовсе:
извлекаются ли формы, нет ли страниц-изображений внутри них. `ingest`
загружает поданные вручную файлы
каталогом и прогоняет по ним контроли; `analyze --from-inbox` проводит одну
организацию полным циклом по тем же файлам. Пакетная загрузка на сплошном
карантине не останавливается — отбракованный комплект обязан остаться
в базе вместе с причиной, иначе откат транзакции унесёт и журнал.
**Сборка расчётом — режим по умолчанию, обращение к модели включается
`--llm`.** Прежде было наоборот, и замер 17.09.2026 на подвыборке из семи
организаций развернул умолчание: документов 4 из 7 против 7 из 7, тридцать
минут против полутора секунд, вклад модели — от 2 до 12 % слов одного
раздела при нулевом вкладе в остальные. Оба содержательных расхождения
оказались не в её пользу: пропала раскладка раздела 3 по группам показателей,
а у одной организации появилось обобщение, которого расчёт не делал
и которое нечем проверить — чисел в нём нет.

Документ называется заключением в обоих режимах: утверждения предписаны
методикой и получены расчётом всегда, различаются только связки между ними.
**Дисклеймер называет, кем связки поставлены**: при `--llm` — что они
порождены языковой моделью и воспроизводимость их не гарантируется, иначе —
что текст сформирован детерминированно и воспроизводим. В приложении
при сборке расчётом стоит «модель не привлекалась».

`reprocess` не обращается к источнику вовсе.

**Контроли качества прогоняются на каждом проходе цикла, в том числе
при пересчёте из кэша.** Прежде они выполнялись только внутри загрузки,
и пересчёт брал их результаты из журнала — от прошлой загрузки, какой бы
давней та ни была. Проверено 17.09.2026: два прогона подряд не тронули
`dq_log` вовсе, и графа отчёта «контроли качества» описывала позавчерашнюю
загрузку. Контроли считаются по методике, методика правится, и результат
обязан меняться вместе с ней — регрессионный прогон затем и запускается
при каждой её правке. Пересчёт карантина при `reprocess` — не побочный
эффект, а то самое поведение: изменилась методика, изменился результат.

## Регрессионный набор

Состав — `eval/sample_40.csv`, настройки измерения — `eval/regression_set.yaml`,
прогон — `eval/regression_run.py`, отчёты складываются в
`data/output/regression/` и в репозиторий не попадают. Перечень организаций
собирается вручную: ГИР БО ищет **только по конкретному ИНН**, и отобрать
организации по признаку у источника нельзя.

**Состав и правила измерения лежат порознь не для красоты.** Состав правится
руками и часто — это таблица, которую открывают в редакторе таблиц; правила
измерения правятся редко и с обоснованием. В составе — ИНН, заявленная
категория, основание включения, статус гипотезы, признак участия в прогоне
и ожидаемый исход.

**ИНН проверяется по контрольным разрядам при загрузке состава.** Опечатка
даёт не ошибку прогона, а тихий пропуск: источник просто не находит
организацию, и набор оказывается меньше, чем считает.

**Заявленная категория — гипотеза, а не факт.** Организацию включают ради
отрицательного капитала, а она сдаёт отчётность с положительным. Поэтому
признаки меряются по базе после прогона и сопоставляются с заявленным:
отчёт показывает заявленное покрытие против фактического, а не пересказывает
файл состава. Признак категории **необходимый, а не достаточный** — полные
формы сдают и средние организации, и крупные, — поэтому рядом печатается
графа «признак есть у других»: это не ошибка состава, а сведение о том,
что признак шире категории.

**Категория без машинного признака объявляет, почему его нет.** Признака
ликвидации в бухгалтерской отчётности не существует: организация в конкурсном
производстве сдаёт те же формы. Выдумывать признак ради полноты таблицы мы
не будем, поэтому у категории объявлено ровно одно из двух — `feature`
или `manual` с причиной.

**Ожидаемый отказ — тоже успех.** Кредитные организации вне периметра
методики, в ГИР БО их нет, и отказ по ним подтверждает правило, а не нарушает
его. Ожидаемый исход объявлен в составе (`analysis` или `refusal`), графа
«итог совпал с ожиданием» сверяет его с тем, что вышло, и в число остановок
такая организация не попадает. Сбой самого прогонщика отказом методики
не считается.

**Резерв остаётся в составе и в прогон не идёт.** Шесть однотипных вырожденных
балансов СФО прогон удлиняют, а нового не показывают; выбрасывать их из файла
при этом незачем — завтра понадобятся.

**Два контура, и они отвечают на разные вопросы.** Быстрый проводит набор
через расчётный слой без модели — минуты, поэтому запускается при каждой
правке методики, и это и есть регрессионный прогон. Полный добавляет
текстовую часть: обращение к модели занимает минуты на организацию, на полном
наборе это часы, поэтому он идёт перед приёмкой этапа и для сравнения схем
в задаче 18. Отчёт у обоих один.

**Метрик текстового слоя у быстрого контура нет вовсе.** Напечатать их нулями
значило бы сказать, что модель не прошла контроли, тогда как её не спрашивали.

**Признаки покрытия измеряются по базе, а не объявляются в файле состава.**
Объявленный признак описывал бы намерение: организацию включили ради
упрощённой формы, а она сдаёт полную, и набор врал бы о себе сам. В файле —
ИНН и основание включения, больше ничего. Коды методики, по которым признак
опознаётся, названы в том же файле, и набор не загрузится, если такого флага
в методике нет: переименованный флаг обязан сломать прогон, а не молча
превратить измерение в непокрытое.

**Контролируемые параметры стоят в шапке отчёта**: версия кода, модель, версии
всех семи справочников. Без них расхождение двух прогонов с одинаковой
вероятностью означает и правку методики, и смену модели.

**Неудача одной организации прогон не останавливает** — набор затем и нужен,
чтобы увидеть все отказы разом, — но и молча она не проходит: этап остановки
и причина стоят в отчёте отдельными графами. Это единственное место, где
`PipelineError` перехватывается и работа продолжается.

**Остановка на этапе и отсутствие класса — разные исходы.** Организация,
не дошедшая до оценки, о присвоении класса не говорит ничего, и в долю без
класса она не входит. По той же причине доля документов, прошедших контроли
текста, считается от тех, кто дошёл до текстовой части.

**Прогон по умолчанию не ходит в сеть**: считается по уже загруженным данным,
`--fetch` включает обращение к источнику. Правка методики новой отчётности
не требует — но контроли качества при этом выполняются заново, а не читаются
из журнала: правка допусков обязана менять их результат в том же прогоне.

**Размерные группы — только для описания набора.** Границы взяты из
постановления № 265 и в расчёте показателей, в оценке и в заключении
не участвуют. Организация без раскрытой выручки в разбивку не попадает:
угадывать размер по валюте баланса нельзя — у транзитной структуры активы
не описывают ни оборот, ни размер деятельности.

## Регрессионный набор МСФО

Состав — `eval/ifrs_sample.csv`, правила измерения —
`eval/ifrs_regression_set.yaml`, загрузчик — `eval/ifrs_set.py`
(`make ifrs-set`). Устройство то же, что у набора РСБУ, и правила те же:
состав и правила лежат порознь, заявленная категория — гипотеза, признаки
меряются по базе после прогона, ожидаемый отказ засчитывается успехом.

**Цена участия эмитента здесь другая, и она объявлена.** В РСБУ отчётность
берётся из ГИР БО по ИНН, и включить организацию ничего не стоит. Здесь
документ выгружается руками. Поэтому у эмитента объявлено `data_source`
(`cbonds` — выгрузка не нужна, `pdf` — нужна, `both` — документ разбирается,
а данные агрегатора служат независимой сверкой), а у каждого признака —
откуда берётся он сам. Объём ручной работы обязан быть виден из файла,
а не выясняться по ходу прогона: без выгрузки проверяются три признака
из двадцати одного — валюта, отрицательный капитал и убыток.

**Наличие документа считается по каталогу**, а не объявляется в составе:
объявленное наличие устаревает в тот день, когда файл переложили, и набор
врал бы о себе сам.

**Непокрытый признак объявляется вместе с причиной.** Отрицательное мнение
аудитора и отказ от выражения мнения добором документов не достаются:
эмитент с таким заключением отчётность публиковать перестаёт, и наблюдения
следует искать в РСБУ у организаций в банкротстве (задача 30). Молчание
об этом читалось бы как «признак покрыт».

## Контроль утверждений текста

Постпроверка чисел отвечает на вопрос «откуда взялось число». `llm/textcheck.py`
проверяет другое: не противоречит ли текст сам себе и расчёту. Экспертная
оценка трёх пилотных документов дала шесть методологических ошибок
интерпретации при чистом расчётном ядре — все в свободном тексте.

Блокирующие правила: технических идентификаторов в разделах нет; класс
не утверждается и не отрицается разом; заявленное изменение равно разности
приведённых уровней; шаблонный блок не выводится при невыполнении условия
применения; показатель с отменённым знаменателем не истолковывается; вопросы
не касаются строк вне применённого набора форм. Предупреждающие: «рост»
и «снижение» для показателей в днях согласованы со знаком (сокращение периода
оборота — это ускорение, а не замедление); конфликт флага и стоп-фактора
зафиксирован в тексте.

**Блокирующее нарушение отменяет ответ, предупреждение — нет.** Предупреждение
попадает в журнал и в замечания повторной попытки, но документу не мешает.

**Коды — механизм проверки, а не часть заключения.** Два требования выглядели
несовместимыми: постпроверка сверяет пару «число — код» и требует код при
каждом числе, а читатель технических кодов видеть не должен. Они совместимы,
если развести моменты: модель пишет размеченный текст, постпроверка работает
по нему, и только затем `llm/cleanup.py` снимает разметку. Код строки
отчётности — «(1600)» — остаётся: для бухгалтерской отчётности это обычная
ссылка, а не технический мусор.

Привязка по наименованиям вместо кодов не годится: русские наименования
склоняются, и по ним число не привязать без морфологии.

**Ссылка на строку в прозе — одно понятие на два модуля.** «Изменение
за период по строке 2120 (2120_chg_pct) — 1 832,1 %» называет перед тегом
код строки, а не величину. `verify.py` такие упоминания из проверки исключал,
а `pairs.py` про них не знал и отдавал им чужой тег — величина изменения
привязывалась к самой строке, и верный ответ отклонялся. Определение
(`pairs.LINE_REFERENCE`) одно и берётся из одного места: разбор пары
«число — код» идёт двумя модулями, и общее понимание у них обязано быть
общим, а не совпадающим по случайности.

## Свобода не исчезает, она переезжает

**Вынося раздел в расчёт, проверяй соседние.** Когда раздел 4 забрали
у модели, интерпретация сигналов, которую она складывала туда, переехала
в раздел 6: там она ввела порог «90 % выручки», которого методика не содержит,
и посчитала разность 691 − (−442) = 1 133 — прямое нарушение инварианта 1.
Заодно поехал раздел 2: вместо величин пошли производные.

Свобода, отнятая в одном месте, проявляется в ближайшем оставшемся, и увидеть
это можно только по замечаниям постпроверки в разрезе разделов. Поэтому
после каждого выноса раздела в расчёт замер повторяется, а замечания
разбираются **по разделам, а не только по кодам нарушения**: суммарное число
может не измениться, а место, где модель сочиняет, — измениться целиком.

Отсюда общее правило, к которому привёл замер 17.09.2026
(`eval/scheme_compare_2026-09-17.md`): **расчёт собирает документ, модель
связывает абзацы.** Оно точнее исходной постановки задачи 18, и данные его
поддерживают: везде, где модели оставили писать самой, вышло хуже.

## Структура документа надёжнее поиска по тексту

Третий случай подряд, и потому это уже правило, а не наблюдение:

- **раздел строки определяется ближайшим итогом ниже неё**, а не тем, к какому
  разделу её отнесло бы наименование: у ЛСР «Торговая и прочая дебиторская
  задолженность» стоит в обоих разделах баланса, и по имени её не развести;
- **примечание находится по ссылке из строки формы** — «Амортизация 6, 7»,
  «Процентные расходы 9», «(прим. 21)», — а не по совпадению наименования:
  у Норникеля «амортизация дисконта по оценочным обязательствам» есть
  финансовый расход, и поиск по слову «амортизация» находит первой её;
- **тип аудиторского мнения читается из заголовка раздела** — МСА предписывают
  называть его «Мнение», «Мнение с оговоркой», «Отрицательное мнение» или
  «Отказ от выражения мнения», — а не разбором текста заключения.

Общее у трёх случаев одно: документ сам объявляет искомое своим строением,
и это объявление точнее любого совпадения слов. Поиск по наименованию даёт
**не отсутствие ответа, а чужой ответ**, и это худший из исходов — он
не отличается от верного ничем.

**Правило: прежде чем искать по наименованию, проверь, не объявляет ли
документ искомое своей структурой.** Сноска, номер, заголовок, порядок
строк, ближайший итог — сначала они, и лишь потом слова.

## Одна величина — один код, считающий её

**Два пути к одному ответу расходятся, и расхождения не видно, пока их
не сравнить.** Это не про красоту кода: обе реализации верны по отдельности,
обе покрыты тестами, и отвечают они по-разному — а какая из двух попала
в документ, зависит от того, кто спросил. Найдено это на экранах сверки
и разметки, которые по одному комплекту ЛСР давали «14 итогов сошлись из 14»
и «провал контроля»: составы итога знал один, а не оба.

Проверено 20.09.2026 по всему проекту, и случаев оказалось пять. Все сведены
к одной реализации:

| Величина | Было | Стало |
|---|---|---|
| сходимость итога по лучшему из составов | своя у разметки, своя у сверки | `ifrs_markup.best_composition` |
| балл по кусочно-линейной шкале | своя у РСБУ, своя у МСФО | `scoring/scale.py::interpolate` |
| доля статьи в валюте баланса | три выражения в трёх модулях | `ifrs_extract.share_of_assets` |
| раздел строки по ближайшему итогу ниже | своя у разбора, своя у разметки | `ifrs_extract.nearest_total_below` |
| число месяцев периода | `months_of` и выражение рядом | `metrics.ifrs.months_of` |

Два из пяти уже расходились на данных: шкалы РСБУ и МСФО при совпавших
абсциссах давали разный балл (одна брала верхнюю точку, другая нижнюю),
а «доля активов» у строки отчёта о прибылях означала долю выручки —
и в этом виде попадала в графу `share_of_assets` журнала подтверждений.
Второй случай показывает и признак: **графа считает то, как называется**,
и расхождение имени с содержанием — тот же дефект, только заметный глазом.

**Разные входы при одном правиле — это норма, и они объявляются.** Разбор
знает только итоги, опознанные справочником; разметка добавляет к ним
присвоенные человеком — у Норникеля итоги обоих разделов обязательств
не подписаны вовсе. Правило при этом одно, и живёт оно в одном месте:
расходиться должны входы, а не арифметика.

## Ноль срабатываний неотличим от невыполненного контроля

**Контроль обязан сообщать не только число нарушений, но и число проверенных
объектов.** Ноль нарушений при неизвестном числе проверок — не успех, а
отсутствие сведений. Так выглядел `check_text`: цикл обработки не передавал
ему контекст, шесть блокирующих правил не работали вовсе, а в замерах стояли
нули и читались как чистый текст.

- **Счётчик проверенного лежит рядом со счётчиком нарушений** и попадает
  туда же, куда нарушения: в `dq_log`, в `llm_log`, в отчёт прогона. Контроль,
  пишущий только срабатывания, при нуле срабатываний неотличим
  от невыполненного. Контроли сходимости этому правилу отвечают — они пишут
  и `pass`, — а `jump_detection` пишет только предупреждения, и сколько пар
  величин он сравнил, не знает никто.
- **Ноль проверенных объектов объявляется явно.** Контроль, у которого
  не нашлось объекта, сообщает «не выполнялся» и причину — так же, как
  контроли сходимости различают «не сошлось» и «проверять нечего».
- **Вынося раздел или этап из-под модели, проверяй, что сторожит контроль.**
  Правила текста привязаны к номерам разделов, и после выноса разделов 2, 4
  и 6 в расчёт шесть правил `textcheck` остались сторожить текст, которого
  модель больше не пишет. Это тот же переезд, что описан выше, только
  переезжает не свобода модели, а слепое пятно, и увидеть его по нулям нельзя.

Отчёт прогона и сводка качества печатают обе величины рядом: «нарушений N
из M проверенных». Графа с одним числом не заводится.

**Документ не утверждает о методике того, чего в методике нет.** Утверждение
«не применяется» допустимо ровно тогда, когда неприменение объявлено
методикой. Оговорка, выдающая наш пробел за решение, — худший вид дефекта
этого семейства: она **закрепляет** пробел вместо того, чтобы его показать,
и снимает вопрос, который иначе задал бы читатель.

Сказано ценой прямого нарушения. 21.09.2026 в заключение по МСФО была добавлена
оговорка «стоп-факторы, ограничивающие класс, в ветке МСФО не применяются» —
с виду честная и написанная против молчания. Методика между тем их содержала
(задача 26: перечень, применимость по типу эмитента, сверка с разделом
аудиторского заключения о непрерывности деятельности), и не применялись они
по другой причине: механизм жил только в замере, а расчёт по фактам звал оценку
с пустым перечнем исключённых. Правильным ответом было провести стоп-факторы
в расчёт, а не объявить их отсутствующими.

Отсюда порядок: **прежде чем написать в документ «не применяется», «не
считается», «не проверяется», найди это объявление в `methodology/`.** Нет
объявления — это долг в `BACKLOG.md`, а не оговорка читателю. Молчание
при этом тоже неверно, но неверно тише: оно не мешает найти пробел.

**Контроль, всегда дающий один ответ, неотличим от невыполненного.** Третий
случай того же класса, и самый скрытный: проверка валюты искала маркер `₽`,
а нормализация превращает знак валюты в пустую строку — пустая же строка
входит в любой текст. Условие возвращало истину всегда. Ни один тест не падал,
ни один документ не был отклонён по этой причине, и по журналу это выглядело
как «валюта определена» у каждого комплекта. Ноль срабатываний хотя бы
заметен глазом; единица срабатываний не заметна ничем.

Отсюда правило: у проверки, построенной на сравнении с перечнем, перечень
обязан быть проверен на вырожденные элементы — пустую строку, значение
по умолчанию, `None`. И у каждой проверки должен существовать вход,
на котором она отвечает «нет»: если такого входа не придумывается,
проверки нет.

**Проверка наличия чего-либо в коде должна быть структурной, а не
текстовой.** Упоминание идентификатора не означает, что он работает: код
контроля может стоять в модуле, который никто не вызывает, наименование —
в ветке, куда не попадают, импорт — в файле, исключённом из сборки. Поэтому
«вызывается» определяется как достижимость от точек входа по графу импортов,
а не как вхождение подстроки.

Сказано это дорогой ценой: реестр контролей, заведённый против дефекта
«написано, но не вызывается», воспроизвёл его внутри себя. Первая редакция
искала код контроля текстом по `src/` — и признала бы подключённым весь
разбор МСФО в тот же день, когда он был написан, хотя цикл его не зовёт.
Механизм проверки подвержен ровно тем же дефектам, что проверяемое.

**Умолчание допустимо там, где ошибка обнаруживается следующим шагом.**
Вид отчётности принимается полным, когда маркеров нет, — и ошибка вскроется
немедленно: примечания, которых требует методика для полной отчётности,
не найдутся. Валюта, единица измерения и разделитель разрядов умолчаний
не имеют: там ошибка тихая — баланс сойдётся, коэффициенты будут верны,
и неверными окажутся только величины. **Везде, где ошибка умолчания тихая,
умолчания быть не должно.**

**Четвёртый случай — аннуализация.** Правило приведения промежуточных
величин к году написано в задаче 27, объявлено в методике и не срабатывало
ни разу: число месяцев приходило в расчёт литералом `months=12`. Пока
промежуточной отчётности в наборе не было, отличить это от работающего
правила было нечем; с первым же полугодовым комплектом выяснилось, что
величины полугодия шли бы в балл как годовые. Поэтому число месяцев берётся
из отчётной даты по правилу методики (`annualisation.months_from`), а не
задаётся вызывающим: **величина, которую можно передать снаружи, однажды
передаётся неверной и об этом не сообщает** — то же основание, по которому
параметр `standards` у `compute_metric` сделан обязательным.

**Папка эмитента содержит комплекты, а не один комплект.** Прогон приёма
брал по одному документу на папку — верно, пока рядом с PDF лежала только
текстовая выгрузка того же отчёта. С появлением промежуточной отчётности
рядом с годовой правило начало терять комплект молча. Отсюда: доставки
одного комплекта сводятся по прочитанному из документа — отчётной дате
и виду отчётности, — а не по папке, и отложенная доставка называется
вместе с причиной.

**Ключом словаря «эмитент → что-то» служит комплект, а не ИНН.** Тот же
дефект в трёх местах разом: вердикт о типе эмитента, восстановление
разметки и строка отчёта. Словарь по ИНН оставлял один комплект из двух
и приписывал его ответ обоим. Ключ — пара «ИНН, отчётная дата»; разметка
принадлежит комплекту, на котором сделана, потому что индекс строки
у другого комплекта означает другую строку, и перенос присвоения был бы
не помощью, а тихим присвоением чужого кода.

**Одна строка комплекта — одно решение человека.** Ключ уникальности журнала
подтверждений строится по строке (`inn, report_date, form_code, row_index`),
а не по паре «строка, код»: иначе исправление не заменяет ошибку, а ложится
рядом с ней. У ФосАгро «права пользования» так собрали три кода за три
присеста — балансовый от 18.09, детализацию и специфический от 20.09, —
и разметка не применялась ни одним: восстановление брало первый, правило
формы его отклоняло, и строка возвращалась в очередь. Обратное правило тоже
нужно: **один код у двух строк формы правомерен** — «Прочие расходы»
встречаются дважды, и прежний ключ второе подтверждение отвергал.

**Отклонённое притязание не молчит.** Строка, чьё притязание отклонено
правилом формы или раздела, возвращается в очередь — и присест начинается
с перечня того, что не применилось, с причиной у каждой записи. Иначе человек
размечает строку заново, не зная, что уже размечал, и так может пройти день.

**Восстановление опирается на место и наименование вместе.** Индекс строки
устойчив внутри одного разбора, но правка разбора его сдвигает — за один день
разбор менялся трижды. Поэтому строка по индексу берётся, если наименование
совпало; иначе наименование ищется по форме и берётся, если единственное;
иначе разметка не применяется, и это называется потерей, а не тишиной.
Потерей считается только случай «строка в очереди стоит, а разметка к ней
не применилась»: если строки в очереди нет, её опознал справочник —
размечать нечего.

**Четвёртое место — сам цикл разметки, и там дефект не только терял работу,
но и уничтожал сделанную.** Решение человека применялось к комплекту, взятому
по ИНН, и записывалось под его отчётной датой: у Сегежи три присвоения
промежуточного комплекта легли на годовой, а одно затёрло запись годового
по ключу журнала (код, ИНН, дата, наименование) — «Акционерам ПАО «Сегежа
Групп»» из −88 337 стало −15 268. Поэтому кандидат разметки несёт отчётную
дату (`Candidate.report_date`), ключом словаря, истории отмены и списка
пропущенных служит пара, а экран печатает дату рядом с ИНН: размечая, человек
обязан видеть, какой комплект перед ним. Заодно код перестал считаться
занятым, когда в другом комплекте того же эмитента он присвоен строке
с тем же наименованием: это одна статья, а не две.

**Тип эмитента определяется по комплекту и на промежуточном теряется.**
У ЛСР годовая отчётность даёт девелопера по эскроу, а полугодовая —
обычного корпоративного эмитента: статьи, по которым тип опознаётся,
в сокращённой промежуточной форме не раскрываются. Тип при этом свойство
организации, а не комплекта, и поправка показателя, привязанная к типу,
на промежуточной отчётности не применяется. Записано как долг.

**Написанное обязано вызываться, и это проверяется механически.**
`quality/wiring.py` — реестр контролей: у каждого объявлено, из каких модулей
он вызывается. Контроль без боевого вызова числится `not_wired` с датой
заведения, причиной и задачей, в которой подключается. Тест сверяет реестр
с исходниками **в обе стороны**: действующий контроль обязан иметь вызов,
а числящийся неподключённым обязан его не иметь — устаревший `not_wired`
означает работающий контроль, которому не верят. Подключил контроль,
не поправив реестр, — тест падает.

**Реестр работает, а не только заведён**: трижды за день он поймал реальный
дефект в момент появления — неподключённый контроль правдоподобия, весь
разбор МСФО, признанный бы подключённым по одному упоминанию, и незавершённую
запись комплекта, объявленную местом вызова прежде, чем цикл её позвал.

Реестр заведён после третьего случая конструкции «написано, но не
вызывается»: `check_text` месяцами не выполнялся в боевом прогоне,
`check_calculated` сторожил разделы, которых модель больше не пишет,
`check_plausibility` написан в задаче 22 и ждёт разбора форм из задачи 23.
Каждый раз код был верен и тесты зелены. Память об этом не работает.

**Где счётчик проверенного лежит сейчас.** `llm_log.checked_numbers` — пары
«число — код», сверенные постпроверкой; `NULL` означает, что она не
выполнялась, и это не то же самое, что ноль. `jump_detection` пишет `pass`
с числом сравнённых пар, а когда сравнивать нечего — «не выполнялся»
с причиной. Загрузчик пишет сводку `line_mapping` по каждой форме: сколько
кодов сопоставлено, сколько игнорируется методикой осознанно, сколько
неприменимо к набору, сколько неизвестно. Без неё ноль неизвестных кодов
ничем не подтверждён. `llm.textcheck.counted` отдаёт число объектов
по каждому правилу текста.

**Правило, утратившее предмет, объявляется явно.** Реестр
`textcheck.NOT_APPLICABLE` называет причину и дату; код правила остаётся
на месте — предмет вернётся, если раздел снова отдадут модели. Удалённое
правило нельзя отличить от забытого, а замолчавшее — от работающего, и тест
не даёт правилу одновременно стоять в реестре и срабатывать. Так объявлены
`risk_without_value` и `question_count`: раздел 4 собирает расчёт с величиной
при каждой формулировке, а перечень вопросов он же и ограничивает.

**Правила проверяют содержание, а не авторство.** Состав фактической базы,
строки, о которых спрашивают, повторы оснований — расчёт ошибается здесь
ровно так же, как ошибалась модель. Поэтому `textcheck.check_calculated`
применяется к разделам 2, 6 и — при сборке без модели — 3 в момент сборки
документа, а не в `verify`: разделы собираются в обоих режимах, и при сборке
расчётом проверять их больше некому. Правила о технических идентификаторах
там нет: в «Фактической базе» коды показателей — часть содержания, и правило
состава ищет величины именно по ним.

## Единая точка округления

Разрядность отображения задана в `metrics.yaml`, блок `display`, по единицам
измерения, с полем `origin`; показатель вправе объявить свою через
`display_scale`. Округляет одна функция — `metrics/display.py::round_to`,
и **дельты с темпами считаются от округлённых величин**, а не от полных.

Прежде дельты считались по полной точности, а уровни отображались
округлёнными, и документ становился арифметически несогласованным:
«рентабельность активов снизилась с 0,41 до 0,31 (изменение 0,11)» —
разность отображаемых уровней 0,10, а темп −25,6 % из 0,41 и 0,31
не выводится, получается −24,4 %. Формально ошибки нет, но читатель видит
противоречие и правильно ему не доверяет.

Отсюда следствия: в `metric_value` значения хранятся **полными** — округление
относится к представлению, а не к точности расчёта; в контекст модели, в текст
документа, в приложение и в вывод CLI идут **одни и те же** округлённые
величины; контроль `delta_does_not_match_levels` в `report/consistency.py`
сторожит равенство и блокирует документ при расхождении.

Это отменяет прежнее решение подавать модели точные значения: оно принималось
ради того же — чтобы текст и приложение не расходились, — и единая точка
округления решает задачу надёжнее.

**Ненулевая величина, округляющаяся в ноль, печатается словами** — «менее
0,01», «более −0,01», формулировки объявлены в блоке `display`. У Сегежи
коэффициент автономии 0,002 при собственном капитале 255 млн печатался как
«0,00», то есть как отсутствие собственных источников, которым он не является:
ноль здесь читается как утверждение, которого расчёт не делал. Разрядность
при этом не увеличивается — различить ноль от почти нуля обязаны слова,
а три знака у коэффициента читателю ничего не добавляют. Правило общее для
всех единиц: сумма, округляющаяся в ноль, читается как ноль так же ложно.
Настоящий ноль остаётся нулём — он раскрыт и равен нулю.

## Заключение в Word

Сборка — `report/`, выход `data/output/{ИНН}_{дата}.docx`. Раздел 1 и приложение
собираются детерминированно из базы (`report/summary.py`, `report/appendix.py`),
разделы 2–6 пишет модель. Ответ модели разбирается по заголовкам
(`report/sections.py`), и **отсутствие обязательного раздела — ошибка**,
а не повод отдать неполный документ. Порядок разделов задаём мы, а не модель.

**Документ не появится, пока ответ не прошёл постпроверку.** Незаверенный текст
не показывается пользователю (инвариант 8), а файл на диске — тем более.

**Печатается единица комплекта, а не единица стандарта.** Правило «форма задаёт
единицу» относится к определению её при загрузке; документ обязан печатать
то, что записано в `src_file.unit_code`. Заключение по ФосАгро печатало
«663 888 тыс. руб.» там, где в отчётности 663 888 млн: ошибка в тысячу раз,
которую не ловит ни один контроль сходимости — сходится всё, кроме самих
величин. Наименования по коду ОКЕИ объявлены в `lines.yaml`, блок
`units.names`; `UnitsDef.name_of` на неизвестном коде отказывает, а
`report/consistency.py::check_unit` блокирует документ, в котором напечатана
чужая единица, и объявляет несверенным пустой текст.

**Класс присваивается по напечатанному баллу** — `scoring/scale.py::
class_by_printed_score`, одна реализация на оба стандарта. У ПАО «Левенгук»
балл 79,997 давал класс B при напечатанных «80,00 из 100» и правиле «A —
от 80»: каждая величина верна, а документ противоречил себе. Единая точка
округления относится и к порогу класса.

**Отчётность называется по стандарту** (`report.yaml`, блок
`statements_wording`, падежи объявлены там же): «по данным бухгалтерской
отчётности» в заключении по консолидированной — утверждение о другом
предмете. Формулировка обязана быть объявлена у каждого стандарта.

**Документ говорит о своём комплекте.** Блокирующие отказы в «Ключевом выводе»
и вопросы к организации берутся только у комплекта этого документа: по годовой
отчётности ФосАгро перечислялись четыре отказа промежуточного комплекта,
а первым вопросом стояло «чем объясняются расхождения в комплекте за 2026
год» — комплект чужой, а расхождения наши. Отбракованный комплект другого
периода при этом не замалчивается: он назван в «Ограничениях анализа»
и в приложении.

**Наш пробел вопросом не становится.** Семейство отказа объявлено методикой
(`refusals.yaml`): из `data_missing` следует запрос к организации,
из `our_gap` и `not_applicable` — прямое «запрашивать нечего». Прежде документ
говорил о показателе двумя голосами: «Ограничения» — «величина есть
в отчётности, извлечение за нами», а «Вопросы» просили расшифровки того же
показателя.

**Тот же показатель дважды в одном разделе говорит дважды одно.** Отказ
расчёта и исключение из балла по причине «не рассчитан» — одно и то же:
нерассчитанный показатель в балл войти не может по устройству, а семейство
отказа у двух строк выходило разным, и раздел просил у организации то, о чём
строкой выше сказано «запрашивать нечего, извлечение за нами». Вторая строка
не печатается. Отказы при этом берутся за **отчётный** период документа: прежде
брался самый ранний, и заключение по 2025 году сообщало «за 2024 год величина
знаменателя пока не извлекается», об отчётном периоде молча.

**Вопрос о планах руководства — единственный вопрос о будущем.** Аудитор,
объявивший существенную неопределённость, указывает, что планы раскрыты,
а их исполнимости не оценивает: это и есть вопрос к организации. Примечание
называется то, которое назвал аудитор — ссылка структурна, как всякая ссылка
на примечание; не назвал — вопрос говорит о примечаниях вообще, и номер
не выдумывается.

**«Основание для выражения мнения» цитируется только при модифицированном
мнении.** Раздел стоит в заключении всегда, но при немодифицированном мнении
содержит предписанное МСА описание процедур аудита: у Сегежи в «Ограничениях
анализа» стояло «Мы провели аудит в соответствии с Международными стандартами
аудита» — слова аудитора, ничего не ограничивающие. Условие печати объявлено
у каждого цитируемого раздела (`ifrs_audit.yaml`, `quoted_sections`).

**Тезис по знаку заменяет тезис по части шкалы**, где методика это объявила
(`sign_supersedes_band` в `theses.yaml`). При операционном убытке отношение
процентов к результату доли не измеряет: рядом с «покрытие отрицательно»
стоял тезис «процентные платежи занимают значительную часть операционного
результата» — утверждение о доле, которой нет.

**Предложение по действиям не ссылается на пустой раздел.** Ссылки объявлены
полем `refers_to` и сверяются с наполнением раздела блокирующим контролем
`action_refers_to_empty_section`: «Запрос пояснений» отсылал к «Рискам
и надзорным сигналам», где расчёт ничего не выявил, потому что обстоятельством
был отбракованный комплект — а он описан в «Ограничениях анализа».

**В заключении об одной организации не называется другая** — блокирующее
правило `other_issuer_mentioned`. Класс тот же, что чужой стандарт: текст
говорит верную вещь не о том предмете. Так протекали наши рабочие пометки
из методики («у ЛСР расхождение между двумя мерами оказалось наибольшим»),
и поэтому у показателей МСФО поле разведено, как у РСБУ: `note` идёт
в документ, `methodology_note` — никуда. Ищется опознавательная часть
наименования целиком, а не отдельные слова: «дом» у «ДОМ.РФ Ипотечный агент» —
обычное слово языка, и первое измерение правила блокировало по нему всякий
документ. Перечень организаций ведёт база, родовые слова и организационные
формы объявлены методикой.

**Наибольшие изменения — по существенности, а не по проценту.** Процент
измеряет изменение относительно собственной прошлой величины и выносит наверх
мелочь: у Левенгука первым стоял итог раздела I с 9 778,1 %, у ФосАгро — налог
на прибыль к возмещению с 11 901 %. Существенность — доля изменения в размере
организации, и база объявлена по формам в справочнике каждого стандарта
(`lines.yaml` и `ifrs_lines.yaml`, блок `materiality`): валюта баланса
для статей на дату, выручка для статей за период, у строки потока базы нет
вовсе. Отсечка считается **после** отбрасывания величин, уже названных
обязательным составом: самыми существенными оказываются сами базы.

**База и равная ей строка в перечень не идут вовсе** (`same_as_base`
в блоке `materiality` обоих справочников). Итог пассива — та же величина,
что итог актива, только с другой стороны формы, и доля его изменения в валюте
баланса равна доле изменения самой базы: у Сегежи «Итого капитал
и обязательства» заняло вторую строку перечня, не сказав ни о чём. Отбор
по `seen` этого не ловит — код другой.

**Единица измерения определяется формой, а не ответом источника.** ГИР БО её
не сообщает вовсе, и прежде она принималась как предположение. Это дефект
данных, а не представления: ошибка в тысячу раз не ловится ни одним контролем —
баланс сойдётся, сходимость разделов сойдётся, коэффициенты будут верны,
а все абсолютные величины окажутся неверны. Правило «форма → код ОКЕИ» лежит
в `lines.yaml`, блок `units`, с полем `origin`; комплект из форм вне перечня
уходит в карантин блокирующим контролем `unit_not_determined`. Значения
`assumed` нет ни в базе, ни в документе.

**Определение единицы по форме — правило, а не факт из данных**, и оно
сломается на источнике, отдающем рубли. Поэтому рядом стоят два контроля
правдоподобия (`methodology/thresholds.yaml`, блок `magnitude`, оба с `origin`):
`balance_magnitude` — грубые границы валюты баланса, предупреждение
с требованием ручного подтверждения; `period_magnitude_shift` — отношение
величин смежных периодов, близкое к тысяче, блокирующий. Проверяется именно
кратность тысяче, а не всякий большой скачок: рост в триста раз бывает
хозяйственным событием и ловится `jump_detection`. Ноль из проверки границ
исключён: умножение на тысячу его не меняет, подменой единицы он быть не может.

**В разделе рисков называются все сработавшие стоп-факторы, а не только
назначивший класс.** У Сегежи их три — неопределённость непрерывности,
отрицательный оборотный капитал и покрытие процентов ниже единицы, — и раздел
называл один: два обстоятельства из трёх до читателя не доходили вовсе, хотя
каждое методика объявила основанием ограничить класс. Перечень хранится
в `assessment.stop_factor_codes`, а `stop_factor_code` остаётся тем, чьё
ограничение младше; ограничение базы не даёт полям разойтись — назначивший
класс обязан стоять среди сработавших.

**Ограничение, слабее присвоенного класса, действующим не называется.**
У Сегежи класс E, а формулировки оборотного капитала и покрытия процентов
обещают ограничение средним: обстоятельство в силе, ограничения оно
не накладывает, и без оговорки раздел противоречит своему же классу.
Оговорка в разделе рисков приводится один раз с перечнем — повторённая при
каждом стоп-факторе, она занимала больше места, чем сами формулировки.

**Стоп-фактор старше правила достаточности.** Отрицательный собственный
капитал — состояние, установленное одним показателем, и узость основания его
не отменяет. При сработавшем стоп-факторе класс присваивается, а недостаток
групп отражается отдельным полем `assessment.breadth_reason` и отдельной
фразой «балльная оценка не формируется». Прежде в разделе соседствовали два
взаимоисключающих утверждения: класс не присвоен и класс присвоен низший.

Из этого следует третье правило раскрытия балла: **при заполненном
`breadth_reason` балла нет нигде**, хотя класс присвоен, — балльной оценки
просто не существует, и число рядом с классом читалось бы как её итог.

Но и умалчивать об узости нельзя: устранение противоречия не должно стоить
потери сведений. Сразу за классом идёт абзац «Класс определён стоп-фактором
и от величины балла не зависит. Балльная оценка не формируется: расчёт
возможен по N группам показателей из M». Сырой текст `breadth_reason` туда
не переносится: он написан для случая, когда класса нет, и содержит слова
«интегральный класс не формируется», которые рядом с присвоенным классом
читаются как противоречие.

**Дисклеймер в шапке контекстный.** Он утверждает факт о конкретном
документе, а не описывает систему вообще: в документе, собранном расчётом,
фраза «текстовые связки порождены языковой моделью» — ложное утверждение
того же рода, что и шаблонные причины исключения.

**Наименование группы показателей открывает свой абзац раздела 3 в обоих
режимах.** Абзацы раздела разложены по тем же группам, по которым считается
балл, и наименование в начале абзаца это отношение называет. Прежде модели
переносить наименования групп запрещалось — ждали псевдозаголовок вместо
текста, — и сравнение документов 17.09.2026 показало цену запрета: тезисы
приводились дословно, а деление на группы пропадало во всех четырёх
документах. Проверка тезисов такого не ловит принципиально: она сверяет
утверждения, а не строение раздела. Требование стало отдельным блокирующим
правилом `group_heading_missing`, и оно ищет наименование **в начале абзаца**:
слова наименования стоят и в самих утверждениях («коэффициент текущей
ликвидности»), поэтому поиск по всему тексту молчал бы как раз там, где нужен.

**Веса групп хранятся долями, оба поля.** `nominal_weight` и
`effective_weight` — величины одного рода, и раньше первое хранилось
процентом, а второе долей. Приложение печатало 3000,0 % вместо 30,0 %.

**Причина исключения из балла имеет машинный вид и фиксированную иерархию**
(`ExclusionKind`): стоп-фактор → нет шкалы уровня → дублирует другой
показатель → нет данных. Текст причины обязан быть безусловным: он печатается
у любой организации, и разъяснение про отрицательный капитал у организации
с положительным — ложное утверждение.

**Класс присваивается не всегда, и это штатный исход.** У двух проб из трёх
класса нет. Тогда вместо класса печатается причина отказа и перечень
показателей, которых не хватило. Нехватка данных и исключение решением
методики разведены: первое — пробел в отчётности, второе — наше решение.

**Балл раскрывается по двум разным правилам, и их нельзя путать:**

| Где | Условие |
|---|---|
| раздел 1 «Ключевой вывод» | класс присвоен **и** стоп-фактор не сработал |
| приложение | класс присвоен; при стоп-факторе — с пометкой «до применения стоп-фактора» |

**Без класса балла нет нигде** — ни в разделе 1, ни в приложении, ни в промпте
модели, ни баллов групп. Причина: балл 67 при отрицательном собственном
капитале арифметически верен, но рядом с отказом присвоить класс читается как
противоречие. Балл единственной уцелевшей группы («Рентабельность» — 94 из 100)
опаснее вдвойне: класс не присвоен именно потому, что основание узкое.

**Документ проверяется на согласованность с собой** (`report/consistency.py`).
Каждый кусок по отдельности верен, а вместе они противоречили: «Ограничения»
сообщали, что отчётность за 2025 год в расчёт не включена, а «Происхождение
документа» перечисляло её среди принятых — выборка комплектов не отсекала
карантин. Противоречие в документе хуже отсутствия сведений, поэтому контроль
блокирующий: документ не формируется.

**Номер таблицы приложения ставит сборщик**, а не заголовок таблицы: таблица
может не строиться, и зашитые номера оставляли дыру — таблицы 3 не было,
а таблица 4 номер сохраняла.

**Графа считает то, как называется.** «Показателей в балле» — именно в балле;
ноль в ней не означает, что показатели группы не рассчитаны. Смешение
«рассчитано» и «участвует в балле» — повторяющийся источник ошибок.

**`make probes` пересчитывает и оценку.** Без этого набор данных расходился
сам с собой: показатели свежие, класс и разложение — от прежней версии
методики.

**Повторная попытка несёт перечень замечаний.** Температура нулевая, и повтор
с тем же промптом давал тот же ответ — вторая попытка была бессмысленна.
`service.with_corrections` дописывает к инструкции, что именно нашла проверка.
Замечания формулируются как факты о прошлом ответе, а не как подсказка, что
написать: содержание — работа расчёта, не модели.

## Состав и структура документа

Правила состава — `methodology/report.yaml`, загрузчик — `report/policy.py`.
**Состав разделов не зависит от того, что модель сочтёт заслуживающим
упоминания.** Экспертная оценка показала, чем это кончается: «Фактическая база»
по Газпрому не содержала совокупного долга, чистого долга, чистого оборотного
капитала и выручки — величин, на которых построены следующие разделы, — зато
содержала сведения о нераскрытии одной строки баланса.

**Семь разделов, и их порядок задаём мы.** Раздел 1 «Ключевой вывод»
и приложение собираются из базы, разделы 2–6 пишет модель (раздел 4 назван
«Риски и надзорные сигналы» и требует привязки каждого тезиса к величине
и порогу), раздел 7 «Предложения по дальнейшим действиям» снова собирается
из базы. Разделы 1, 4 и 7 обязаны остаться в документе, собранном
без модели: они от неё не зависят.

**Обязательный состав фактической базы задан методикой**: валюта баланса,
собственный капитал, выручка, финансовый результат, совокупный и чистый долг,
чистый оборотный капитал. Остальное попадает туда по машинному признаку —
участие в стоп-факторе, во флаге, вхождение в число наибольших изменений.
Величина, которой у организации нет, из перечня выпадает: требовать назвать
нераскрытую строку значит требовать выдумать число.

**Строка отчётности называется с кодом, показатель — наименованием.**
«БАЛАНС (актив) (1600)» — привычная ссылка, по которой читатель находит
величину в самой отчётности; `debt_total` и `nwc` — внутренние идентификаторы
методики, и тексту документа они чужие. Прежде печаталось и то и другое,
а правило состава искало обязательные величины по кодам показателей — то есть
требовало в тексте ровно то, отсутствия чего требует правило технических
идентификаторов. Два правила отменяли друг друга на одном тексте; противоречие
снято в пользу читателя. Правило состава ищет показатель по наименованию
(`TextContext.metric_names`), и в замечании называется наименование, а не код:
читать его будет человек. Код производной величины не печатается вовсе —
изменение названо словами рядом.

**Вопросы задаются по существу обстоятельства, а не о форме.** Вопрос
«почему не раскрыта строка 1410» содержательного ответа не имеет: упрощённая
форма её не предусматривает. Поэтому вопросы о строках вне применённого набора
форм запрещены блокирующим контролем, дубли снимаются, число ограничено
тремя–пятью, а порядок задан тяжестью основания (`subject_order`): надзорный
сигнал, стоп-фактор, конфликт флага и стоп-фактора, сигнал внимания,
отбракованный комплект, нерассчитанный показатель.

**Предложения по действиям — следствие машинных признаков, а не суждение.**
Признак (`Trigger`) — факт расчёта: сработал сигнал, сработал стоп-фактор,
класс не присвоен, комплект в карантине, данные устарели, провален блокирующий
контроль. Формулировки предписаны справочником. Документ, содержащий вопросы,
но не содержащий вывода о том, что делать, работу не заканчивает.

**Разрыв между отчётной датой и днём формирования документа — обстоятельство
документа, а не расчёта.** В шапке стоят обе даты и разрыв в месяцах.
Отсечка `freshness.max_months` — 15: комплект за истекший год сдаётся до конца
марта следующего, и до пятнадцати месяцев разрыва означают, что более свежей
годовой отчётности попросту нет. Разрыв больше означает другое — свежая
отчётность не сдана либо не получена, — и тогда в «Ключевой вывод» идёт
обязательная оговорка, что выводы описывают состояние на отчётную дату,
а не на день чтения.

**Флаг не отменяет стоп-фактор.** Флаг объявляет `scope` — показатели,
прочтение которых он ставит под вопрос, — но неприменимой группу показателей
не объявляет: признак, построенный на доле финансовых вложений, для такого
утверждения слишком слаб. Когда флаг и стоп-фактор из его области срабатывают
вместе, оценка **не смягчается**: флаг, отменяющий стоп-фактор, был бы путём
обхода оценки. Молчать о столкновении тоже нельзя, поэтому в «Ключевой вывод»
идёт обязательный абзац с фиксацией конфликта и требованием ручной проверки.

**«Ключевой вывод» объясняет не только результат, но и порядок его получения.**
Рядом с классом — шкала соответствия балла классу, при сработавшем
стоп-факторе — класс до и после его применения (класс E у набравшего по баллу
B и класс E у набравшего E — разные сведения, а выглядели одинаково), рядом
с уверенностью — правило, по которому она получилась. Провал блокирующего
контроля называется здесь же, наименованием контроля, а не кодом.

**Таблица причин разделена на две.** Постоянная причина исключения из балла
и период, за который показатель не рассчитан, — разные сведения, и прежде они
сливались в одну ячейку без указания периода. В сводке контролей по той же
причине стоят графы «Период» и «Объект контроля»: без них не установить,
какой период отбракован и какая строка не сошлась.

## Расчёт показателей

Определения — `methodology/metrics.yaml`, интерпретатор — `metrics/formula.py`,
без `eval`. Язык формул беден намеренно: четырёхзначное число — код строки,
`avg(код)` — полусумма на начало и конец периода, прописное имя — константа
из `thresholds.yaml`. **Числовых литералов в формулах нет**: любое число было бы
магическим, и разбор такую формулу отвергает. Число дней в периоде — константа
`DAYS`, потому что для отчётности за неполный год оно другое.

**Нормативов в методике нет.** Ни отраслевых, ни единых абсолютных: основа
интерпретации — динамика во времени, а не сравнение с числом неизвестного
происхождения. Исключение — четыре стоп-фактора, у которых порог содержателен
вне отрасли: отрицательный собственный капитал, отрицательный коэффициент
автономии, отрицательный чистый оборотный капитал, покрытие процентов меньше
единицы. Они помечены в `metrics.yaml` полем `stop_factor`.

**Один недостающий компонент отменяет показатель целиком.** Частичных
вычислений нет. В `reason` перечисляются все отсутствующие коды, в `reason_code`
— машинная причина: `missing_lines`, `no_previous_period`, `zero_denominator`.
Раскрытый ноль и нераскрытая строка ведут себя по-разному: при нулевых запасах
оборачиваемость не определена, но данные полны, и текст причины другой.

**Средние величины без предыдущего периода не считаются.** Полусумма требует
двух точек; подставлять значение на конец периода вместо средней запрещено —
это тихо исказило бы оборачиваемость и рентабельность. Следствие: за самый
ранний период в базе показатели по средним величинам не рассчитываются никогда.

**Предыдущий период определяется видом величины, а не близостью даты.**
Вид объявлен справочником позиций (`measures` в `lines.yaml`): умолчание
задаёт форма, строка, от своей формы отличающаяся, объявляет вид сама —
так устроены остатки денежных средств 4450 и 4500, стоящие в отчёте
за период и являющиеся величинами на дату. Выводить вид из кода строки
нельзя: правило «код на 1 — баланс» сломается на первой же форме с другой
нумерацией и на МСФО, где кодов нет вовсе.

| Вид | С чем сравнивается |
|---|---|
| на дату (`stock`) | конец предыдущего **годового** периода |
| за период (`flow`) | отрезок **той же длительности** за прошлый год |

У годовой отчётности обе базы совпадают, и правило ничего не меняет.
На промежуточной они расходятся всегда: у комплекта за полугодие баланс
сравнивается с 31 декабря, а отчёт о прибыли — с 30 июня прошлого года.
Прежде базой служил ближайший предыдущий период любой длины, и с первым же
полугодовым комплектом годовая прибыль сравнилась бы с полугодовым
изменением капитала. **Показатель берёт базу по виду каждой своей величины
отдельно**, а не одну на формулу.

**Сопоставимого периода нет — отказ, а не подстановка ближайшего**
(`no_comparable_period`, отдельно от `no_previous_period`: первая причина
исправляется загрузкой сопоставимого комплекта, вторая не исправляется
ничем — это самый ранний период организации). Проверено на наборе: у ПАО
«ТГК-2» комплект 2024 года в карантине, и пять показателей по средним
величинам считались от 2023 года, то есть через период. Теперь они
не считаются.

**Производные величины считаются в Python и подаются модели готовыми.**
Темпы изменения нужны в заключении постоянно, но во входных блоках их не было,
и модель делила числа сама — прямое нарушение инварианта 1. Поэтому
`metrics/derived.py` считает изменение за период (`1230_chg_abs`),
то же изменение в процентах (`1230_chg_pct`) и долю строки в валюте баланса
(`1230_share`); те же окончания у показателей (`cur_liq_chg_pct`). Состав —
в `metrics.yaml`, блок `derived`: перечни строк там, а не в коде.

Производные хранятся в `metric_value` рядом с показателями и **в балльную
оценку не входят**: скоринг перебирает показатели справочника, а динамика уже
учтена в балле показателя отдельным слагаемым. Справочник не примет показатель,
чей код оканчивается как производная, — иначе они делили бы один код.

**Процент не считается от неположительной базы и при смене знака.** «Рост
на 55 %» при движении капитала с −442 до −200 и «снижение на 150 %» при
переходе прибыли в убыток арифметически верны, но читаются как ложь. Причины —
`zero_denominator`, `negative_denominator`, `sign_change`; величины и
абсолютное изменение при этом остаются, и динамика описывается словами.

**Нет данных — производной нет вовсе**, а не `not_calculable`: иначе за самый
ранний период в контекст ушли бы десятки строк «нет предыдущего периода»
и содержательный отказ утонул бы среди них.

**Динамика требует минимум двух рассчитанных точек**, и её достоверность
ограничена доверием к периодам. `metrics.store.MetricSeries` отдаёт ряд вместе
с `confidence` каждой точки и готовым текстом оговорки: ряд, опирающийся на
`comparative_only` периоды, обязан сопровождаться этой оговоркой в заключении.
