```
Прочитай CLAUDE.md. Создай каркас проекта:

   pydantic, pydantic-settings, python-dotenv, pyyaml, python-docx, typer,

## Задача 2 — Справочник кодов строк

```
Создай methodology/lines.yaml — справочник строк форм РСБУ:
0710001 (баланс), 0710002 (отчёт о финансовых результатах),
0710005 (отчёт о движении денежных средств).

Для каждой строки: код, наименование, форма, раздел, знак (нормальный

4300, 4400, 4450, 4500.

Плюс src/normalize/lines.py — загрузчик справочника с валидацией через
pydantic и тесты на целостность: все коды в составе итоговых строк
существуют в справочнике.

## Задача 3 — Источник данных

```
Реализуй получение бухгалтерской отчётности российского юрлица по ИНН
из государственного информационного ресурса бухгалтерской отчётности ФНС
(bo.nalog.ru).

ВАЖНО: не пиши парсер вслепую. Сначала:
1. Разберись с фактическим протоколом: какой endpoint отдаёт поиск по ИНН,
   какой — саму отчётность, какой формат ответа.
2. Сделай один пробный запрос по ИНН 7736050003, сохрани сырой ответ
   в data/raw/ и покажи мне его структуру.
3. Только после моего подтверждения пиши разбор.

Требования к клиенту:
- сырой ответ всегда сохраняется на диск с контрольной суммой;
- повторный запуск берёт из кэша, сеть не дёргается;
- таймауты, ретраи с экспоненциальной паузой, вежливый User-Agent;
- если источник недоступен — внятная ошибка, а не заглушка.
```

## Задача 4 — Нормализация

```
src/normalize/ — приведение полученной отчётности к таблице fact_report.

Одна строка = один код показателя за один период за одну организацию.
Периоды: отчётный и предыдущий, оба сохраняются.

Требования:
- единицы измерения приводятся к тысячам рублей, исходная единица
  сохраняется в src_file;
- незаполненные строки пишутся как NULL, не как 0;
- загрузка идемпотентна: ON CONFLICT (inn, report_date, form_code, line_code)
  DO UPDATE;
- коды, отсутствующие в справочнике, не отбрасываются молча — логируются
  и попадают в отчёт о загрузке.

Тесты на идемпотентность: двойная загрузка не увеличивает количество строк.
```

## Задача 5 — Контроли качества

```
src/quality/ — контроли, выполняются до любых расчётов.

Реализуй:
1. balance_equality: 1600 = 1700
2. section_sum: итог каждого раздела равен сумме входящих строк
   (состав берётся из methodology/lines.yaml)
3. profit_chain: 2110 - 2120 = 2100; 2100 - 2210 - 2220 = 2200
4. period_continuity: значения на начало периода совпадают со значениями
   на конец предыдущего периода, если предыдущая отчётность есть в БД
5. mandatory_fields: 1600, 1700, 1300, 2110 заполнены
6. jump_detection: изменение показателя более чем в 5 раз — предупреждение,
   не блокирующая ошибка

Допуск на округление — из methodology/thresholds.yaml.
Результаты пишутся в dq_log. При провале блокирующей проверки статус
src_file = 'quarantine', расчёт не запускается.

Тесты на каждый контроль: случай прохождения и случай провала.
```

## Задача 6 — Расчёт показателей

```
methodology/metrics.yaml — определения показателей: код, наименование,
формула в кодах строк, группа, норматив, направление (больше-лучше /
меньше-лучше), требуемые входные коды.

Реализуй показатели ликвидности, финансовой устойчивости, долговой нагрузки,
рентабельности и оборачиваемости — состав согласуй со мной перед написанием
кода, покажи список.

src/metrics/ — интерпретатор формул. Требования:
- вычисления в Decimal;
- если хотя бы один требуемый код = NULL, показатель получает статус
  not_calculable с указанием отсутствующего кода. Никаких подстановок;
- деление на ноль -> not_calculable, не бесконечность;
- средние балансовые величины считаются как полусумма начала и конца
  периода, при отсутствии предыдущего периода — статус not_calculable;
- результат пишется в metric_value: код, период, значение, статус, причина.

Тесты: контрольный пример организации, посчитанный вручную, — все значения
должны совпасть до второго знака.
```

## Задача 7 — Флаги и скоринг

```
methodology/flags.yaml — условия срабатывания флагов с уровнями
critical / warning и формулировками для заключения.
methodology/scoring.yaml — группы показателей, веса групп, шкалы баллов,
стоп-факторы, границы классов.

src/scoring/ — расчёт баллов, применение стоп-факторов, присвоение класса.

Требования:
- стоп-фактор перекрывает баллы: при отрицательных чистых активах класс
  не может быть выше низшего;
- показатели со статусом not_calculable исключаются из группы, вес группы
  пересчитывается, а факт неполноты фиксируется и попадает в раздел
  "Ограничения анализа";
- если в группе нерасчётных показателей больше половины — уверенность
  оценки помечается как низкая;
- версия методики фиксируется в результате.

Тесты: набор синтетических балансов с ожидаемыми классами.
```

## Задача 8 — Модель и постпроверка

```
src/llm/ — работа с локальной моделью через Ollama.

1. prompts/conclusion.md — шаблон инструкции с плейсхолдерами для блоков
   ОРГАНИЗАЦИЯ, ДАННЫЕ, ПОКАЗАТЕЛИ, ФЛАГИ, ОЦЕНКА, ОГРАНИЧЕНИЯ.
2. src/llm/context.py — сборка этих блоков из БД. Модель получает только
   посчитанное, исходный файл ей не передаётся.
3. src/llm/client.py — httpx-клиент к LLM_BASE_URL, temperature=0.
4. src/llm/verify.py — извлечение всех чисел из ответа, нормализация,
   сверка с числами входных блоков. Исключения: 0, 1, 100, номера годов,
   номера пунктов списка. Возвращает verified: bool и список посторонних чисел.
5. Каждое обращение пишется в llm_log: модель, имя и текст промпта, ответ,
   результат проверки, посторонние числа, время.
6. Не прошедший проверку ответ не возвращается наверх, делается одна
   повторная попытка, затем ошибка.

Тесты на verify: ответ с выдуманным числом должен отклоняться.
```

- Задачи 8-9 — быстро, если ядро сделано правильно.

После каждой задачи: `git commit`, запуск тестов, короткая проверка руками
на одной реальной организации.
