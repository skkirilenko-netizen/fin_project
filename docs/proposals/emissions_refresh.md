# Предложение: политика обновления файлов выпусков эмитентов

Статус: **предложение исполнителя, без кода; `scripts/daily_run.py` не меняется.**
Поручение владельца 12.10.2026 (задача 4 ночи): гипотеза «устаревший файл»
у ПИК, Вуша и ГТМ из замера `no-bonds-impact` 09.10.2026. Числа — после
запуска владельцем `~/Work/fin-runs/emissions-freshness/run.sh` (только диск);
здесь — устройство, найденное чтением кода, и предложение.

## Что это за файлы и кто их читает

| Файл кэша (`data/raw/cbonds/`) | Что в нём | Кто читает |
|---|---|---|
| `emissions_<ИНН>.json` | выпуски эмитента: статус, признак дефолта, ISIN, объём, оферта (`get_emissions`, отбор по ИНН) | событийный слой (`cbonds_events.issues_of`): статус выпуска, дефолт по выпуску, объём долга (`routing_store._outstanding`), графики и оферты (`flows_fetch` берёт выпуски отсюда), срез биржи (`moex_fetch`) |
| `emissions_ru_outstanding.json` | перечень выпусков в обращении российских эмитентов (`get_emissions` с отбором, ~5 400 выпусков, 2 запроса) | универсум маршрута (`cbonds.bond_issuers`), рыночный круг (`market.universe`), охват (`eval/exit_criteria.py`), периметр (`bond_sources`) |
| `emitents.json` | карточки эмитентов: статус, отрасль, SPV (`get_emitents`, запрос на ИНН) | тип эмитента, выход из списка, отраслевой гаситель; **и перечень, по которому доставляются выпуски** |

## Как обновляются сейчас

1. **`emissions_<ИНН>.json`** — стадия «выпуски эмитентов» ежедневного
   прогона (`scripts/emissions_fetch.py`, решение владельца 25.09.2026):
   - ежедневно — **отбором** по `updating_date ≥ дня прошлого прогона`
     (единицы запросов) и запросом на каждого эмитента, у которого выпуски
     изменились;
   - по понедельникам — **полным обходом** всех эмитентов `emitents.json`
     (977 запросов) как контролем отбора; пропуски отбора печатаются;
   - файл переписывается только новым ответом; ответ, полученный сегодня,
     не переспрашивается; сбой эмитента оставляет прежний файл.
2. **`emissions_ru_outstanding.json`** — **ежедневным прогоном не обновляется
   вовсе**: в `scripts/` нет ни одного вызова `outstanding_universe(refresh=True)`
   (проверено поиском 12.10.2026). Перечень лежит с того дня, когда его
   забрали вручную, и `bond_issuers()` читает его с диска.
3. **`emitents.json`** — тоже вне ежедневного прогона: дополняется вручную
   `eval/cbonds_emitents.py` (спрашивает только недостающие ИНН).

Отсюда три возможные причины расхождения «перечень видит выпуск, файл —
нет», и замер `emissions-freshness` различает их числами:

| Причина | Признак в отчёте замера |
|---|---|
| файл не переспрашивался (сбой стадии, отбор пропустил, понедельничный обход не прошёл) | расхождения сосредоточены в файлах старше 7 дней; `emissions_delta_*` показывает отказы или отсутствие полного обхода |
| эмитента нет в `emitents.json` — стадия выпусков его не знает | эмитент перечня **без карточки** и без файла либо с давним файлом |
| источник отдаёт выпуск по отбору «в обращении», а по отбору «по ИНН» — нет либо с другим статусом | расхождения есть и у свежих файлов (≤ 7 дней), «ISIN есть, статус иной» |

Третья причина — свойство источника, а не наше: её не лечит частота, её
лечит сверка (и запрос к Cbonds). **Прежде чем объявить её свойством
источника — опровергнуть первые две** (урок «аномалия сперва наша»).

## Предложение политики

Порядок — от дешёвого к дорогому; каждый шаг — отдельной правкой и после
просмотра чисел замера.

1. **Перечень в обращении — ежедневно, первой стадией Cbonds после
   дефолтов** (`outstanding_universe(refresh=True)`, 2 запроса). Без этого
   и универсум маршрута, и охват, и периметр стоят на перечне неизвестной
   давности. Дата перечня — в журнал прогона (`routing_run.sources`)
   и в утреннюю сводку.
2. **Новые эмитенты перечня — карточка в тот же день**: ИНН, которых нет
   в `emitents.json`, дозапрашиваются (`get_emitents`, запрос на ИНН)
   до стадии выпусков; иначе стадия выпусков их не видит вовсе.
3. **Сверка «перечень против файла» — правило переспроса**: эмитент, у
   которого в перечне есть ISIN, которого нет в его файле (или он там
   с иным статусом), переспрашивается в тот же день, даже если отбор
   по дате его не назвал. Если и после переспроса ISIN нет — это не наш
   пропуск, а расхождение источника: строка в перечень вопросов к Cbonds
   (как прочерки), счётчик — в сводке; периметр такого эмитента и так
   не выводит («источники расходятся»).
4. **Понедельничный полный обход остаётся** — контролем отбора, как решено
   25.09.2026. Ежедневный полный обход не предлагается: он не нужен, если
   работают 1–3, а стоит десятую часть нормы.
5. **Возраст файла — видимое сведение**: в карточке эмитента дата файла
   выпусков; в сводке — число файлов старше 7 дней (после понедельничного
   обхода их не должно быть вовсе; ненулевое число — обход не прошёл).

## Оценка запросов к Cbonds в сутки (норма 10 000)

| Что | Запросов в сутки | Основание |
|---|---|---|
| перечень в обращении | 2 | ~5 400 выпусков, страница 5 000 |
| карточки новых эмитентов | число новых ИНН в перечне; ожидание — единицы | один запрос на ИНН (`in` источник не поддерживает) |
| выпуски новых эмитентов | столько же | один запрос на ИНН (со страницами при > 200 выпусков) |
| переспрос по сверке | число эмитентов с расхождением: первый день — по замеру `emissions-freshness`, дальше — единицы | один запрос на ИНН |
| **прибавка к нынешнему, установившийся режим** | **десятки** | менее 1 % нормы |
| первый день (догон) | 2 + без карточки + с расхождением | по замеру; верхняя граница — число эмитентов перечня (~700), < 10 % нормы |
| для сравнения: полный обход выпусков | 977 (по понедельникам, как сейчас) | `emissions_fetch.py` |

Для сравнения с остальным днём: снимок рейтингов, графики по изменившимся
выпускам и отчётность расходуют остальное; фактический расход по стадиям —
`routing_run.sources[].requests` (печатает `make status`). Если в понедельник
сумма с полным обходом подходит к норме, переспрос по сверке в этот день
не нужен — полный обход его покрывает.

## Вопросы владельцу

1. Шаги 1–2 (перечень и карточки — ежедневно) — заводить отдельной стадией
   `daily_run` или внутри стадии выпусков? Предлагаю внутри стадии выпусков:
   одна стадия — один источник правды о выпусках, и порядок «перечень →
   карточки → выпуски» не может нарушиться.

   **Ответ владельца 13.10.2026 (предварительный):** отдельной стадией
   перед стадией выпусков — свой учёт запросов, свой сбой; её сбой не валит
   выпуски. Окончательно — после отчёта `emissions-freshness/run.sh`;
   код `daily_run` до того не меняется.
2. Шаг 3 (переспрос по сверке) — после чисел замера: если расхождения
   сосредоточены в старых файлах, хватит шагов 1–2 и понедельничного обхода.
3. Расхождения источника (ISIN есть в перечне, нет по ИНН после переспроса) —
   в общий перечень вопросов к Cbonds или отдельный?
